# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A single-page personal "home" site (Korean: 갠홈) — a static HTML/CSS/JS app with no build step, deployed via GitHub Pages at `https://xngsuii.github.io/`. Data (profile, cards, pair posts, archive, images) lives in Firestore instead of localStorage, so edits persist across reloads, browsers, and devices; only the admin account (Firebase Authentication) can write.

There is no package.json, no bundler, and no test runner — the site is plain files served as-is.

## Commands

There is no build/lint/test tooling in this repo. To preview locally:

```
py -m http.server 8790
```

then open `http://localhost:8790/`. Serve over HTTP (not `file://`) — the app loads `js/firebase-store.js` as an ES module and needs a real origin for Firebase Auth persistence and CORS.

There are no automated tests. Verify changes by loading the page in a browser and checking the browser console for errors — do this before committing (see Workflow notes below).

## Architecture

**File layout** — everything is hand-split from what used to be one monolithic HTML file:
- `index.html` — markup only
- `css/style.css` — all styles
- `js/main.js` — UI logic and rendering (view switching, cards, pair posts, archive, image adjuster widget, rich-text editing)
- `js/firebase-store.js` — the persistence layer (see below)
- `js/firebase-config.js` — Firebase project config + `ADMIN_UID` (safe to be public; not a secret — see Security model)
- `firestore.rules` — Firestore security rules (read: public, write: admin UID only); must be pasted into the Firebase console manually, this repo file is not auto-deployed

**Storage adapter contract** — `main.js` never talks to Firestore directly. It only calls `storageGet(key, fallback)` / `storageSet(key, value)` (defined in `main.js`, thin wrappers around `window.SiteStore`). All Firestore-specific behavior (chunking, image extraction, debouncing) lives entirely in `firebase-store.js` behind that same `get`/`set` shape. When adding a new piece of persisted state, add its key to `SCALAR_KEYS` (single doc field) or `LIST_KEYS` (one Firestore doc per array item, keyed by `item.id`) in `firebase-store.js` — don't invent a new storage path in `main.js`.

**Why data is split across documents** — Firestore caps documents at 1 MiB. `cards`, `pairPosts`, and `archive` are arrays that could grow large, so each array item is stored as its own document under `site/main/<key>/<id>` instead of one big array field. Small scalar fields (`profile`, `siteName`, `homeIntro`, `homeBanner`, `archiveSeqCounter`) live together in the single `site/main` doc.

**Image/blob handling** — Images are still authored as data URLs in `main.js` (via `fileToDataUrl`, which now actually calls `SiteStore.compressImage` — resizes to a max dimension and re-encodes as JPEG/PNG under a target size). Before any save, `firebase-store.js` walks the value (including `data:` URLs embedded inside rich-text HTML fields) and pulls each one out into `site/main/blobs/<sha256>`, replacing it in place with a `blob://<hash>` reference; large blobs are split into `parts` sub-documents to stay under the size cap. On load, references are inflated back into real data URLs before `main.js` ever sees the data — the UI layer is unaware this happens. Same-hash images are automatically deduplicated. Unreferenced blobs are garbage-collected after the blob index arrives (only when logged in as admin, and only if there are no unsaved local changes — see `collectGarbage`).

**Blobs load lazily — `blob://` refs stay in the data.** This is the single most important thing about the storage layer. Images are ~99.9% of this site's payload (measured: 297 blobs / 302 docs / **122 MB** of base64, against **0.09 MB** for every post, card and folder combined). `loadAll()` used to fetch all of them, one chunk at a time, *before* the first render — first paint took 23–28 s. It now fetches only `site/main` + the four list collections (~0.2 s), sets `loaded`, and returns; `loadBlobIndex()` then pulls the small `{chunks,len}` index and downloads blobs in the background, **6 at a time** (measured 2.8× faster than serial) via a priority queue.

Consequences you must respect:
- **`inflate()` is no longer applied at load.** `cache` — and therefore `state` in `main.js` — holds `blob://<id>` strings, not data URLs. Anything that draws an image must go through `SiteStore.resolve()` (`imgUrl()` in `main.js`), which returns `''` for a blob that hasn't arrived.
- **Never write `''` into the data in place of a missing image.** `deflate()` passes `blob://` through untouched (it only rewrites `data:`), so a save round-trips byte-identically whether or not the blob has loaded — but an empty string would be saved as an empty string and the image would be gone forever. This is why `resolve()` is a read-time lookup and not a mutation.
- **Editors must `await SiteStore.ensure(value)` before filling.** `fillLogEditor()` and `openArcWriteModal()` do; they read the editor back out on save, so filling them with unresolved refs is exactly the data-loss case above. `ensure()` jumps the queue and resolves in well under a second for one post.
- Everything else paints optimistically and repairs itself: `whenImgArrives(value, el, redraw)` parks a redraw closure, and `SiteStore.onBlobs` → `flushPendingPaints()` runs it when the blob lands (dropping entries whose element left the DOM). **Repaint the element, never re-render the view** — a full re-render moves the caret while the user is typing. `applyThumbBg()` self-registers, so any caller of it is already covered; anything that sets `img.src` or `background-image` directly needs its own `whenImgArrives`.
- `SiteStore.prefetch(value)` pulls a value's blobs to the front. Detail modals and the lightbox call it; `whenImgArrives` calls it too, so whatever is being drawn is automatically prioritised. `boot()` re-prioritises HOME last, because `renderAll()` draws the hidden views too and each `prefetch` jumps the queue.
- `blobIdsIn()` and `inflate()` both short-circuit on `data:` strings — they run on every paint, and scanning a 400 KB data URL for refs each time is visible.
- `SiteStore.blobStats()` drives `initPhotoIndicator()` (bottom-left, mirrors the save indicator), which fades out once every blob has arrived.

Result: first paint **0.4 s** (was 23–28 s); all 297 images land in ~14 s in the background. The remaining cost is that Firestore documents aren't browser-cacheable, so every visit re-downloads 122 MB — fixing that means moving image bytes to Firebase Storage or a CDN, which needs a paid plan and is deliberately **not** done.

**Thumbnail rendering** — stored images are ~800–1800px, but most places display them at 60–430px. Drawing a 830px source into a 124px box makes Chrome downscale ~7x in one pass, which visibly aliases ("계단 현상"). `downscaleThumb`/`applyThumbBg` in `main.js` build a **display-only** variant by halving on a canvas until close to the target, cached per (source, 64px bucket); the target is `display width × devicePixelRatio × 1.25`, and sources that aren't at least 1.25x larger than that are left alone. `state` always keeps the original, so full-size views and the zoom/pan adjuster are unaffected. If thumbnails still look rough, fix the downscale path — **do not raise `compressImage`'s `maxDim`**, which only inflates storage and makes the ratio worse. Callers pass a fixed `boxPx` for fixed-size boxes and omit it to have the element measured (with a short retry, since hidden views report width 0). Note `requestAnimationFrame` never fires in a background tab, so this code deliberately uses `setTimeout` to wait for layout.

**Paged grids** — three views now share the same "one page fills the remaining height, page buttons pinned below" shape: Pair list, ARCHIVE PROMPT, and the pair-detail gallery. Their view roots (`#view-pair.active`, `#view-archive.active`) are `display:flex; flex-direction:column`, the body is `flex:1; min-height:0`, and the grid is `flex:1` with **explicit `grid-template-rows`**. The per-page count in JS must match rows × columns in CSS or the last row will be clipped: `PAIR_PER_PAGE`/PROMPT are `8` (4×2 desktop, 2×4 phone), OOC/ETC are 15/10 rows, gallery is `galleryPerPage()`. Short pages are padded with invisible `.post-slot` / `.gallery-slot` elements so the grid height never changes with item count.

**Gallery/LOG are shared engines** — the pair-detail gallery and log panes are also used by the OC detail modal, so those renderers do **not** look elements up by id. They read a *host* object — `PAIR_GALLERY_HOST` / `OC_GALLERY_HOST` / `PAIR_LOG_HOST` / `OC_LOG_HOST`, each `{root, getPost, save, horizontal}` — and resolve elements as `root.querySelector('.gallery-grid')` etc. via the `gq()` / `lq()` helpers. **If you add a control to one pane, give it a class and bind it inside `initGalleryRoot()` / `initLogRoot()`, not by id**, or the OC copy silently won't work. `galleryHost`/`logHost` are set when a detail modal opens (and re-set by any control's own handler, since only one modal is open at a time). Module-level gallery state (`galleryPage`, `gallerySelectMode`, …) is deliberately shared and reset on open. `host.horizontal` flips the page-change animation between `translateY` and `translateX`.

**OC** — a third content type between PAIR and ARCHIVE: `state.ocPosts` (a `LIST_KEYS` array) plus `state.ocCats` (see Sidebar sub-categories below), where **each category owns its own folder list** (`cat.folders`, same shape as PROMPT folders but blur is forced off and the folder modal hides that option via `ctx.hideBlur`). Folders used to be one flat list shared by every OC post regardless of category; `ocFolderCtx(catId)` / `renderOcFolderBar(catId)` / `ocFoldersOf(catId)` all take the category explicitly now, and `ocFolderIdOf(item)` resolves through `ocCatOf(item.type)` first — so switching categories in the sidebar shows a completely different folder bar. The legacy global list still lives at the (now write-only-never-again) `ocFolders` scalar key purely so `normalizeOcCats()` can absorb it into the first category on the one-time upgrade from "no categories" to "at least one" — don't repurpose that key for anything new. The list view reuses PAIR's paged grid (8/page) and PROMPT's folder-tab styling, scoped to the current category. The detail modal has **no index tabs** — `#ocPages` holds three absolutely-positioned `.oc-page`s (profile / gallery / log) that `setOcPage()` slides vertically with `translateY((i-current)*100%)`, driven by the wheel (600 ms lock so one flick moves one page) and a vertical swipe only — there are no click targets; `.oc-page-dots` sits *outside* the modal on the left and is display-only. **Its gallery pages horizontally** so that vertical scrolling stays free for the modal's own paging. `consumedByInnerScroll()` stops a page flip while a nested scroller (`.oc-free-box`, `.log-table-scroll`, or on phones the `.oc-page` itself) still has room to scroll.

**OC must stay dimensionally identical to PAIR.** `.oc-pages` is the counterpart of `.pd-tab-content` (both `580px`), and the `8px 4px 8px 0` inset that `.pd-tab-content` carries as *padding* lives on each `.oc-page` instead — the pages are `inset:0` and slide by `translateY(100%)`, so shrinking the container would leave the next page peeking. Two consequences to keep in mind when editing: `.oc-page-gallery .gallery-fab-row` needs `bottom:16px` (not 8px) because its containing block is the page's padding box, one level further out than PAIR's `.pd-tab-pane-gallery`; and the horizontal `《 》` hints sit at `top:17px / bottom:14px` rather than PAIR's `11px / 4px` because ︽ ︾ draw only 13px of ink inside their 26px box while 《 》 draw 25px — those four numbers are what make the two galleries line up pixel for pixel. On phones the hints go back to `4px` or they cover the first/last thumbnail row.

**Sidebar sub-categories (PAIR · OC)** — the `전체 / Ai chat / Dream` strip is no longer fixed markup. `state.pairCats` and `state.ocCats` are `SCALAR_KEYS` lists of `{id, name}`, and each post carries that id as `post.type`. `#pairSub` / `#ocSub` are empty in `index.html`; `renderNavSub(nav)` draws them, where `nav` is `PAIR_CAT_NAV` / `OC_CAT_NAV` — the same host-object pattern the gallery and theme songs use, so both sides run one implementation off the same code. **PAIR's two ids must stay `aichat` / `dream`**: existing posts point at them, and `normalizeCats()` only supplies those as the *fallback* when the key is absent.

**PAIR keeps `전체`, OC does not** — that's the one real behavioral fork between the two, driven by `nav.hasAll` / `nav.minCats`:
- **PAIR** (`hasAll:true, minCats:0`): `전체` is a render-only row, not in the list, so there's no "default" to fall back to. Deleting a category leaves its posts' `type` pointing at a dead id — they just show under `전체` (`catCtx().onDelete` deliberately does not clear `type`, so re-creating the same id restores them). `catName()` returns `''` for a dead id, which blanks the `.post-type` line on a card. Deletion has no floor; the last category can go.
- **OC** (`hasAll:false, minCats:1`): there is no `전체`, so a post with no valid category would simply never be visible anywhere — OC can't tolerate that. `normalizeOcCats()` guarantees at least one category always exists (seeding an id'd `기본` category on first-ever load if the list is empty), `loadState()` re-homes any post whose `type` doesn't match a real category to `state.ocCats[0]`, and `catCtx().canDelete` refuses once `cats().length <= minCats` (so the last one can't be deleted from the UI). Deleting a non-last OC category **reassigns its posts to the next remaining category** instead of leaving them dangling — the delete-warning text says so, and differs from PAIR's wording for exactly this reason. `defaultCatId(nav)` / `catTitle(nav, id)` centralize the `hasAll` branching so call sites don't special-case it themselves.

**Adding a category no longer opens a modal.** The `PAIR`/`OC` sidebar row now carries a small `＋` (`.nav-cat-add`, a sibling of `.nav-item` inside `.nav-item-row` — button-in-button isn't valid HTML) that calls `startAddCat(nav)`: switch to that section (`openNavSection`, factored out of `selectNavSub` since the plus icon needs the same view-switch without touching the currently-selected category) and set `nav.adding = true`, which makes `renderNavSub` render an inline `.ns-add-row` (input + ✓ + ✕) at the bottom of the list instead of nothing. Enter/✓ commits, Escape/✕ discards; there is no other create path. **Rename/delete still reuse `openFolderModal()`** via `catCtx(nav)` — that's why the modal's title, name label, placeholder, error text and delete button all read `ctx.label` (`'카테고리'`), and why `catCtx` no longer defines `newFolder`/`onCreate` (dead now that add doesn't go through the modal). The active highlight is painted on `.nav-item-row` itself (`.nav-item-row:has(.nav-item.active)`, with `.nav-item.active`'s own background made transparent inside a row) rather than on `.nav-item`, so it visually extends behind the `＋` too instead of stopping at the label's edge — this is the codebase's first use of `:has()`.

**Every entry point that changes the current PAIR/OC category must call `nav.title(catTitle(nav, id))`.** The topbar's "Pair · Dream" text is only ever set by that call — it is not derived from `currentPairFilter`/`currentOcFilter` at render time. Clicking a sub-category (`selectNavSub`) and deleting a category both call it, but the plain `PAIR`/`OC` sidebar row's own click handler resetting the filter back to `defaultCatId(nav)` originally didn't, so entering `OC` from the top-level menu could show whatever category name was last set — e.g. a stale `ARCH` — instead of the category it actually landed on. If you add another place that reassigns `currentPairFilter`/`currentOcFilter`, set the title in the same place.

Reorder is a `draggable` `.nav-sub-item` with a live FLIP (`flipByKey`); the `dragover` handler **moves the existing node with `insertBefore` instead of re-rendering** — re-rendering destroys the element being dragged, so `dragend` never fires and the new order is never saved. Same trap as the gallery's live reorder.

Two knock-on rules: the move buttons in the select bars are generated per category (`renderMoveBtns`), so `particleRo()` picks 로/으로 from the name's final jamo — don't hard-code the particle. `카테고리 없음으로` (move to no-category) is gated on `nav.hasAll` and only ever renders for PAIR, since OC has nowhere for a categoryless post to go. And `.nav-sub`'s `max-height` is a generous fixed value (560px / 70vh) because the transition needs one; a longer list is absorbed by the sidebar's own scroll.

**PROMPT folders** — `state.archiveFolders` (a `SCALAR_KEYS` entry) is a flat list of `{id, name, secret, pwHash, blur}`, and each PROMPT post carries a `folderId`. The add/edit modal is **shared with the pair gallery** — `openFolderModal(ctx, folder)` takes a context object (`galleryFolderCtx(post)` / `archiveFolderCtx()` / `ocFolderCtx(catId)`) supplying `getList/canDelete/deleteWarn/newFolder/onCreate/onDelete/save/rerender`. Two deliberate differences from the gallery: deleting a PROMPT/OC folder moves its posts to a remaining folder instead of deleting them, and PROMPT's blurred thumbnails are revealed by a per-post `👁` button (`arcUnblurred`, cleared on page/folder change) rather than by hover, because hover is already taken by the overlay+title. **`canDelete` is `list.length > 1` for every folder host, not "not the default folder"** — any folder (including the seeded `기본`/default one) can be deleted as long as one is left. `arcFolderIdOf()` / `ocFolderIdOf()` both resolve a post's `folderId` against **whatever folder is first in the current list**, not a hard-coded default id, precisely so this still works once the original default folder itself has been deleted; `normalize*Folders()` only seeds a `기본` folder when the list would otherwise be *empty* (first-ever load), not merely because that one id happens to be missing — the old version re-inserted it every load, which would have silently resurrected a folder the user just deleted.

Folder tabs carry **two** drag behaviours on the same element: dropping an item (image/post) onto a tab files it there, and dragging the tab itself reorders the folder list (`bindFolderTabReorder()`, shared by all three bars). They coexist because each handler bails unless *its own* marker is set — `draggedGalleryKey`/`draggedArcId`/`draggedOcId` for the item drop, `draggedFolderId` for the reorder. Keep that guard when adding anything else droppable here. The `normalize*Folders()` helpers only prepend the default folder when it is **missing**, so a reordered list survives a reload.

**Re-binding a shared element is how post data leaks between posts.** The detail modals are reused for every post, so any binder called from `fillOcDetail`/`fillPairDetail` must not `addEventListener` on the shared element — the old listener stays attached and its closure still points at the *previous* post, so editing post B writes B's markup into A. This actually shipped: `bindMetaContainer()` did it and two OC posts ended up with identical labels. It now binds once (`el._metaBound`) and every handler saves through `el._saveMeta`, which each call reassigns. `bindMeta`/`bindBodyText` are safe only because they assign `el.oninput`/`el.onblur` (properties replace, listeners accumulate) — keep that distinction in mind when adding a binder.

**OC profile page order** — keyword row → profile → quote → free-text toolbar → free-text box, with the right-hand column holding a two-page horizontal slider (vertical image / theme songs) driven by `makeSidePager()` via horizontal swipe, horizontal wheel, or the dots beneath it. The profile's label box (`.oc-label-box`) holds *only* `.meta-row` labels, capped at 7 by `data-max-rows` on its toolbar and never scrolls, so `.oc-info-main .pd-profile` is `min-height:192px` (the photo's 3:4 height) and grows with the labels; the photo is `align-self:start` so it doesn't stretch with it. `bindRichTextToolbars()` binds the command buttons and the `＋` row button **independently**, because this toolbar has no `data-target` body element.

**Side columns are shared pagers** — both detail modals put a `.side-pages` / `.side-page` / `.side-dots` slider in their right column, built by `makeSidePager(pagesEl, dotsEl)`: OC has [image · theme], PAIR has [image · TIMELINE · messages · theme]. The dots must live **inside** `.side-pages` — that's the only positioned ancestor, so a `.side-dots` placed as its sibling anchors to the modal instead. Theme songs are host-driven for the same reason the gallery is (`OC_THEME_HOST` / `PAIR_THEME_HOST` = `{root, getPost, save, idx}`, elements looked up by class inside `root`) — two copies exist in the DOM at once, so ids are not available.

**PAIR INFO is height-fixed** — the pane is a flex column, `.pd-info-grid` takes the remaining height, both profiles share it (`flex:1`), and `.pd-desc-box` absorbs the slack and scrolls internally, so the pane never scrolls. Two consequences: `.pd-info-main .pd-profile-img` has `aspect-ratio:auto` + `align-self:stretch` so the photo tracks the row height, and **the phone block must undo all of it** (`display:block`, `aspect-ratio:3/4` back, `max-height` on the desc box) or the images collapse to zero height.

**Messages** — `p.messages` is `[{id, side:'char'|'persona', text, images:[]}]`, one photo per bubble (the array is kept for the storage layer's sake: `deflate()` turns array data URLs into blob refs, whereas a data URL inline in `text` would only be caught if it were an `img src`). In **view mode a bubble with no text renders no `.msg-text` at all**, so a photo-only bubble hugs its image — don't "simplify" that back to a hidden or empty div. The photo button sits in `.msg-tools` above the bubble and appears only on `.msg-row.editing`; that element deliberately carries **no `data-editonly`**, because the global `body.logged-in [data-editonly]` rule outweighs the `.editing` selector and would pin it open.

**Horizontal wheel** — trackpads send `deltaX`, but a wheel mouse with Shift held sends `deltaY` in some browsers, so `wheelDeltaX(e)` accepts either. Anything it handles is stamped with `markOcHandled(e)` and the OC modal's own wheel listener bails on that flag — otherwise one Shift+wheel would flip both the side column (or gallery page) and the modal's page. Both galleries take horizontal wheel; only PAIR's takes vertical, because the OC modal needs vertical for its own paging.

**Unsaved-changes guard on write modals** — `guardUnsavedClose(overlayId, getSnapshot)` (near `openModal`/`closeModal`) is wired for `modalArcWrite` and `modalLogWrite`, the two modals with an explicit "게시"/"저장" button (as opposed to PAIR/OC detail, which autosave every field on blur and so have nothing to lose). It arms a baseline snapshot — `JSON.stringify([...current field values])` — via `overlay._armUnsavedGuard()`, called once at the end of `openArcWriteModal`/`fillLogEditor` (after any async content load completes, not before). It intercepts `.modal-close` (the ✕) and a click on the overlay background in the **capture** phase, ahead of the generic `[data-close]`/`.modal-overlay` handlers registered earlier in the file, and calls `stopPropagation()` only when the current snapshot differs from the baseline — otherwise it lets the click fall through to the ordinary close. On a real difference it opens `siteConfirm(...)` (the site-styled confirm, not `window.confirm`) and only closes if the user confirms. The "취소" button is deliberately **not** covered — it's `.btn-ghost`, not `.modal-close`, and clicking it already *is* the user's explicit "discard" decision, so re-confirming would be redundant.

**Sign-out must not wait on the save queue** — `SiteStore.signOut()` used to `await flushNow()` unconditionally. `flushNow()` returns the tail of `flushChain`, and a Firestore write that never gets acknowledged (offline, or the write stream backed up) leaves that promise pending **forever** — so the 로그아웃 button silently did nothing, permanently, for the rest of the session. It now races the flush against a 3s timeout and signs out regardless. Any binder that awaits a Firestore promise before doing something user-visible needs the same treatment.

**Theme songs** — `o.themeSongs` is `[{id, cover, title, artist, lyrics}]`. Clicking a row promotes it to the "NOW PLAYING" card and expands its lyrics (only the current row shows them — the column is too narrow to expand all). The site deliberately does **not** host audio and no longer stores a link either: an mp3 would be inlined into Firestore as a data URL by the blob extractor and make every load drag. If asked for real playback, raise that trade-off first.

**Gallery images can be added by dropping OS files, not just the `＋` button.** `initGalleryRoot()` binds `dragover`/`drop` on `.gallery-grid-wrap` guarded by `e.dataTransfer.types.includes('Files')`, so it only fires for an external file drag — the same element already has thumbnail-reorder and cross-page drag wired up via the internal `draggedGalleryKey` state, and those never carry `Files` in `dataTransfer.types`. Both the `＋` button and the drop handler funnel through the same `addGalleryFiles(fileList)` closure. The `dragover` handler must call `preventDefault()` (it's the only thing suppressing the browser's default "navigate to the dropped file" behavior); the `.gallery-file-dragover` class it toggles is purely a visual affordance and has no logic riding on it.

**Gallery move vs. reorder** — dropping a thumbnail on a folder tab and dropping it on another thumbnail are two different operations on the same drag. `drop` fires *before* `dragend`, but the tab handler `await`s its save, so when `dragend` runs the DOM still shows the old page while the arrays have already shrunk — the reorder path then wrote `undefined` into the source folder and left blank thumbnails. `galleryDropHandled` (set in the tab's `drop`, cleared in `dragstart`) makes `dragend` stand down, and the reorder additionally refuses to write unless every entry is a string. `migrateGalleryFolders()` strips any blanks already saved by the old bug.

**Font-size stepping** — the OC free-text toolbar (`.rt-toolbar-ocfree`, bound in `initOcFreeToolbar()`) has ˄/˅ buttons that change the selection by 1px. `execCommand('fontSize')` only accepts steps 1–7, so `stepFontSize()` runs it with `7` purely to make Chrome split the range, then rewrites each `font[size="7"]` into a `<span style="font-size:…">`. **The base size must be measured before calling `execCommand`** (`selectionFontSize()`) — Chrome *replaces* an existing sized span with the `<font>` element, so reading the size afterwards always returns the box's default and every click past the first would be a no-op. Any nested `font-size` inside the new span is stripped so repeated clicks don't compound.

**Profile subtitle** — `.pd-sub-input` is the small grey line under each name (PAIR's character and persona, OC's profile). It is deliberately `display:block`: an `input` is inline-block by default, so in PAIR's block-flow profile column it would sit in an anonymous line box and pick up ~4px of leading above it, making the gap 29px instead of 25px. The 25px name-to-subtitle spacing is bought back from `.pd-profile-info .pd-meta-row{margin-bottom:2px}` (was 8) and `padding-bottom:0` on the name input (was 4) — that reclaims 10px against the subtitle's 11px, which is why adding it grew the profile row by only 1px. The `body.logged-in` variant of the padding rule is required because `body.logged-in .pd-input` rewrites the whole `padding` shorthand.

**Pinning** — ARCHIVE and LOG (both PAIR's and OC's, via the shared engine) each cap pins at 3 and sort pinned items to the front at render time; nothing about the stored order changes, an entry just carries `pinned:true`. The visible `No` column is therefore **not** the row's position — it comes from a `Map` of registration order (`displayNo`), so pinning or searching never renumbers an existing post. The limit is per list: three per ARCHIVE category-set and three per post's `log`.

**Post body transforms** — saved post HTML is decorated at *render* time, never at save time, so the stored content stays plain editor output. `decorateContent(el)` runs `applyCodeFences()` (turns ` ``` `-fenced runs into `.code-block` with a copy button) and `ensureCodeEmbedCopy()` (back-fills a copy button into `.code-embed` toolbars saved before that button existed). `applyAutoFormat()` skips anything inside `.code-block`.

**Fold blocks** (`.fold-block`, Notion-toggle style) are real saved markup; a delegated click toggles `.open` — the whole `.fold-head` is clickable when reading, but **only the `.fold-arrow`** while editing, so clicking the title still places the caret. `.fold-title`/`.fold-body` hold no placeholder text — they're genuinely empty and rely on `body.logged-in .fold-title:empty:before` / `.fold-body:empty:before` (same trick as `.oc-free:empty:before`) for the "타이틀"/"내용을 입력하세요" hint, so there's nothing to select-and-delete before typing. All three editors that offer a fold button (ARCHIVE, PAIR_LOG, OC free text) insert them through the shared `insertFoldBlock(editorId)`, and save through `editorHtml(editorId)`, which strips `.open`, so a post always opens collapsed no matter how the author left the editor.

**Collapsing hides every direct child of `.fold-block` except `.fold-head`** (`.fold-block:not(.open) > *:not(.fold-head){display:none}`), not specifically `.fold-body`. This is deliberate defense-in-depth: some already-saved posts have a fold with **multiple sibling `.fold-body` divs** inside one `.fold-block` (see the `initFoldEnter` note below for how that happened), and `applyCodeFences` itself can legitimately leave a `.code-block` as a direct sibling of `.fold-head` rather than nested one level down inside `.fold-body` (when the fenced lines were the *only* content of their line-container — see the `fenceLineBoundary` note). Targeting `.fold-body` specifically would miss both of these and leave content visible after collapsing.

`insertFoldBlock` builds the block with `document.createElement` and places it via `Range.insertNode()` at the current selection **instead of** `execCommand('insertHTML')` — critically, this means it inserts wherever the caret actually is, including inside another fold's `.fold-body`, which is what makes folds-inside-folds work with zero extra code. The same reasoning applies to `insertBlockquote(editorId)` (shared by ARCHIVE and OC free text): `execCommand('formatBlock', false, 'blockquote')` converts the *nearest block ancestor*, which inside a fold is `.fold-body` itself — it doesn't turn the quoted line into a blockquote, it wraps the whole fold body in one (`<blockquote><div class="fold-body">…`), corrupting the fold. `insertBlockquote` sidesteps this the same way `insertFoldBlock` does: build the `<blockquote>` and `Range.insertNode()` it (wrapping the current selection if non-collapsed, otherwise inserting empty with a `<br>` to type into).

**Anything inserted through a modal or native file picker must save and restore the caret Range explicitly**, or it silently escapes an enclosing fold. `arcInsertCodeBtn` (opens `#modalArcCode`) and `arcInsertImageBtn` (opens a native `<input type=file>`) both call `editor.focus()` right before their `execCommand('insertHTML', …)` — but focusing an already-focused editor does **not** restore whatever selection existed before the modal/file-dialog stole focus, so without help the browser drops the caret back at its own default position (observed: escaping any enclosing fold entirely). Both now capture `window.getSelection().getRangeAt(0).cloneRange()` the moment the button is first clicked (before focus moves anywhere) and re-`sel.addRange()` it right before the `insertHTML` call.

**Fold Enter** is handled by `initFoldEnter(editorId)` (wired for all three editors alongside their fold button), which covers **two** carets, not one:

- **`.fold-title`**: pressing Enter always inserts a single `<br>` and never touches `execCommand`. If the fold is **collapsed**, the `<br>` goes immediately after the `.fold-block` in *its own* parent — which is either the top-level editor or, for a nested fold, the outer fold's `.fold-body` — so the cursor "exits" exactly one level up. If the fold is **open**, the `<br>` goes at the very start of `.fold-body` instead, so Enter drops the cursor straight into the content without leaving the fold. Both branches are one `insertBefore` call; nesting depth never needs special-casing because the block's own `parentNode` is always the correct target.
- **`.fold-body`**: this branch exists because leaving Enter here to the browser default is actively destructive. Chrome splits a block on Enter by cloning its own class onto a new sibling — so typing multiple lines inside `.fold-body` produced **several sibling `<div class="fold-body">` elements** instead of one `.fold-body` with internal `<br>`s. (This is why the collapse-hiding rule above targets "every child but the head," and why some already-saved posts have this exact shape.) The fix intercepts Enter here too and inserts a plain `<br>` in place, so multi-line fold content always stays inside the one `.fold-body` it started in.

Both branches route the resulting cursor placement through **`placeCursorAfterBr(sel, br)`**, not a bare `range.setStartAfter(br)`. This exists because of a real Chrome quirk: if the freshly-inserted `<br>` ends up as the *last* node in its container, positioning the collapsed selection immediately after it is not reliable — `execCommand('insertText')` (and real typing) can insert the next character *before* the `<br>` instead of after it, even though the Range itself was provably at the correct DOM boundary. `placeCursorAfterBr` works around this by guaranteeing the `<br>` is never trailing: if there's nothing after it (or only an empty text node), it inserts a filler `<br>` right after and points the selection **before that filler** instead — "before a following node" is the position browsers handle predictably; "after the last node in a container" is not. Watch for this same failure mode in any *new* Enter-key handling added to a contenteditable region — it doesn't reproduce under `dispatchEvent`-only synthetic testing without actually typing more text afterward, so verify with a real follow-up character, not just `evt.defaultPrevented`.

**Blockquote Enter** (ARCHIVE and OC free text, via a shared `keydown` listener) intercepts plain Enter — not Shift+Enter, which keeps the browser's default in-place `<br>` — while the caret is inside a `<blockquote>`: it `extractContents()`s anything after the caret into a new sibling `<div>` and moves the caret there, so writing continues as a normal paragraph instead of the browser's default of minting a second, nested blockquote.

**Code-fence parsing (`applyCodeFences`) works on flattened text, not top-level DOM children.** An earlier version grouped only the element's *direct* children into "lines" (`<br>` or a top-level block tag as the separator), on the assumption that contenteditable always puts each visual line at the top level. It doesn't — the line right after inserting an `<img>` or `<hr>` often lands as a bare text node merged with the previous inline content (no `<br>` at all), which silently deleted that content and could desync which `` ``` `` paired with which, dropping or corrupting later code blocks in a post with several. `flattenForFences(root)` instead does a full recursive walk, building one plain-text string (with `\n` inserted for every `<br>` and — de-duplicated, so adjacent block tags don't produce a blank line — every block-tag boundary at any nesting depth) plus a parallel `marks` array of `{pos, container, offset}`, always recorded even when the `\n` itself is deduped away, so a position where several nesting levels' boundaries coincide still resolves to a specific (and specifically the most-recently-recorded) DOM point. `applyCodeFences()` finds all `` ``` `` occurrences globally and pairs them in document order `(1,2)(3,4)…` (an unpaired trailing fence is left untouched). Pairs are walked **back to front** so an earlier deletion never shifts a later mark's coordinates.

**Finding *which* DOM range to delete for a fence pair needs two passes, not one.** `resolveFenceOffset()` turns `openPos`/`closePos` (positions in the flattened string) back into an exact `(textNode, offset)` — that part is unambiguous, since fence characters always live in one specific text run. But the *deletable range* isn't "from one resolved point to the other": `fenceLineBoundary(root, point, after)` walks up from that text node to the nearest enclosing block-tag element (e.g. `.fold-body`), because coordinate math alone can't disambiguate nested closing boundaries that land on the same character position (opening boundaries nest inward so last-recorded/innermost naturally wins a tie; closing boundaries cascade outward, so the same rule picks the **outermost** one — exactly backwards for staying inside a fold). It returns `null` when there's no wrapping block at all (bare text merged directly into the editor root), and only then does the coordinate-based `resolveFenceOffset` fallback apply.

Finding the enclosing block is still not the whole answer, though — **that block can itself hold more than one line.** If a fold's content was typed as `<br>`-separated lines directly inside one `.fold-body` (rather than one nested `<div>` per line), naively deleting "all of `.fold-body`" to remove just the fenced lines would take the surrounding lines with it — real content loss, not just a fold-nesting cosmetic issue. `localLineBoundary(el, node, dir)` handles both shapes with one rule: walk `node`'s siblings within `el` looking for a `<br>` in direction `dir`; if found, the boundary is *inside* `el`, right at that `<br>` (correctly scoping to just this line among several). If no `<br>` turns up before running out of siblings, that means `el` itself holds nothing but this one line (the one-`<div>`-per-line shape), so the boundary is `el`'s **own** position within *its* parent — which is what makes `el` (the whole line-`<div>`) the unit that gets replaced, matching the earlier-established nested-fold behavior. This is also why the collapse-hiding CSS rule (above) can't assume the resulting `.code-block` always ends up wrapped in a `.fold-body` — the `<br>`-lines case leaves it as a direct sibling of `.fold-head` instead, by design.

If two pairs' line-ranges would overlap (only possible if a closing fence and the next block's opening fence somehow land on the exact same line, which normal typing doesn't produce), the earlier one is left as plain text rather than risking a corrupt range — same "if unsure, don't touch it" fallback as an unpaired fence.

**ARCHIVE write modal (`#modalArcWrite`) fills available height with flexbox** (`display:flex;flex-direction:column`, plus `.arc-editor{flex:1 1 auto;min-height:160px;max-height:none}`) instead of giving the editor a fixed `max-height`. A fixed px cap (previously 320px, copied from `.log-editor`) meant a post with a large image made only the editor scroll internally (correct, per the "ARCHIVE 글쓰기 모달 스크롤" requirement) but left the *edit* modal much shorter overall than the *view* modal — since only `.arc-editor` was capped, not the modal around it. With flex, `.arc-editor` absorbs whatever room the fixed-size chrome (title, category, toolbar, attachments, buttons) doesn't need, up to the inherited `88vh`, so a large-image post's edit modal now reaches the same height as its view modal, and a short/blank post's modal still sizes naturally to its content (flex-grow has nothing to distribute when total content is already under `88vh`) rather than stretching into a mostly-empty box.

**That flex rule must stay scoped to `#modalArcWrite`** (`#modalArcWrite .modal.wide.arc-modal{…}`) — **`#modalArcView` reuses the very same `.modal wide arc-modal` class list**, so an unscoped `.modal.wide.arc-modal{display:flex}` silently reformats the read-only view modal too: `.arc-view-content` becomes a flex item, gets shrunk instead of laying out at full height, and the modal's own `overflow-y:auto` stops being what scrolls. The two modals are meant to scroll differently — **view scrolls as one window** (plain `.modal` block layout, the default), **edit scrolls inside the body box only** (flex, so the surrounding chrome stays pinned while typing). Verify both when touching `.arc-modal`: view should report `display:block` with `modal.scrollHeight > modal.clientHeight`, edit should report `display:flex` with the modal *not* scrolling and `#arcContentEditor` scrolling instead.

**Header bars** — `.topbar` (PAIR/ARCHIVE) and `.cards-topbar` (LOVE INTEREST) are pinned to a fixed `height:60px`, not padding-driven. That number is the edit-mode height (14+14 padding + a 31px button + 1px border); without it the bar collapsed to 44px in view mode and the LOVE INTEREST bar sat at 50px, so the title line jumped when switching views or logging in. **`.li-icon`'s explicit `width` must equal that height minus the 1px border** (59px) — Safari can't derive an `aspect-ratio` width from a stretched height, so the square is hard-coded. On phones the padding drops to 9px so the 40px touch-target buttons still fit inside the same 60px.

**Responsive layout** — the site was desktop-only until responsive support was added; all of it lives in `@media` blocks at the **end of `css/style.css`**, plus a handful of existing `:hover` rules wrapped in `@media (hover:hover)` inline. Two breakpoints: `769–1100px` (tablet — releases the 16:9 letterbox, keeps the sidebar) and `≤768px` (phone). **Nothing applies above 1100px, so the PC design is untouched** — when changing layout, verify at 1920×1080 that `.pd-tab-content` is still `580px`, `.pd-info-grid` `margin-top:10px`, and the pd-modal `720px` wide with the index tabs to its left.

Phone-specific structure worth knowing before editing:
- `.app-window` flips to `flex-direction:column`, which turns the left/right punch-hole margins into top/bottom strips with no markup change. Height is `100vh` then `100dvh` (the second line is the iOS address-bar fix; keep both).
- The sidebar becomes a fixed off-canvas drawer toggled by `#mobileMenuBtn`. z-index order is deliberate: ☰ `56` > backdrop `55`, both < drawer `60` < `.modal-overlay` `100`, so the drawer never covers a modal and the ☰ never covers the drawer.
- The `.pd-index-tabs` (INFO/GALLERY/LOG) can't stay at `right:100%` on a phone, so `.pd-modal-wrap` becomes a column and they render as a horizontal strip **below** the modal. On tablet they stay on the left, which is why `.pd-modal` there is `min(720px, calc(100vw - 168px))` — the tabs are drawn outside a centered modal, so the modal must be narrower than `viewport - 2 × tab width` or they slide off-screen.
- **`galleryPerPage()` in `main.js` must stay in sync with `.gallery-grid`'s column count in CSS**: 15 (5 cols) desktop, 9 (3 cols) phone, 6 on phones under 720px tall. Row count is implicit, so only the JS number changes between the last two. `initResponsiveWatch()` re-renders on breakpoint change.

**Touch input** — HTML5 drag-and-drop does not fire on touch at all, and four features depend on it (card order, profile meta rows, gallery thumbnails, folder-tab drops). Rather than rewrite them, `initTouchDrag()` in `main.js` is one delegated `pointerdown` listener that long-presses (400 ms) any `[draggable="true"]` element and then **dispatches `MouseEvent`s named `dragstart`/`dragover`/`dragleave`/`drop`/`dragend`** at the right targets. The existing handlers are plain listeners, so they run unchanged — including the gallery's dwell-on-arrow page flip. If you add a new drag site, just set `draggable="true"` and it works; don't add touch code. Elements inside `[contenteditable="true"]` are skipped so iOS text selection still works. Wheel-only interactions (Home page flip, gallery paging) got touch equivalents too: swipe handlers plus tappable `︽`/`︾` arrows (`pointer-events` is opened up on phones only — their tap padding is horizontal-only so it can't cover the first thumbnail row).

**Write batching** — `main.js` calls `storageSet` very frequently (e.g. on every `input` blur). `firebase-store.js` debounces actual Firestore writes (~1.2s), diffs against the last-saved JSON per document so unchanged items aren't rewritten, and only marks a change as "saved" after the write actually succeeds (a failed write keeps the key `dirty` and retries automatically) — this was a deliberate fix for a bug where failures were recorded as successes and silently dropped edits.

**Save-state visibility** — `SiteStore.onSaveState(cb)` fires `'saving' | 'saved' | 'error'`; `main.js` renders this as a fixed indicator (bottom-right) via `initSaveIndicator()`. Don't reintroduce silent failure here — if you touch the flush/retry logic in `firebase-store.js`, make sure errors still propagate to this indicator rather than only `console.error`.

**Auth model** — Firebase Authentication (email/password), not the old hardcoded `CREDENTIALS` object (removed). `window.SiteStore.isAdmin` is true only when the signed-in user's UID matches `ADMIN_UID` from `firebase-config.js`; the client-side check is a convenience, the Firestore security rules in `firestore.rules` are the actual enforcement point. `js/main.js`'s login modal collects an email (not a username) — see `loginErrorMessage()` for the mapping from Firebase auth error codes to Korean UI messages if you need to add a new one (e.g. new failure codes from console changes like unauthorized domain).

**GitHub Pages deployment** — this repo must be named exactly `xngsuii.github.io` to serve from the domain root (user site, not project site); renaming it changes the site URL, and Firebase's authorized-domains list (console → Authentication → Settings) must contain whatever domain the site is actually served from or login will fail with `auth/unauthorized-domain`.

## Terminology

The user may refer to the two UI states by their badge labels:
- **LOCKED** = 보기 모드 (view mode) — visitor state, nothing editable
- **UNLOCKED** = 편집 모드 (edit mode) — admin signed in, `body.logged-in` is set and `[data-editonly]` controls appear

## Cache busting

`index.html` references its assets with a version query — `css/style.css?v=N`, `js/main.js?v=N`, `js/firebase-store.js?v=N` (and `firebase-store.js` imports `./firebase-config.js?v=N`). **Bump every one of those `N`s together whenever you change a CSS or JS file.** GitHub Pages serves the HTML with a short cache but assets with a long one, so without a bump a returning visitor gets new HTML with stale JS — and since `main.js` wires up elements at top level, a mismatch used to kill the whole script. The top-level init blocks now bail out politely when their elements are missing, but that only degrades gracefully; it does not make the page correct. The version bump is the actual fix.

## Workflow notes

- **Do not commit without testing first, and confirm with the user before committing.** Since there's no automated test suite, "testing" means actually loading the page (local server or the live site) and exercising the change in a browser — check the console for errors and confirm the save indicator behaves correctly for anything touching storage.
- **When a change touches color** (CSS colors, inline styles, color pickers, theme variables in `:root`), always print the affected HTML color codes (hex/rgba) in the response, not just describe the color.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A single-page personal "home" site (Korean: 갠홈) — a static HTML/CSS/JS app with no build step, deployed via GitHub Pages at `https://xngsuii.github.io/`. Data (profile, cards, pair posts, archive, images) lives in Firestore instead of localStorage, so edits persist across reloads, browsers, and devices; only the admin account (Firebase Authentication) can write.

There is no package.json, no bundler, and no test runner — the site is plain files served as-is.

## Commands

There is no build/lint/test tooling in this repo. To preview locally:

```
py -m http.server 8790
```

then open `http://localhost:8790/`. Serve over HTTP (not `file://`) — the app loads `js/firebase-store.js` as an ES module and needs a real origin for Firebase Auth persistence and CORS.

There are no automated tests. Verify changes by loading the page in a browser and checking the browser console for errors — do this before committing (see Workflow notes below).

## Architecture

**File layout** — everything is hand-split from what used to be one monolithic HTML file:
- `index.html` — markup only
- `css/style.css` — all styles
- `js/main.js` — UI logic and rendering (view switching, cards, pair posts, archive, image adjuster widget, rich-text editing)
- `js/firebase-store.js` — the persistence layer (see below)
- `js/firebase-config.js` — Firebase project config + `ADMIN_UID` (safe to be public; not a secret — see Security model)
- `firestore.rules` — Firestore security rules (read: public, write: admin UID only); must be pasted into the Firebase console manually, this repo file is not auto-deployed

**Storage adapter contract** — `main.js` never talks to Firestore directly. It only calls `storageGet(key, fallback)` / `storageSet(key, value)` (defined in `main.js`, thin wrappers around `window.SiteStore`). All Firestore-specific behavior (chunking, image extraction, debouncing) lives entirely in `firebase-store.js` behind that same `get`/`set` shape. When adding a new piece of persisted state, add its key to `SCALAR_KEYS` (single doc field) or `LIST_KEYS` (one Firestore doc per array item, keyed by `item.id`) in `firebase-store.js` — don't invent a new storage path in `main.js`.

**Why data is split across documents** — Firestore caps documents at 1 MiB. `cards`, `pairPosts`, and `archive` are arrays that could grow large, so each array item is stored as its own document under `site/main/<key>/<id>` instead of one big array field. Small scalar fields (`profile`, `siteName`, `homeIntro`, `homeBanner`, `archiveSeqCounter`) live together in the single `site/main` doc.

**Image/blob handling** — Images are still authored as data URLs in `main.js` (via `fileToDataUrl`, which now actually calls `SiteStore.compressImage` — resizes to a max dimension and re-encodes as JPEG/PNG under a target size). Before any save, `firebase-store.js` walks the value (including `data:` URLs embedded inside rich-text HTML fields) and pulls each one out into `site/main/blobs/<sha256>`, replacing it in place with a `blob://<hash>` reference; large blobs are split into `parts` sub-documents to stay under the size cap. On load, references are inflated back into real data URLs before `main.js` ever sees the data — the UI layer is unaware this happens. Same-hash images are automatically deduplicated. Unreferenced blobs are garbage-collected after the blob index arrives (only when logged in as admin, and only if there are no unsaved local changes — see `collectGarbage`). GC decides what to delete by scanning `savedJson` for `blob://` refs and removing everything in `knownBlobIds` that isn't there; the blob index only supplies the *candidate* list, so an incomplete index makes it delete **less**, never more. Do not invert that.

**Blobs load lazily — `blob://` refs stay in the data.** This is the single most important thing about the storage layer. Images are ~99.9% of this site's payload (measured: 984 blobs / 1000 chunks, against **0.09 MB** for every post, card and folder combined). `loadAll()` used to fetch all of them, one chunk at a time, *before* the first render — first paint took 23–28 s. It now fetches only `site/main` + the four list collections (~0.2 s), sets `loaded`, and returns; blobs are fetched **on demand**, 6 at a time (measured 2.8× faster than serial) via a priority queue.

**Read quota is the binding constraint, and every Firestore document is one read.** The Spark plan allows 50,000 reads/day; exceeding it suspends the project until midnight Pacific (16:00 KST). Two things used to blow it:
- `loadBlobIndex()` did `getDocs(blobs)` to learn each blob's chunk count — **one read per photo**, 984 of them on every single page load.
- After the first paint it queued *every* blob (`blobQueue = [...first, ...rest]`), so opening HOME downloaded the whole gallery — another ~1000 reads and several hundred MB.

Together ≈ **2,080 reads per visit**; twenty-four page loads exhausted the day. The three fixes, in order of size:
1. **Only fetch what was asked for.** `startBlobQueue()` seeds the queue from `blobWanted` alone. Everything drawn already registers demand through `whenImgArrives`/`applyThumbBg`, so nothing needs a manual prefetch to appear — if you add a render path that sets `img.src`/`background-image` from `imgUrl()` and *doesn't* register, that image now stays blank forever instead of arriving eventually. `.an-img` in the ARCHIVE grid was exactly that case and had to be fixed.
2. **The chunk table rides along on `site/main`.** `meta.blobIndex` is `{blobId: chunkCount}` (36 KB for 984 photos; the 1 MiB doc cap is ~25,000 photos away), so it costs **zero** extra reads — `loadAll()` has already fetched that document. `writeBlob()` returns its chunk count and `flush()` merges the new entries in one `setDoc(..., {merge:true})`; nested-map merge means other photos' entries are untouched. `collectGarbage()` removes entries with `deleteField()` **per id it actually deleted** — never rewrite the whole map, or a photo uploaded from another device disappears from the table.
3. **Photos are cached in IndexedDB** (`siteBlobs`, stores `blobs`/`stat`, 350 MB budget, oldest-first eviction). A blob id *is* the SHA-256 of its content, so a cached entry can never be stale — no expiry, no revalidation. Second and later visits fetch **no** photo documents at all.

**The blob index is an optimisation, never a source of truth.** `readBlob(id)` falls back to `getDoc(blobs/<id>)` for its chunk count when the id isn't in the table, so a missing, stale or half-written index costs an extra read per photo and nothing else. Keep it that way — the older code filtered unknown ids out of `wantBlobs()`, which meant any drift silently made photos un-loadable. `ensureBlobIndex()` builds the table from a full collection scan exactly once, admin-only, and only when `meta.blobIndex` is absent.

Result per visit: **~2,080 reads → ~126 first visit, ~96 on return** (the ~96 is one meta doc plus one per post/card — see "list order" below if you want that lower too).

Consequences you must respect:
- **`inflate()` is no longer applied at load.** `cache` — and therefore `state` in `main.js` — holds `blob://<id>` strings, not data URLs. Anything that draws an image must go through `SiteStore.resolve()` (`imgUrl()` in `main.js`), which returns `''` for a blob that hasn't arrived.
- **Never write `''` into the data in place of a missing image.** `deflate()` passes `blob://` through untouched (it only rewrites `data:`), so a save round-trips byte-identically whether or not the blob has loaded — but an empty string would be saved as an empty string and the image would be gone forever. This is why `resolve()` is a read-time lookup and not a mutation.
- **Editors must `await SiteStore.ensure(value)` before filling, and honour its answer.** `fillLogEditor()` and `openArcWriteModal()` do; they read the editor back out on save, so filling them with unresolved refs is exactly the data-loss case above. `ensure()` jumps the queue and resolves in well under a second for one post, but it **returns `false` on timeout** — both call sites then close the modal and say so rather than opening an editor over blank images. Do not "simplify" that back to an unchecked `await`.
- Everything else paints optimistically and repairs itself: `whenImgArrives(value, el, redraw)` parks a redraw closure, and `SiteStore.onBlobs` → `flushPendingPaints()` runs it when the blob lands (dropping entries whose element left the DOM). **Repaint the element, never re-render the view** — a full re-render moves the caret while the user is typing. `applyThumbBg()` self-registers, so any caller of it is already covered; anything that sets `img.src` or `background-image` directly needs its own `whenImgArrives`.
- **`SiteStore.prefetch(value)` now downloads, it no longer merely reorders.** While every blob was being fetched anyway, passing a whole post to it was free — it just moved things up the queue. Now it *is* the fetch, so scope every call to what is actually on screen. `openPairDetail`/`openOcDetail` use `prefetchDetailImgs()`, which strips `galleryFolders`/`gallery`: passing the raw post pulled 138 photos for one character (measured 167 in flight) where 12 were visible. The lightbox uses `prefetchLbWindow()` (2 back / 5 ahead, re-run on every paint) instead of the whole folder — 63 photos down to a handful. The grid page, the thumb strip and the pop-out all self-scope already.
- `blobIdsIn()` and `inflate()` both short-circuit on `data:` strings — they run on every paint, and scanning a 400 KB data URL for refs each time is visible.
- `SiteStore.blobStats()` drives `initPhotoIndicator()` (bottom-left, mirrors the save indicator). `total` is now **outstanding demand** (`loaded + queued + in-flight`), not the site's photo count — with on-demand loading there is no meaningful "all photos" figure. The indicator therefore hides and re-appears repeatedly as you browse, so its fade-out timer must be **cancelled** when new work arrives; leaving it latched pinned the indicator open forever after the second burst.
- A blob that fails is retried twice then dropped (`BLOB_TRIES`), because the old unconditional 4-second retry loop would hammer a missing document forever and burn quota with nobody watching. Any *fresh* demand through `wantBlobs()` clears the failure count, so a user action always gets a full set of retries.

Result: first paint **0.4 s** (was 23–28 s), and a visit costs ~126 reads / a few MB instead of ~2,080 reads / hundreds of MB. Moving image bytes to Firebase Storage or a CDN would be better still, but needs a paid plan and is deliberately **not** done.

**Thumbnail rendering** — stored images are ~800–1800px, but most places display them at 60–430px. Drawing a 830px source into a 124px box makes Chrome downscale ~7x in one pass, which visibly aliases ("계단 현상"). `downscaleThumb`/`applyThumbBg` in `main.js` build a **display-only** variant by halving on a canvas until close to the target, cached per (source, 64px bucket); the target is `display width × devicePixelRatio × 1.25`, and sources that aren't at least 1.25x larger than that are left alone. `state` always keeps the original, so full-size views and the zoom/pan adjuster are unaffected. If thumbnails still look rough, fix the downscale path — **do not raise `compressImage`'s `maxDim`**, which only inflates storage and makes the ratio worse. Callers pass a fixed `boxPx` for fixed-size boxes and omit it to have the element measured (with a short retry, since hidden views report width 0). Note `requestAnimationFrame` never fires in a background tab, so this code deliberately uses `setTimeout` to wait for layout.

**Typefaces are assigned per place, by hand.** There are four, and `--pixel` is gone as a concept (it survives only as an alias for `--font-gm` so nothing breaks): `--mono` KoPub 돋움 (body), `--font-gm` G마켓 산스, `--font-free` 프리젠테이션/Freesentation, `--font-chosun` 조선일보명조. An earlier version tried to be clever — Latin from Gmarket, Hangul from Freesentation, split with `unicode-range` — and it was reverted because the owner wants to pick each slot herself. **Don't reintroduce automatic script splitting.** Current map:

**Anything new defaults to KoPub 돋움 (`--mono`).** This is an explicit standing instruction from the owner, given after noticing that new windows and controls were arriving with G마켓 산스 / 프리젠테이션 / KoPub mixed together at the author's discretion. When you add a feature, a modal, or a control, put **every** string in it on `--mono` and say so in the hand-off; she will look at it and name the exceptions herself. Do **not** pick a display face because it seems to suit the slot — the table above is the record of choices she made, not a pattern to extrapolate from.

Only weights that actually exist are declared (Gmarket 500/700, Freesentation 400/700/800); asking for an undeclared weight makes the browser thicken strokes itself, and faked bold on Hangul fills in the counters. `--name-font` (OC/PAIR profile names) is Freesentation and its one call site pins `font-weight:800`, so it keeps the ExtraBold cut it always had — the 800 file stays `unloaded` until a profile name is on screen.

**Sidebar emphasis is text-only, which has three non-obvious costs.** Hover/current state is `color:var(--accent)` plus a thickening with **no background box**, so (a) the resting weight is 500 — starting at 700 leaves nowhere to go and reads as a colour change only — and (b) `.nav-item`/`.nav-sub-item` carry a **fixed `height`+`line-height`** (32 / 25, `.nav`'s gap 1px), because bold text is a hair taller and without it every hover nudged the items below by a pixel. Row spacing is therefore changed by moving those heights, not by padding — the phone block's vertical padding had to be dropped to `0` when they came down from 34/28, because 13px of padding on a 25px box makes the box 26px and the two menu levels stop lining up. The "you are here" bold on a sub-category is scoped by `body[data-view=…]` (set by `markCurrentView()`), not by `.active` alone: each menu keeps its own `.active` child, so styling `.active` directly left PAIR's last-picked category bold while you were looking at OC.

And (c) **the thickening is `-webkit-text-stroke-width`, not `font-weight`, because the owner asked for it to animate.** `font-weight` is technically animatable, but G마켓 산스 ships only 500 and 700 and is not a variable font, so CSS font-matching snaps anything above 500 straight to the 700 face — the transition is invisible and the change lands as a single frame. The resting weight therefore stays 500 everywhere and hover/active grow the stroke `0 → .55px` over `.3s`; `-webkit-text-stroke-color` defaults to `currentcolor`, so the colour transition carries it for free. `.45px` matched the 500/700 stem difference at 11–12px on paper but read as too faint, so the shipped value is `.55px` (`.275` per side) — **re-derive it if the sidebar font size or family changes**, and check Hangul counters at the new value, since this is exactly the faked bold that fills them in at larger sizes. All four selectors must be changed together (`.nav-item`, `.nav-item-row:hover .nav-item`, `.nav-sub-item:hover`, and the three `body[data-view=…] … .active` rules); leaving `font-weight:700` on any one of them makes that item jump while its neighbours fade.

**LOG is a masonry card grid, and its geometry comes from JS.** `renderLogList()` draws 10 cards (`LOG_PER_PAGE`) into `.log-cards`, and `layoutLogCards()` absolutely positions each one into whichever of three columns is currently shortest. CSS `column-count` was rejected on purpose: it reads top-to-bottom within a column, so the newest post would not sit top-left and the second-newest would land under it rather than beside it. Consequences worth knowing:
- **A card in a hidden pane measures 0 and cannot be laid out.** LOG lives behind a tab in both hosts, so it is *usually* hidden when first drawn. A short retry loop used to cover this and would simply give up if the user opened the tab later — leaving every card stretched to full width. There are now two paths: a `ResizeObserver` on `.log-list` (survives re-renders, and its own height is pinned by the parent so writing the grid height back doesn't re-trigger it), **and** an explicit `relayoutLogCards()` from the PAIR tab click and `setOcPage()`. Keep both — a background tab renders no frames, so the observer never fires there.
- **Never set `img.src` to the empty string.** A post's first image replaces the preview text, but the blob may not have arrived, and `imgUrl()` returns `''` for that. Assigning it fires `error` immediately, which collapsed the thumbnail before the photo could land. `draw()` now assigns only a non-empty URL and `whenImgArrives` fills it in later; `error` genuinely means a broken image.
- **The grid keeps a trailing gap below the last row.** `grid.style.height` is `Math.ceil(max(colH))` — the row gap is deliberately *not* subtracted. Subtracting it put the lowest card's bottom edge exactly on the scroll container's edge, and since card heights are fractional while `offsetHeight` is an integer, the last card looked clipped at full scroll.
- **Hover changes the border colour and drops a shadow; it never changes the fill.** An earlier version darkened the background to `--surface` and the owner asked for it back out — with ten cards of different heights the shifting fills read as noise. `border-color:var(--accent)` plus `box-shadow:0 5px 12px rgba(0,0,0,.16)` is the whole effect.
- **The card title and the post's own title must stay on the same face.** `.lc-title` is 프리젠테이션 with no case transform, but `#modalLogView h3` inherits `.modal h3` (KoPub 돋움 + `text-transform:uppercase`), so an English title read lowercase on the card and SHOUTED once opened. `#modalLogView h3` now restates `font-family`, `text-transform:none` and `letter-spacing:0`. Only the size still differs (14 vs 12.5) — it is a heading.
- Preview length is `-webkit-line-clamp:8`, not a character count — clipping by characters gives a different number of lines per card once the font or column width changes. A post shorter than eight lines simply makes a shorter card, which is the whole point of the layout.
- `.log-cards-scroll` had to be added to `consumedByInnerScroll`'s selector list, or scrolling the card list flips the OC page out from under you.

**Paged grids** — three views now share the same "one page fills the remaining height, page buttons pinned below" shape: Pair list, ARCHIVE PROMPT, and the pair-detail gallery (LOG is no longer one of them — it is the card grid above, and is allowed to scroll). Their view roots (`#view-pair.active`, `#view-archive.active`) are `display:flex; flex-direction:column`, the body is `flex:1; min-height:0`, and the grid is `flex:1` with **explicit `grid-template-rows`**. The per-page count in JS must match rows × columns in CSS or the last row will be clipped: `PAIR_PER_PAGE`/PROMPT are `8` (4×2 desktop, 2×4 phone), OOC/ETC are 15 rows editing / **14 reading** / 10 on phones, gallery is `galleryPerPage()`. OOC/ETC are the one case that varies with `isLoggedIn` — they're a `<table>`, not a grid, so there is no CSS row count to keep in sync, and reading mode gives a row back to the search bar that only exists there. `applyEditMode()` re-renders ARCHIVE, so the count follows a login/logout without anything extra.

**`.archive-body`'s `padding-bottom:4px` is a measured value, not a taste call.** Even at 14 rows the reading-mode table was 472px inside a 466px `.archive-table-scroll` and scrolled by exactly 6px; the 6px came back by trimming the body's bottom padding from 10px, which also pushes the page buttons down 6px (body height itself is unchanged). Because `.arc-nai-grid` and `.archive-table-scroll` are both `flex:1` in the same body, PROMPT grows by the same 6px and all three sub-categories keep their page buttons on one line. If you change row height, row count, `gap`, or the pagination slot's `min-height`, re-measure `scrollHeight - clientHeight` on `.archive-table-scroll` with a **full** page — a folder with fewer posts than a page will report 0 and tell you nothing. Short pages are padded with invisible `.post-slot` / `.gallery-slot` elements so the grid height never changes with item count.

**Gallery/LOG are shared engines** — the pair-detail gallery and log panes are also used by the OC detail modal, so those renderers do **not** look elements up by id. They read a *host* object — `PAIR_GALLERY_HOST` / `OC_GALLERY_HOST` / `PAIR_LOG_HOST` / `OC_LOG_HOST`, each `{root, getPost, save, horizontal}` — and resolve elements as `root.querySelector('.gallery-grid')` etc. via the `gq()` / `lq()` helpers. **If you add a control to one pane, give it a class and bind it inside `initGalleryRoot()` / `initLogRoot()`, not by id**, or the OC copy silently won't work. `galleryHost`/`logHost` are set when a detail modal opens (and re-set by any control's own handler, since only one modal is open at a time). Module-level gallery state (`galleryPage`, `gallerySelectMode`, …) is deliberately shared and reset on open. `host.horizontal` flips the page-change animation between `translateY` and `translateX`.

**OC** — a third content type between PAIR and ARCHIVE: `state.ocPosts` (a `LIST_KEYS` array) plus `state.ocCats` (see Sidebar sub-categories below), where **each category owns its own folder list** (`cat.folders`, same shape as PROMPT folders but blur is forced off and the folder modal hides that option via `ctx.hideBlur`). Folders used to be one flat list shared by every OC post regardless of category; `ocFolderCtx(catId)` / `renderOcFolderBar(catId)` / `ocFoldersOf(catId)` all take the category explicitly now, and `ocFolderIdOf(item)` resolves through `ocCatOf(item.type)` first — so switching categories in the sidebar shows a completely different folder bar. The legacy global list still lives at the (now write-only-never-again) `ocFolders` scalar key purely so `normalizeOcCats()` can absorb it into the first category on the one-time upgrade from "no categories" to "at least one" — don't repurpose that key for anything new. The list view reuses PAIR's paged grid (8/page) and PROMPT's folder-tab styling, scoped to the current category. The detail modal has **no index tabs** — `#ocPages` holds three absolutely-positioned `.oc-page`s (profile / gallery / log) that `setOcPage()` slides vertically with `translateY((i-current)*100%)`, driven by the wheel (600 ms lock so one flick moves one page) and a vertical swipe only — there are no click targets; `.oc-page-dots` sits *outside* the modal on the left and is display-only. **Its gallery pages horizontally** so that vertical scrolling stays free for the modal's own paging. `consumedByInnerScroll()` stops a page flip while a nested scroller (`.oc-free-box`, `.log-table-scroll`, or on phones the `.oc-page` itself) still has room to scroll.

**PAIR's detail modal is now the same machine as OC's.** It used to navigate by an index tab strip drawn outside the modal (`.pd-index-tabs`, `right:100%`); the owner asked for OC's scroll behaviour instead, so the tabs are gone entirely and `.pd-tab-content` / `.pd-tab-pane` are now the exact counterpart of `.oc-pages` / `.oc-page`: container `position:relative; height:580px; overflow:hidden`, panes `position:absolute; inset:0` sliding by `translateY((i - idx) * 100%)`, driven by `setPdPage()` and a `#pdPageDots` strip that is display-only. Three knock-on facts:
- **The `8px 4px 8px 0` inset moved from the container to each pane**, for the same reason OC's did — a pane is `inset:0` and must land exactly outside the frame when pushed 100%. That makes an absolutely-positioned child's containing block the pane's padding box, so `.pd-tab-pane-gallery .gallery-fab-row` needs `bottom:16px` (8 + 8), which is why it now shares OC's rule instead of the base `8px`. Verified identical to OC: grid top offset `117.6`, grid `658 × 390.8`, fab `16` from the frame's bottom edge, container `580`.
- **PAIR's gallery pages horizontally now** (`PAIR_GALLERY_HOST.horizontal = true`, `.gallery-grid-wrap.horiz`, `《 》` in place of `︽ ︾`). It has to: vertical wheel and vertical swipe are what flip the modal's own page, exactly as in OC. The `.horiz` hint positions (`top:17px / bottom:14px`) exist because `︽ ︾` draw only 13px of ink inside their 26px box while `《 》` draw 25px — those numbers are what keep the two galleries lined up. On phones the hints go back to `4px` or they cover the first/last thumbnail row.
- **`.pd-tab-content` no longer scrolls** (`overflow:hidden`). INFO is designed to fit 580 exactly with `.pd-desc-box` absorbing the overflow; on phones `.pd-tab-pane` gets `overflow-y:auto` so the column scrolls instead, matching `.oc-page`.

**The two page sliders share one gesture binder,** `bindPageGestures(el, step, paneSel)` — vertical wheel (600 ms lock), middle-button drag, vertical swipe — called once for `#ocPages` and once for `#modalPairDetail .pd-tab-content`. It bails on `e.__ocHandled` and on any horizontal wheel (the side pagers and both galleries claim those), refuses to flip while a scrolled-in `.oc-theme-list` is under the pointer, and defers to any inner scroller that still has room: `.oc-free-box, .side-memo-box, .log-table-scroll, .log-cards-scroll, .pd-desc-box, .timeline-list, .msg-list` plus the pane selector. The last three are PAIR-only and the first two OC-only; listing all of them for both is harmless because a box with no overflow reports `scrollHeight <= clientHeight` and is skipped. **Add a new scrolling box inside either modal and you must add it here**, or scrolling it flips the page out from under the reader.

The horizontal hints sit **7px** in from the side, not 2px: `.gallery-grid-wrap` is `overflow:hidden` and the idle bounce translates them 4px *outward*, so a 2px inset put them 2px past the edge for half of every cycle and they visibly clipped. 7 leaves 3px of clearance at the peak (measured). The vertical pair are safe at 4px because `︽ ︾` draw their ink in the upper half of their 26px box, leaving ~16px of empty box on the side they bounce toward. And `.gallery-grid-wrap.horiz .gallery-scroll-hint.disabled` has to re-state `animation:none` — the plain `.gallery-scroll-hint.disabled` rule that greys out a dead-end arrow is a weaker selector than the `.horiz` positioning rules, so in the OC gallery the greyed-out arrow went on twitching.

**Sidebar sub-categories (PAIR · OC)** — the `ALL / Ai chat / Dream` strip is no longer fixed markup. `state.pairCats` and `state.ocCats` are `SCALAR_KEYS` lists of `{id, name}`, and each post carries that id as `post.type`. `#pairSub` / `#ocSub` are empty in `index.html`; `renderNavSub(nav)` draws them, where `nav` is `PAIR_CAT_NAV` / `OC_CAT_NAV` — the same host-object pattern the gallery and theme songs use, so both sides run one implementation off the same code. **PAIR's two ids must stay `aichat` / `dream`**: existing posts point at them, and `normalizeCats()` only supplies those as the *fallback* when the key is absent.

The `ALL` row's **id stays `'all'`** while its visible label lives in one constant, `ALL_CAT_LABEL` — it is display text, not something any stored post points at, so renaming it (it was `전체` until now) is a one-line change.

**Both have `ALL` now; what differs is what happens to posts when a category is deleted** — `nav.orphanOnCatDelete` / `nav.minCats`. `hasAll` is true for both and only controls whether the `ALL` row is drawn; **do not re-fuse the two flags**, they were one flag until OC gained `ALL` and the delete behaviour has to stay split:
- **PAIR** (`orphanOnCatDelete:true, minCats:0`): `ALL` is a render-only row, not in the list, so there's no "default" to fall back to. Deleting a category leaves its posts' `type` pointing at a dead id — they just show under `ALL` (`catCtx().onDelete` deliberately does not clear `type`, so re-creating the same id restores them). A dead id is invisible on the list card — cards show title + subtitle, never the category. Deletion has no floor; the last category can go.
- **OC** (`orphanOnCatDelete:false, minCats:1`): a categoryless OC post is still impossible, **not because it would be invisible — `ALL` would show it — but because OC folders hang off the category** (`cat.folders`), so `ocFolderIdOf()` has nowhere to resolve. `normalizeOcCats()` guarantees at least one category always exists (seeding an id'd `기본` category on first-ever load if the list is empty), `loadState()` re-homes any post whose `type` doesn't match a real category to `state.ocCats[0]`, and `catCtx().canDelete` refuses once `cats().length <= minCats` (so the last one can't be deleted from the UI). Deleting a non-last OC category **reassigns its posts to the next remaining category** instead of leaving them dangling — the delete-warning text says so, and differs from PAIR's wording for exactly this reason. `defaultCatId(nav)` / `catTitle(nav, id)` centralize the `hasAll` branching so call sites don't special-case it themselves.

**OC's `ALL` has to reckon with secret folders, which PAIR's doesn't** — it lists every post in `state.ocPosts` order regardless of category or folder, so posts from locked secret folders land in it. They are rendered, not filtered out (hiding them would leak "there is nothing here"): `ocLockedFolderOf(post)` resolves the post's own category → folder → `folderLocked()`, and a match gets `.post-card.locked` — thumbnail blurred, title and catchphrase replaced by **`&nbsp;` placeholders with `LOCKED` overlaid absolutely**. Keep the two empty lines; deleting them shrinks that one card and breaks the grid's row height. The blur carries a `scale(1.14)` (the gallery's trick for pushing a blur's soft edges out of frame), and that overscan spills **downward into the title strip**, which has no background of its own — so `.oc-lock-info` gets `background:var(--bg); z-index:1` to keep the blur visually confined to the photo. Verified: locked and normal cards both 249px tall with a 50px info block. Clicking opens the same `openFolderUnlock()` dialog the folder itself uses, and on success re-renders and opens the post — the session's `unlockedFolders` set is shared site-wide, so unlocking from `ALL` unlocks the folder everywhere, which is the intent. None of this is reachable in edit mode: `folderLocked()` always returns false for the admin. The folder dropdown is `display:none` while `ALL` is showing (folders are per-category, so there is nothing coherent to pick), and `ocWriteBtn` therefore ignores `currentOcFolderId` entirely in `ALL` and files the new post in the **first category's first folder**, locked or not; inside a category it still uses the folder you are looking at.

**List cards are identical on both sides**: thumbnail, then `.post-title` (제목) and `.post-catch` (타이틀/부제, `post.subtitle`), ellipsized to one line so every card's info block is the same height. **PAIR and OC lists are sorted for display by `byNewest()`, not left in array order.** The stored order is meaningless: new posts are `unshift`ed to the front, but folder/category moves and re-saves have shuffled it — in the live data OC's newest post sat third and PAIR's third-newest sat seventh. `id` is `Date.now()` at creation, so sorting by it descending is the real "newest first". Sort a **copy** — reordering `state.ocPosts` / `state.pairPosts` itself would be picked up as a change and written back to Firestore.

**Adding a category no longer opens a modal.** The `PAIR`/`OC` sidebar row now carries a small `＋` (`.nav-cat-add`, a sibling of `.nav-item` inside `.nav-item-row` — button-in-button isn't valid HTML) that calls `startAddCat(nav)`: switch to that section (`openNavSection`, factored out of `selectNavSub` since the plus icon needs the same view-switch without touching the currently-selected category) and set `nav.adding = true`, which makes `renderNavSub` render an inline `.ns-add-row` (input + ✓ + ✕) at the bottom of the list instead of nothing. Enter/✓ commits, Escape/✕ discards; there is no other create path. **Rename/delete still reuse `openFolderModal()`** via `catCtx(nav)` — that's why the modal's title, name label, placeholder, error text and delete button all read `ctx.label` (`'카테고리'`), and why `catCtx` no longer defines `newFolder`/`onCreate` (dead now that add doesn't go through the modal). The active highlight is painted on `.nav-item-row` itself (`.nav-item-row:has(.nav-item.active)`, with `.nav-item.active`'s own background made transparent inside a row) rather than on `.nav-item`, so it visually extends behind the `＋` too instead of stopping at the label's edge — this is the codebase's first use of `:has()`.

**Every entry point that changes the current PAIR/OC category must call `nav.title(catTitle(nav, id))`.** The topbar's "Pair · Dream" text is only ever set by that call — it is not derived from `currentPairFilter`/`currentOcFilter` at render time. If you add another place that reassigns `currentPairFilter`/`currentOcFilter`, set the title in the same place.

Reorder is a `draggable` `.nav-sub-item` with a live FLIP (`flipByKey`); the `dragover` handler **moves the existing node with `insertBefore` instead of re-rendering** — re-rendering destroys the element being dragged, so `dragend` never fires and the new order is never saved. Same trap as the gallery's live reorder.

Two knock-on rules: the move buttons in the select bars are generated per category (`renderMoveBtns`), so `particleRo()` picks 로/으로 from the name's final jamo — don't hard-code the particle. `카테고리 없음으로` (move to no-category) is gated on `nav.orphanOnCatDelete` and only ever renders for PAIR, since OC has nowhere for a categoryless post to go. And `.nav-sub`'s `max-height` is a generous fixed value (560px / 70vh) because the transition needs one; a longer list is absorbed by the sidebar's own scroll.

**ARCHIVE folders are per sub-category.** Each of OOC / PROMPT / ETC owns its own flat list of `{id, name, secret, pwHash, blur}`, and each post carries a `folderId`. The three lists are three separate `SCALAR_KEYS` entries mapped by `ARC_FOLDER_KEY` — PROMPT keeps the original `archiveFolders` key (renaming it would orphan live data), OOC/ETC use `archiveFoldersOoc`/`archiveFoldersEtc`. The symptom is a category that always opens on the same non-first folder no matter what. The add/edit modal is **shared by every folder host** — `openFolderModal(ctx, folder)` takes a context object (`galleryFolderCtx(post)` / `archiveFolderCtx(cat)` / `ocFolderCtx(catId)` / `logFolderCtx(post)`) supplying `getList/canDelete/deleteWarn/newFolder/onCreate/onDelete/save/rerender`. **LOG folders** (`post.logFolders`, on both PAIR and OC posts, set up by `migrateLog`) use the **gallery's tab row**, not the topbar dropdown, for the same reason the gallery does: LOG lives inside a detail modal, which has no topbar. That works because the dropdown sits *outside* the `[data-editonly]` block, and that block carries `.keep-space` so view mode swaps it to `visibility:hidden` (still occupying its box) instead of the global `display:none`. **On phones that reservation is dropped back to `display:none`** — the topbar is too narrow to hold empty space for two absent buttons. The ARCHIVE dropdown is now shown for all three sub-categories; it is never hidden (the LOG tab row *is* conditionally hidden, but only because it competes for list height — the topbar has a fixed 60px height, so an extra button there costs nothing).

**LOG has the same select mode**, driven by `logSelectMode` / `logSelectedIds` and the `.log-select-btn` / `.log-select-delete` buttons that share the `.log-pane-toolbar` row with the folder tabs. **ARCHIVE select mode works in all three sub-categories.** `arcSelectMode` / `arcSelectedIds` and the 삭제 button were already category-agnostic; what differed was the UI, since OOC/ETC render a table rather than a thumbnail grid. **Re-binding a shared element is how post data leaks between posts.** The detail modals are reused for every post, so any binder called from `fillOcDetail`/`fillPairDetail` must not `addEventListener` on the shared element — the old listener stays attached and its closure still points at the *previous* post, so editing post B writes B's markup into A. This actually shipped: `bindMetaContainer()` did it and two OC posts ended up with identical labels. It now binds once (`el._metaBound`) and every handler saves through `el._saveMeta`, which each call reassigns. `bindMeta`/`bindBodyText` are safe only because they assign `el.oninput`/`el.onblur` (properties replace, listeners accumulate) — keep that distinction in mind when adding a binder.

**OC profile page order** — keyword row → profile → quote → free-text toolbar → free-text box, with the right-hand column holding a three-page horizontal slider (vertical image / theme songs / memo) driven by `makeSidePager()` via horizontal swipe, horizontal wheel, or the dots beneath it. **Side columns are shared pagers** — both detail modals put a `.side-pages` / `.side-page` / `.side-dots` slider in their right column, built by `makeSidePager(pagesEl, dotsEl)`: OC has [image · theme · memo], PAIR has [image · TIMELINE · messages · theme · memo] — the memo is the last page in both. Theme songs are host-driven for the same reason the gallery is (`OC_THEME_HOST` / `PAIR_THEME_HOST` = `{root, getPost, save, idx}`, elements looked up by class inside `root`) — two copies exist in the DOM at once, so ids are not available.

`.side-pages` is `overflow:hidden`, which stops *scrollbars* but does **not** stop the box from being scrolled: focusing a caret (or selecting text) inside a page that is currently translated off-screen makes Chrome silently scroll the container to reveal it, and with no scrollbar it never comes back — the whole column stays offset by that amount forever. Two defences, keep both: `makeSidePager` listens for `scroll` and forces `scrollLeft`/`scrollTop` back to 0, and anything that focuses an editor inside a side page uses `focus({preventScroll:true})`. This only became reachable once a page held a text editor (the memo), so it is easy to reintroduce by adding another.

**Memo pages** (`.side-page[data-sidepage="memo"]`, `#ocMemo` / `#pdMemo`, stored on `o.memo` / `p.memo`) are deliberately chrome-free — no heading, border, or background, just text in a `.side-memo-box` that scrolls on its own (and is listed in `consumedByInnerScroll()` so scrolling it doesn't flip the OC window's page). They are the only editors that **round-trip between a source form and a decorated form in the same element**: `paint()` writes the stored HTML and runs `applyCodeFences()` so ``` ``` ``` shows as a real code block, and `_toRaw()` puts the source back. The swap to source is bound to **`mousedown`, not `focus`** — it has to happen before the caret is placed, or the click lands in a DOM that is about to be replaced and the caret jumps to the start. Consequences worth knowing: the code block's copy button can't be clicked while logged in (the mousedown swaps it away first — copying is a reading-mode action), and **saving must never run against the decorated DOM** or the ``` fences are destroyed permanently. `_save()` therefore checks the live DOM (`el.querySelector('.code-block')`) rather than a boolean flag — a flag drifts out of sync whenever the element is re-rendered while already focused, since no `focus` event fires to clear it. Only `applyCodeFences` runs here, not the full `decorateContent`, so `#`/`|`/`>` stay literal. Its toolbar is the free-text one minus U and S, which is what makes it fit PAIR's 244px column on one row (8 × 24px buttons + a 9px separator + 32px of gaps = 233px) — it is `flex-wrap:nowrap` for that reason, and the phone block puts `wrap` back because 38px touch targets can't fit either way. `.side-memo blockquote` has to repeat the `border-left:3px solid var(--accent)` rule; that styling is written out per editor (`.arc-editor` / `.arc-view-content` / `.oc-free` / `.md-quote`), so a new editor with a 인용구 button silently renders quotes as plain text until it's added to that list.

**`.side-memo` and `.oc-free` are `display:flow-root`, and must stay that way.** Both are `min-height:100%` inside a scrolling box, i.e. already exactly as tall as the space available. A blockquote, `<hr>` or code block as the *first* child brings an 8px top margin, and on a plain block that margin **collapses out** and becomes the box's own margin — pushing a full-height element down by 8px and producing a phantom 8px scroll on content that is one line long. Measured: a single `<blockquote>` gave `scrollHeight 502` against `clientHeight 494`. `flow-root` makes the element a block formatting context so the margin stays inside. **Unsaved-changes guard on write modals** — `guardUnsavedClose(overlayId, getSnapshot)` (near `openModal`/`closeModal`) is wired for `modalArcWrite` and `modalLogWrite`, the two modals with an explicit "게시"/"저장" button (as opposed to PAIR/OC detail, which autosave every field on blur and so have nothing to lose). **Sign-out must not wait on the save queue** — `SiteStore.signOut()` used to `await flushNow()` unconditionally. `flushNow()` returns the tail of `flushChain`, and a Firestore write that never gets acknowledged (offline, or the write stream backed up) leaves that promise pending **forever** — so the 로그아웃 button silently did nothing, permanently, for the rest of the session. It now races the flush against a 3s timeout and signs out regardless. Any binder that awaits a Firestore promise before doing something user-visible needs the same treatment.

**Sign-out is also latched, because `signOut(auth)` can fail quietly.** Timing it out (or having it reject on blocked IndexedDB / no network) leaves the session **persisted in the browser**, so the next reload — or any token refresh, or another tab — fires `onAuthStateChanged` with the admin user still there and the site walks itself back into edit mode. That is the other way "로그아웃이 안 돼요" happens, and no amount of timeout tuning fixes it. `SiteStore.signOut()` therefore writes a `siteSignedOut` flag to `localStorage` **first**, before doing anything that can fail; while that flag is set, the auth listener refuses to go admin, reports signed-out, and retries `signOut(auth)` in the background until it takes. `signIn()` clears the flag **before** awaiting `signInWithEmailAndPassword`, not after — the auth callback lands during that await, and clearing afterwards would have the listener eject the login that just succeeded. `signOut()` also notifies unconditionally now instead of only `if (isAdmin)`, so a UI stuck in edit mode is pushed back regardless of what the module thinks the state is.

**Theme songs** — `o.themeSongs` is `[{id, cover, title, artist, lyrics}]`. **The free-text toolbar is shared by three editors** — OC's free-text box (`.rt-toolbar-ocfree`) and the two memo pages (`.rt-toolbar-memo` inside `#ocSidePages` / `#pdSidePages`), all bound by `bindFreeToolbar(toolbar, editorId, save)`. **Font-size stepping** — that toolbar's ˄/˅ buttons that change the selection by 1px. `execCommand('fontSize')` only accepts steps 1–7, so `stepFontSize()` runs it with `7` purely to make Chrome split the range, then rewrites each `font[size="7"]` into a `<span style="font-size:…">`. **The base size must be measured before calling `execCommand`** (`selectionFontSize()`) — Chrome *replaces* an existing sized span with the `<font>` element, so reading the size afterwards always returns the box's default and every click past the first would be a no-op. **Profile subtitle** — `.pd-sub-input` is the small grey line under each name (PAIR's character and persona, OC's profile). **The two lightboxes are separate implementations that must look identical.** `#lightbox` (gallery, `z-index:200`) is a **column**: an `.lb-row` of `‹ .lb-stage ›` above an `.lb-thumbs` strip of the current folder's images, capped at `min(720px,92vw)` so it never grows past the detail modal it sits over. `#arcLightbox` (ARCHIVE attachments, `z-index:700`) keeps its right-hand vertical thumb column; only its arrow shape (`border-radius:50%`) and image corner radius were matched to the gallery's. `.lb-count` (the `n / total` chip) is anchored to `.lb-stage`, which is why the stage is sized by the image rather than being a fixed box — a fixed stage would letterbox portraits and leave the chip floating in black. It appears on `:hover`, and unconditionally under `@media (hover:none)`.

`#lightbox` has a second state, `.zoomed`, toggled by the `.lb-zoom` button that shares `.lb-count`'s hover-to-reveal rule: it collapses the thumb bar and lifts the image cap from `80vw/74vh` to `calc(100vw - 116px)/100vh`. Four things it depends on:
- **The transition is on `max-width`/`max-height`, not `transform: scale()`.** Both caps are animatable lengths, so the photo really does take up more room as it grows — which matters because `.lb-count`, `.lb-zoom` and the two arrows are all positioned off the photo's actual box. A `scale()` would move the pixels and leave every one of those behind. `--lb-zoom-ms` / `--lb-zoom-ease` in `:root` keep the photo, the thumb bar and the column gap on one beat.
- **The thumb bar collapses by `max-height`, not `display:none`,** since display can't be transitioned — hence the `.lb-thumb-bar` wrapper around `.lb-thumbs`. And the "only one image" case hides that wrapper **by a `.hide` class rather than an inline `style.display`** (CSS cannot override an inline style, so the two hiding conditions would have fought).
- **The arrows stay flex siblings of the photo** at the usual 18px, in both states — anchoring them to the viewport edges instead left a huge dead gap beside a narrow photo. The price is that the 116px they occupy (`40×2 + 18×2`) has to come off the zoomed `max-width`, or a wide photo slides under them. The phone block already absolutes the arrows over the photo, and there `max-width` goes back to a full `100vw`. Verified: gap is exactly 18px either side, zoomed and not, for both a landscape and a portrait source.
- The zoom icon is inline SVG for the same reason the alignment icons are, and `openGalleryLightbox` clears `.zoomed` on every open so zoom never leaks from one photo to the next. That removal happens while the lightbox is still `display:none`, which is also what stops it from animating on open.

The photo is still capped at its natural size — `max-width` only ever shrinks — so zoom gains nothing on a source smaller than the viewport. Deliberate: upscaling past the stored resolution just looks soft.

**The thumb strip is a nine-wide window, not the whole folder.** `lbThumbWindow(idx)` is `clamp(idx − 4, 0, n − 9)`, which puts the current photo in the middle slot everywhere except the first and last four, where there is nothing to pad with and the strip sits flush against the end. `markGalleryLbThumb` recomputes it on every photo change and only re-renders when the window actually moved. The `‹ ›` buttons at the two ends (`.lb-thumb-nav`, which carries `.lb-nav` too so it inherits the symbol-rescue font, the centring correction and the styling) page **the strip alone** by nine at a time and deliberately leave the displayed photo where it is — so the strip stays where the reader put it until they change photo, at which point it recentres. `.lb-thumb-bar:not(.paged)` hides both buttons when nine or fewer images make paging meaningless. The widths are chosen so the whole bar is exactly 720px, the detail modal's width: `64×9 + 8×8 + 2×2 = 644` for the strip, plus `28×2` buttons and `8×2` gaps.

Arrow keys drive both lightboxes (`initLightboxKeys`, a single document-level `keydown`). It checks `#arcLightbox` before `#lightbox` because the attachment lightbox sits above the gallery one, and it bails on `isContentEditable`/`INPUT`/`TEXTAREA`/`SELECT` targets — a lightbox can be open while a post editor still holds focus behind it, and there the arrows have to keep moving the caret.

**Testing any of this from an automation tab needs care: the MCP tab reports `document.hidden === true`.** CSS transitions do not advance and `setTimeout` is throttled to ~1s there, so the zoom appears not to happen at all and one arrow press per ~2.5s is all that gets through `lbAnimating`. Neither is a real bug — nothing here waits on a transition event. To check the zoom rules, inject `*{transition:none!important}` and read the end state; to check the mid-flight layout, set the interpolated values by hand and confirm the photo never leaves the viewport (it can't: the photo grows by 26vh exactly as the 68px bar plus 14px gap collapse, landing on 100vh).

**Lightbox slide animation must not depend on animation events or on frames happening.** `slideGalleryLightbox(dir, commit)` chains out → swap → in, and both hand-offs are plain `setTimeout`s. `Animation.onfinish` was tried first and is wrong here: the finish event is delivered as part of the rendering step, so in a **background tab it never fires** — the image froze mid-fade and every later arrow press was blocked by the `lbAnimating` guard. For the same reason the incoming animation is explicitly `.cancel()`ed on a timer: a freshly created animation gets its start time during the first frame, so in a hidden tab it stays pending at keyframe 0 (opacity 0) forever. Timers are throttled to ~1s in background tabs but they do fire, so state always converges. Same rule applies to `scrollIntoView` — the thumb strip uses the default instant behavior, not `'smooth'`, which also needs frames.

**Pinning** — ARCHIVE and LOG (both PAIR's and OC's, via the shared engine) each cap pins at 3 and sort pinned items to the front at render time; nothing about the stored order changes, an entry just carries `pinned:true`. The visible `No` column is therefore **not** the row's position — it comes from a `Map` of registration order (`displayNo`), so pinning or searching never renumbers an existing post. The limit is per list: three per ARCHIVE category-set and three per post's `log`. The `📌` marker (`.arc-pin-tag`, shared by both tables) needs `display:inline-block; font-size:9px; line-height:1` — left at the cell's own size, an emoji's line box is taller than the text's and **grew the pinned row by 3px** (35 vs 32), so a pinned row visibly stepped out of the table. Any emoji dropped inline into a fixed-height row needs the same treatment.

**Two-across image blocks** (`.img-pair`) — unlike code fences and auto-format, this one **is** real saved markup, not a render-time transform: `<div class="img-pair" contenteditable="false"><div class="img-pair-cell"><img></div>×2</div>`. It is created by dragging one image in the editor onto another (`initEditorImageTools(editorId)`, wired for `arcContentEditor` and `logContent`), and afterwards edited only through the hover toolbar, which grows two buttons when the hovered image sits in a cell: `변경` (file picker → replace that one cell) and `⇄` (swap the cells). `↑ ↓ ✕` retarget too — up/down move the **whole block** among its siblings, and `✕` deletes just that cell and then *unwraps* the block back to a plain `<img>`, since a one-cell "pair" is meaningless.

Three constraints worth keeping:
- **Only plain images participate in the drag** — `plainImg()` returns `null` for anything already inside an `.img-pair`, on both the source and target side. Allowing a drop onto an occupied cell would silently discard the image that was there; the `변경` button is the one deliberate path for that.
- **The `drop` handler must `preventDefault()`.** contenteditable performs its own image move as the drop's default action, so without it the browser relocates the source image *in addition to* the block being built.
- `contenteditable="false"` on the block (same as `.code-embed`) is what stops the editor from splitting cells or parking a caret between them. It is a `DIV`, so `BLOCK_TAGS` already counts it as a fence line separator; `.fold-block > .img-pair` gets the same `margin-left:20px` as `.code-block` for when it lands as a direct sibling of `.fold-head`. `.img-pair > .img-pair-cell > img` needs **two classes** in the selector to beat the per-editor `… img{margin:8px 0}` rules, which are spread through the file and some come later.

Touch is not wired: `initTouchDrag()` deliberately skips `[contenteditable="true"]` so iOS text selection keeps working, so the block is created on desktop only. It renders and can be reordered/deleted anywhere.

**Post body transforms** — saved post HTML is decorated at *render* time, never at save time, so the stored content stays plain editor output. `decorateContent(el)` runs `applyCodeFences()` (turns ` ``` `-fenced runs into `.code-block` with a copy button), then `applyMarkdownBlocks()`, then `ensureCodeEmbedCopy()` (back-fills a copy button into `.code-embed` toolbars saved before that button existed). `applyAutoFormat()` skips anything inside `.code-block`.

**Markdown is split across two functions by scope, and the order matters.** Line-level syntax (`> quote`, `# heading` ×6, `| table |`) lives in `applyMarkdownBlocks()`, which runs from `decorateContent` and therefore applies everywhere post bodies are drawn (ARCHIVE and LOG). Inline syntax (`**bold**`, `*italic*`, plus the quote/paren auto-coloring) lives in `applyAutoFormat()`, which only LOG calls — so italic works exactly where bold already did. Three ordering constraints:
- `applyCodeFences` must run **first**, and `applyMarkdownBlocks` skips any line that resolves inside `.code-block`/`.code-embed` (`mdInsideCode`) — otherwise a `#` or `|` inside a code sample gets eaten.
- In `applyAutoFormat`'s alternation, `\*\*…\*\*` must stay **ahead of** `\*…\*`. Regex alternatives are tried in order, so italic-first would claim the leading `**` of every bold run. The capture-group indices shifted by one when italic was inserted — the branches read `m[1]`…`m[4]`, not `m[1]`…`m[3]`.
- A table needs a `|---|---|` separator line **directly under** its header row (`MD_TABLE_SEP_RE` demands two or more columns). Without that requirement a lone `---` used as a divider, or any sentence containing `|`, would turn into a table.

`applyMarkdownBlocks` reuses the code-fence machinery wholesale — `flattenForFences` → line list → `resolveFenceOffset` → `fenceLineBoundary` → replace one Range — for the same reason fences need it: contenteditable does not reliably put each visual line at the top level. Groups are collected first, then applied **back to front**, because `marks` holds pre-edit coordinates. Verified against all 53 stored posts: 0 exceptions, and on the two posts that actually convert, the rendered text is byte-identical once markdown markers are stripped — nothing but the markers is consumed.

**Post bodies have two deliberate leadings: 17.5px for a wrapped line, 21px for one the author broke with Enter.** The 21 is `line-height` + `margin-top:3.5px`. This started as `.fold-body`'s 7px, which existed only to separate a fold's title from its content — but because a single `.fold-block` routinely holds **many sibling `.fold-body` divs**, one per line, from the old Chrome-splits-on-Enter behavior (see the collapse-hiding note), that margin was in practice already acting as the Enter-line gap *inside* folds while lines outside folds got nothing. Three rules now carry it: `.fold-body` keeps `7px` (title gap only), `.fold-body ~ .fold-body` overrides to `3.5px` (line gap), and `.arc-view-content > div:not([class])` — plus the same for `.arc-editor` / `.log-editor` — gives outside-fold lines the same `3.5px`.

`:not([class])` is what keeps this off the block widgets — the line `<div>`s contenteditable produces have no class, while `.fold-block` / `.code-block` / `.code-embed` / `.img-pair` all do and carry their own spacing. The `:first-child` reset only fires when a body happens to start with a `<div>`; the usual shape starts with a bare text node, so the first `<div>` is genuinely the second line and correctly keeps its margin. A `<div><hr></div>` line measures more than 21 — that is the `<hr>`'s own margin, not a bug.

Two things this cost a round trip to learn, worth not repeating. First, pasted blank lines (`<div><br></div>`) are all over these posts and *look* like the cause — they are not, and stripping them at render time is the wrong fix: a blank line is supposed to render as a blank line. Measure `getBoundingClientRect()` on consecutive single-line blocks against the wrapped-line delta inside one block before concluding anything. Second, "make the spacing consistent" turned out to mean "standardize on the larger value," not the smaller one.

**Paste normalization is formatting-only, by explicit instruction.** `normalizePastedText()` converts CRLF→LF and `&nbsp;`→space and does nothing else. Earlier versions also collapsed blank lines and trimmed trailing whitespace; that was rejected as **changing the author's content** rather than matching format. Keep any future additions to this function on the same side of that line — invisible characters that break layout, yes; anything that removes or merges what was written, no.

**Fold blocks** (`.fold-block`, Notion-toggle style) are real saved markup; a delegated click toggles `.open` — the whole `.fold-head` is clickable when reading, but **only the `.fold-arrow`** while editing, so clicking the title still places the caret. `.fold-title`/`.fold-body` hold no placeholder text — they're genuinely empty and rely on `body.logged-in .fold-title:empty:before` / `.fold-body:empty:before` (same trick as `.oc-free:empty:before`) for the "타이틀"/"내용을 입력하세요" hint, so there's nothing to select-and-delete before typing. All three editors that offer a fold button (ARCHIVE, PAIR_LOG, OC free text) insert them through the shared `insertFoldBlock(editorId)`, and save through `editorHtml(editorId)`, which strips `.open`, so a post always opens collapsed no matter how the author left the editor.

**Collapsing hides every direct child of `.fold-block` except `.fold-head`** (`.fold-block:not(.open) > *:not(.fold-head){display:none}`), not specifically `.fold-body`. This is deliberate defense-in-depth: some already-saved posts have a fold with **multiple sibling `.fold-body` divs** inside one `.fold-block` (see the `initFoldEnter` note below for how that happened), and `applyCodeFences` itself can legitimately leave a `.code-block` as a direct sibling of `.fold-head` rather than nested one level down inside `.fold-body` (when the fenced lines were the *only* content of their line-container — see the `fenceLineBoundary` note). Targeting `.fold-body` specifically would miss both of these and leave content visible after collapsing.

`insertFoldBlock` builds the block with `document.createElement` and places it via `Range.insertNode()` at the current selection **instead of** `execCommand('insertHTML')` — critically, this means it inserts wherever the caret actually is, including inside another fold's `.fold-body`, which is what makes folds-inside-folds work with zero extra code. The same reasoning applies to `insertBlockquote(editorId)` (shared by ARCHIVE and OC free text): `execCommand('formatBlock', false, 'blockquote')` converts the *nearest block ancestor*, which inside a fold is `.fold-body` itself — it doesn't turn the quoted line into a blockquote, it wraps the whole fold body in one (`<blockquote><div class="fold-body">…`), corrupting the fold. `insertBlockquote` sidesteps this the same way `insertFoldBlock` does: build the `<blockquote>` and `Range.insertNode()` it (wrapping the current selection if non-collapsed, otherwise inserting empty with a `<br>` to type into).

**Anything inserted through a modal or native file picker must save and restore the caret Range explicitly**, or it silently escapes an enclosing fold. `arcInsertCodeBtn` (opens `#modalArcCode`) and `arcInsertImageBtn` (opens a native `<input type=file>`) both call `editor.focus()` right before their `execCommand('insertHTML', …)` — but focusing an already-focused editor does **not** restore whatever selection existed before the modal/file-dialog stole focus, so without help the browser drops the caret back at its own default position (observed: escaping any enclosing fold entirely). Both now capture `window.getSelection().getRangeAt(0).cloneRange()` the moment the button is first clicked (before focus moves anywhere) and re-`sel.addRange()` it right before the `insertHTML` call.

**Fold Enter** is handled by `initFoldEnter(editorId)` (wired for all three editors alongside their fold button), which covers **two** carets, not one:

- **`.fold-title`**: pressing Enter always inserts a single `<br>` and never touches `execCommand`. If the fold is **collapsed**, the `<br>` goes immediately after the `.fold-block` in *its own* parent — which is either the top-level editor or, for a nested fold, the outer fold's `.fold-body` — so the cursor "exits" exactly one level up. If the fold is **open**, the `<br>` goes at the very start of `.fold-body` instead, so Enter drops the cursor straight into the content without leaving the fold. Both branches are one `insertBefore` call; nesting depth never needs special-casing because the block's own `parentNode` is always the correct target.
- **`.fold-body`**: this branch exists because leaving Enter here to the browser default is actively destructive. Chrome splits a block on Enter by cloning its own class onto a new sibling — so typing multiple lines inside `.fold-body` produced **several sibling `<div class="fold-body">` elements** instead of one `.fold-body` with internal `<br>`s. (This is why the collapse-hiding rule above targets "every child but the head," and why some already-saved posts have this exact shape.) The fix intercepts Enter here too and inserts a plain `<br>` in place, so multi-line fold content always stays inside the one `.fold-body` it started in.

Both branches route the resulting cursor placement through **`placeCursorAfterBr(sel, br)`**, not a bare `range.setStartAfter(br)`. This exists because of a real Chrome quirk: if the freshly-inserted `<br>` ends up as the *last* node in its container, positioning the collapsed selection immediately after it is not reliable — `execCommand('insertText')` (and real typing) can insert the next character *before* the `<br>` instead of after it, even though the Range itself was provably at the correct DOM boundary. `placeCursorAfterBr` works around this by guaranteeing the `<br>` is never trailing: if there's nothing after it (or only an empty text node), it inserts a filler `<br>` right after and points the selection **before that filler** instead — "before a following node" is the position browsers handle predictably; "after the last node in a container" is not. Watch for this same failure mode in any *new* Enter-key handling added to a contenteditable region — it doesn't reproduce under `dispatchEvent`-only synthetic testing without actually typing more text afterward, so verify with a real follow-up character, not just `evt.defaultPrevented`.

**Blockquote keys** live in `initBlockquoteKeys(editorId)`, which **every editor with a 인용구 button must call** — ARCHIVE directly, and the three free-text editors (OC free text, the two memos) through `bindFreeToolbar`. It was hard-wired to `#arcContentEditor` before, so quotes in the other editors had neither behaviour.

- **Enter** (not Shift+Enter, which keeps the browser's in-place `<br>`) `extractContents()`s anything after the caret into a new sibling `<div>` and moves the caret there, so writing continues as a normal paragraph instead of the browser's default of minting a second, nested blockquote.
- **Backspace at the very start** unwraps the blockquote in place. Without this a quote sitting at the **top of the post is unremovable** — the browser's default backspace merges a block into the preceding one, and when there is no preceding one it does nothing at all, with no other gesture that dissolves a blockquote. "Very start" is tested by cloning the range from the quote's start to the caret and checking it holds no text and no `img`/`hr`, so a leading image counts as content; anywhere else, and for non-collapsed selections, the browser's default is left alone.

`initFoldEnter` **returns early when the caret is inside a blockquote**, because a quote nested in a fold body puts both listeners on the same Enter and `preventDefault()` does not stop the other one from running. The innermost construct wins.

**Code-fence parsing (`applyCodeFences`) works on flattened text, not top-level DOM children.** An earlier version grouped only the element's *direct* children into "lines" (`<br>` or a top-level block tag as the separator), on the assumption that contenteditable always puts each visual line at the top level. It doesn't — the line right after inserting an `<img>` or `<hr>` often lands as a bare text node merged with the previous inline content (no `<br>` at all), which silently deleted that content and could desync which `` ``` `` paired with which, dropping or corrupting later code blocks in a post with several. `flattenForFences(root)` instead does a full recursive walk, building one plain-text string (with `\n` inserted for every `<br>` and — de-duplicated, so adjacent block tags don't produce a blank line — every block-tag boundary at any nesting depth) plus a parallel `marks` array of `{pos, container, offset}`, always recorded even when the `\n` itself is deduped away, so a position where several nesting levels' boundaries coincide still resolves to a specific (and specifically the most-recently-recorded) DOM point. `applyCodeFences()` finds all `` ``` `` occurrences globally and pairs them in document order `(1,2)(3,4)…` (an unpaired trailing fence is left untouched). Pairs are walked **back to front** so an earlier deletion never shifts a later mark's coordinates.

**Font size is the one thing carried across the fence.** `.code-block-body` is a `<pre>` filled by `textContent`, so every scrap of markup inside the fenced region is discarded on purpose — code has to render as written. That silently threw away the size set with the ˄/˅ buttons, which is the only formatting anyone actually wants on a code block. `fenceFontSize(root, range, point)` therefore reads a size out of the region *before* `deleteContents()` and `makeCodeBlock(code, fontSize)` writes it back as an inline style on the `<pre>` (beating the class's `font-size:11px`). It looks in two places because `stepFontSize` can leave the `<span style="font-size:…">` either **inside** the fenced region (the usual case — only the code lines were selected) or **wrapping the whole thing including both fences**, in which case the span is an ancestor of the range and never appears in `range.cloneContents()`; the second lookup walks ancestors up to `root`. The size lives on in the stored source as that same span, so it survives edit round-trips.

**Finding *which* DOM range to delete for a fence pair needs two passes, not one.** `resolveFenceOffset()` turns `openPos`/`closePos` (positions in the flattened string) back into an exact `(textNode, offset)` — that part is unambiguous, since fence characters always live in one specific text run. But the *deletable range* isn't "from one resolved point to the other": `fenceLineBoundary(root, point, after)` walks up from that text node to the nearest enclosing block-tag element (e.g. `.fold-body`), because coordinate math alone can't disambiguate nested closing boundaries that land on the same character position (opening boundaries nest inward so last-recorded/innermost naturally wins a tie; closing boundaries cascade outward, so the same rule picks the **outermost** one — exactly backwards for staying inside a fold). It returns `null` when there's no wrapping block at all (bare text merged directly into the editor root), and only then does the coordinate-based `resolveFenceOffset` fallback apply.

Finding the enclosing block is still not the whole answer, though — **that block can itself hold more than one line.** If a fold's content was typed as `<br>`-separated lines directly inside one `.fold-body` (rather than one nested `<div>` per line), naively deleting "all of `.fold-body`" to remove just the fenced lines would take the surrounding lines with it — real content loss, not just a fold-nesting cosmetic issue. `localLineBoundary(el, node, dir)` handles both shapes with one rule: walk `node`'s siblings within `el` looking for a **line separator** in direction `dir`; if found, the boundary is *inside* `el`, right at that separator (correctly scoping to just this line among several). If none turns up before running out of siblings, that means `el` itself holds nothing but this one line (the one-`<div>`-per-line shape), so the boundary is `el`'s **own** position within *its* parent — which is what makes `el` (the whole line-`<div>`) the unit that gets replaced, matching the earlier-established nested-fold behavior. This is also why the collapse-hiding CSS rule (above) can't assume the resulting `.code-block` always ends up wrapped in a `.fold-body` — the `<br>`-lines case leaves it as a direct sibling of `.fold-head` instead, by design, which is in turn why `.fold-block > .code-block/.code-embed` needs its own `margin-left:20px` to line up with `.fold-body`'s `padding-left`.

**A "line separator" is not just `<br>`** (`isLineSeparator()`): it also counts `<img>`, `<hr>`, any `BLOCK_TAGS` element, and existing `.code-block`/`.code-embed` boxes. These contribute **zero characters** to the flattened text, so in string coordinates they collapse onto the same position as whatever surrounds them — but every one of them renders as its own `display:block` line and, more importantly, is content that must not be deleted. This was a live data-loss bug: real saved posts contain `<div class="fold-body"><img>```</div>` (image inserted into a fold, then backticks typed immediately after, with no `<br>` in between). Scanning backward for `<br>` alone found nothing, fell through to the "replace the whole `el`" branch, and **deleted the image along with the fence line** — silently, at render time, on every view. Counting `<img>` as a separator makes the boundary land right after the image instead. When touching this scan, remember the invariant is "don't cross anything that occupies its own line," not "find a `<br>`."

If two pairs' line-ranges would overlap (only possible if a closing fence and the next block's opening fence somehow land on the exact same line, which normal typing doesn't produce), the earlier one is left as plain text rather than risking a corrupt range — same "if unsure, don't touch it" fallback as an unpaired fence.

**ARCHIVE write modal (`#modalArcWrite`) fills available height with flexbox** (`display:flex;flex-direction:column`, plus `.arc-editor{flex:1 1 auto;min-height:160px;max-height:none}`) instead of giving the editor a fixed `max-height`. A fixed px cap (previously 320px, copied from `.log-editor`) meant a post with a large image made only the editor scroll internally (correct, per the "ARCHIVE 글쓰기 모달 스크롤" requirement) but left the *edit* modal much shorter overall than the *view* modal — since only `.arc-editor` was capped, not the modal around it. With flex, `.arc-editor` absorbs whatever room the fixed-size chrome (title, category, toolbar, attachments, buttons) doesn't need, up to the inherited `88vh`, so a large-image post's edit modal now reaches the same height as its view modal, and a short/blank post's modal still sizes naturally to its content (flex-grow has nothing to distribute when total content is already under `88vh`) rather than stretching into a mostly-empty box.

**That flex rule must stay scoped to `#modalArcWrite`** (`#modalArcWrite .modal.wide.arc-modal{…}`) — **`#modalArcView` reuses the very same `.modal wide arc-modal` class list**, so an unscoped `.modal.wide.arc-modal{display:flex}` silently reformats the read-only view modal too: `.arc-view-content` becomes a flex item, gets shrunk instead of laying out at full height, and the modal's own `overflow-y:auto` stops being what scrolls. The two modals are meant to scroll differently — **view scrolls as one window** (plain `.modal` block layout, the default), **edit scrolls inside the body box only** (flex, so the surrounding chrome stays pinned while typing). Verify both when touching `.arc-modal`: view should report `display:block` with `modal.scrollHeight > modal.clientHeight`, edit should report `display:flex` with the modal *not* scrolling and `#arcContentEditor` scrolling instead.

**Changing the body font can make symbols vanish, and fallback will not save you.** KoPub 돋움 contains `⇄`, `‹`, `›` and `⋮` as *empty* glyphs — present in the font, zero advance width, nothing drawn. Because the character is technically covered, the browser never falls through to the next family in the stack, so the RELATIONSHIP arrow, both lightboxes' prev/next arrows and the kebab buttons all silently disappeared. The fix is a targeted `font-family:system-ui,'Segoe UI Symbol',sans-serif` on exactly those elements (`.rel-icon`, `.lb-nav`, `.arc-lb-nav`, `.arc-kebab-btn`, and the image toolbar's flip button). **After any font swap, sweep for this**: walk every text node plus `[placeholder]`/`[title]`/`[value]`, keep the non-Hangul/ASCII characters, and measure each one's width in the new face against `sans-serif` — anything measuring 0 in one and non-zero in the other is broken. 37 characters were in play here and exactly those four failed.

**A font swap also knocks every single-glyph icon button off centre, and `align-items:center` is what betrays you.** Flex centring centres the *line box*, not the ink, and the line box is built from the font's ascent/descent — KoPub 돋움 is 0.85/0.25 em where 조선굴림체 was 0.86/0.14. The extra descender room parks the glyph high. Two facts make this tractable:
- **`line-height` is not the knob.** Under `align-items:center` the baseline lands at `contentCentre + (ascent − descent)/2`, which contains no `line-height` term — changing it does nothing. The knob is `padding-top`/`padding-bottom`, and because the boxes are fixed-height `border-box`, **a padding of N moves the glyph N/2**.
- **Chrome quantises the used ascent/descent to whole pixels at small sizes**, so the pure-metrics prediction can be a full pixel out. Measure the rendered result, don't compute it.

Measure like this: append a zero-height `inline-block` next to the glyph (**inside a `<span>` wrapping the text** — a bare append to a flex button becomes its own flex item and reads nonsense) and its bottom edge is the exact baseline; get the ink extents from canvas `measureText().actualBoundingBox*` at ~1000px and scale down; compare the ink midpoint with the box midpoint. The corrections currently in the file, all derived that way (positive = the glyph was sitting high): `.rt-toolbar button` +1.2 (with `:has(.rt-ico)` excluded — the alignment icons are SVG and already exact, and `[data-cmd="blockquote"]` needs a further +2.4 because `❝` is drawn at the top of the line by design), `.code-block-copy` +2.25, `.gallery-fab.gallery-add` +0.6 / `.gallery-select-toggle` −1, `.lb-nav`/`.arc-lb-nav` −3.5 (those two are the worst because `system-ui`'s ascent/descent split is even more lopsided than KoPub's). The phone block re-states the toolbar value scaled to its 14px font. **Every one of these numbers is font-specific — re-measure them all after any font change.**

**The lightbox counts two ways at once, and that is the whole design.** Arrows move by **photo** (`galleryLbFlat`, built by `flattenEntries()`; `galleryLbIndex` indexes it, and the `n / total` chip counts every photo in the folder including stacked ones). The thumbnail strip moves by **entry** (`galleryLbEntries`; `lbThumbWindow()` and `lbThumbStart` are entry indices) — a stack is one 64px slot showing *the photo currently being viewed*, with a `+N` corner tag. **Its pop-out must be `position:fixed` with JS-computed coordinates** (`openLbPop`): `.lb-thumbs` carries `overflow-x:auto` for narrow screens, and an absolutely-positioned pop-out above the strip is simply clipped away — it renders but is invisible. Hidden while `.lightbox.zoomed`.

- **Moving inside a stack is a card deal, and the two directions are exact mirrors.** `dealGalleryLightbox()` (▸) flings the current photo out to the **left** (`LB_DEAL_AWAY`) while `.lb-back-1` animates from its resting transform to identity. `dealBackGalleryLightbox()` (◂) runs it backwards: it commits *first*, then brings the new main photo in from that same thrown-away position while the photo you just left — now `.lb-back-1` — sinks from identity to its resting transform. **Paper grain overlay** — `.paper-grain` is a fixed, `pointer-events:none` full-viewport layer that gives the whole page (including the red page margin) a printed-paper texture. Three things about it are load-bearing:

- **It is an `<img>`, not a `background-image`.** Texture photos routinely carry an EXIF orientation tag; `<img>` honours it in every engine, `background-image` does not, so a background version can render rotated 90°. `img/paper-grain.jpg` is also the repo's only binary asset — unlike everything else on this site it is a static file, so it is browser-cacheable and costs nothing after the first visit. It sits at the very end of `<body>` so it never blocks first paint.
- **`mix-blend-mode: overlay`, not `multiply`.** Multiply darkens every channel equally and turned the `#EF3921` page red muddy. Overlay only pushes light areas lighter and dark areas darker, so hues survive.
- **`filter: brightness()` must be re-derived whenever the texture image changes.** Overlay's no-op point is mid-grey; a texture whose *mean* luminance isn't 0.5 shifts the entire page's brightness. The filter normalizes that: `brightness = 0.5 / mean`. The current image measures 0.798, hence `brightness(.627)`. Measure a replacement (draw it to a canvas and average the luminance) and update the number — otherwise the whole site gets brighter or darker and it will look like a color-palette bug.

`--grain` in `:root` is the only strength knob (1 = full, lower = fainter); `soft-light` is the gentler alternative to `overlay` if it ever reads as too much. `z-index:50` deliberately places it above all in-page content (which tops out at 20) but **below** the mobile drawer (55–60) and every modal/lightbox (100+), so modals render clean — verified with `elementFromPoint` and by comparing z-indexes. Measured cost is zero (16.7 ms median frame time with and without). Hidden in `@media print`.

An iframe gets its own viewport, so the media queries evaluate for real. Wait for the frame's `store-ready` event before stubbing `contentWindow.SiteStore.set`; the frame's globals (`state`, `isLoggedIn`, the pagers) are **not** reachable from the parent because `main.js` is a classic script, so drive it through the DOM (click the dots, click cards) rather than by calling its functions.

Phone-specific structure worth knowing before editing:
- `.app-window` flips to `flex-direction:column`, which turns the left/right punch-hole margins into top/bottom strips with no markup change. Height is `100vh` then `100dvh` (the second line is the iOS address-bar fix; keep both).
- The sidebar becomes a fixed off-canvas drawer toggled by `#mobileMenuBtn`. z-index order is deliberate: ☰ `56` > backdrop `55`, both < drawer `60` < `.modal-overlay` `100`, so the drawer never covers a modal and the ☰ never covers the drawer.
- PAIR's detail modal takes the same phone rules as OC's now that both are page sliders: the modal fills the width and `.pd-page-dots` moves inside to `left:3px`. That puts the dots on the window's cream rather than the dark overlay, so the phone block also repaints them (inactive `--text-muted` at `.35`, active `--accent`) — white-on-cream was invisible.
- **Per-page counts in `main.js` must stay in sync with the matching grid's row/column count in CSS**, and every one of them re-renders from `initResponsiveWatch()` on breakpoint change: `galleryPerPage()` ↔ `.gallery-grid` (15 = 5 cols desktop, 9 = 3 cols phone, 6 on phones under 720px tall — row count is implicit there, so only the JS number changes between the last two); `pairPerPage()`/`ocPerPage()` ↔ `.post-grid` (8 = 4×2 desktop, 4 = 2×2 phone — **both** the JS number and the CSS `grid-template-rows` change); ARCHIVE's PROMPT grid ↔ `.arc-nai-grid` (8 = 4×2 desktop, 4 = 2×2 phone — it used to restack to 2×4 and keep the count, which made each thumbnail too small to read on a phone). `initResponsiveWatch()` also resets `pairPage`/`ocPage`/`galleryPage`/`arcPage` to 1, because a page index valid at one count can be past the end at the other. PROMPT's per-page number is read **twice** in `renderArchive` — once for the page slice and once for the locked-folder placeholder grid — so it lives in the `perPage` local rather than being written out as a literal.

**Touch input** — HTML5 drag-and-drop does not fire on touch at all, and four features depend on it (card order, profile meta rows, gallery thumbnails, folder-tab drops). Rather than rewrite them, `initTouchDrag()` in `main.js` is one delegated `pointerdown` listener that long-presses (400 ms) any `[draggable="true"]` element and then **dispatches `MouseEvent`s named `dragstart`/`dragover`/`dragleave`/`drop`/`dragend`** at the right targets. The existing handlers are plain listeners, so they run unchanged — including the gallery's dwell-on-arrow page flip. If you add a new drag site, just set `draggable="true"` and it works; don't add touch code. Elements inside `[contenteditable="true"]` are skipped so iOS text selection still works. Wheel-only interactions (Home page flip, gallery paging) got touch equivalents too: swipe handlers plus tappable `︽`/`︾` arrows (`pointer-events` is opened up on phones only — their tap padding is horizontal-only so it can't cover the first thumbnail row).

**Sidebar music widget** — the old name/bio block is gone from the sidebar; `state.profile` is still loaded and saved, so restoring the markup would bring the text back. In its place a widget drives a YouTube IFrame player: `musicList` (a new `SCALAR_KEY`, `[{id, videoId, title, artist}]`) holds the playlist, while **volume lives in `localStorage`, not Firestore** — it is a per-device preference and syncing it would change the volume on her other machines. Two things are easy to get wrong here:
- **The player element must stay inside the viewport.** `display:none` or `left:-9999px` makes Chrome treat it as not worth rendering and playback sticks in `BUFFERING` forever. `#ytHost` sits at the bottom-left corner at its real 200×150 with `opacity:0`.
- **There is no autoplay.** Browsers block sound without a user gesture, so the first song is `cueVideoById`'d (loaded, paused) and waits for ▶. Don't "fix" this with `loadVideoById` on boot — it just fails silently and looks broken.
`musicVolume()` guards `raw == null` explicitly because `Number(null)` is `0`, not `NaN` — reading the unset key straight through silenced the widget on first visit.

**The LP is a progress ring.** It began as line art with one asymmetric arc (`.mb-lp-glint`) whose only job was to make the rotation visible — a perfectly symmetric disc spinning looks completely static. That arc is now `.mb-lp-prog`, a circle whose `stroke-dashoffset` runs from the full circumference down to 0 as the song plays, so it reads as elapsed time *and* still breaks the symmetry. It sits at `r=24`, i.e. **on top of an existing groove one line inside the outer rim** rather than in the gap next to the rim where it started. Three things it depends on:
- **The circumference is written twice** — `stroke-dasharray:150.8` in CSS and `LP_PROG_LEN = 150.8` in `main.js`. Change the radius and both must move (`2π × r`).
- **`transform="rotate(-90 30 30)"` is on the circle, not the SVG**, so the ring starts at 12 o'clock while the whole SVG keeps spinning (`.mb-lp.spinning`). Putting it on the SVG would fight the spin animation.
- **`resetLpProgress()` clears the ring with the transition switched off** before a new song loads; without it the `.5s` transition plays the ring *backwards* every time you skip. It is called from `loadCurrentSong` only when the song actually changed.

**The song name marquees instead of ellipsizing.** `setMarqueeText(box, text)` puts the string in an inner `.mb-mq` span and `applyMarquee(box)` compares `inner.scrollWidth` against `box.clientWidth`; if it overflows it writes `--mq-dist` and an `animation-duration` and adds `.scrolling`, which slides the span left by exactly the overflow, pauses, and slides back (`@keyframes mb-marquee`, ~16px/s). Two details: the measurement is repeated on a **700 ms `setTimeout`** because a webfont arriving late changes the text width and `requestAnimationFrame` never fires in a background tab, and `.mb-title`/`.mb-artist` must keep `overflow:hidden` with **no `text-overflow`** — an ellipsis and a marquee cancel each other out.

**The playlist (`#mbPlaylist`) is an in-flow accordion inside `.music-block`, not a floating panel.** It was tried as a `position:fixed` pop-out first (anchored beside, then under, the widget) and rejected: the owner wants it to **push the menu down** rather than cover it, with no border or shadow so it sits on the sidebar's own ground. That means there is no placement code at all — the DOM order does the work, which is also why it must live *inside* `.music-block` rather than as a sibling (the block's `padding-bottom:26px` is the gap to the menu, and a sibling would add the sidebar's own 16px flex gap on top).

Two numbers are linked: `.mbp-list{max-height:104px}` shows exactly five rows, where a row is `3 + 14 + 3 = 20px` and four `1px` hairlines sit between them (`.mbp-item + .mbp-item{border-top}` — between only, never after the last). **Change the font size or the row padding and that 104 has to be recomputed**, or you get a clipped sixth row instead of a clean five.

Opening runs `@keyframes mbp-drop` (`max-height 0 → 116px`, opacity, `translateY(-8px) → 0`) so it reads as coming down from above. It has to be an **animation, not a transition** — the element goes from `display:none`, and a transition cannot run on the frame an element starts being rendered. The 12px gap above the list is `padding-top` rather than `margin-top` for the same animation: margin sits outside `max-height`, so the menu would jump that 12px before the list started opening. (Testing note: toggling the class off and on in one synchronous block produces **no** animation at all — Chrome sees no net class change. Let a frame pass in between or you will think it is broken.)

Only the LP and Escape toggle it. An outside-click-to-close listener was removed when it stopped floating: clicking a menu item would collapse the list and yank the whole nav upward mid-click. Rows show a zero-padded number (`.mbp-no`) before the title. The list is read-only by design — reordering and deleting stay in the 노래 관리 modal — and clicking a title jumps to that song, loading before rendering for the same reason `stepMusic` does (a render-time `cue` would overwrite the play request).

**Reordering in 노래 관리 is a live FLIP, and its handlers must not close over the index.** `dragover` moves the row with `insertBefore` and replays `flipByKey`, `dragend` reads the order back out of the DOM — re-rendering mid-drag would destroy the dragged node and `dragend` would never fire, exactly like the sidebar categories and the gallery. Because nothing re-renders until the drop, the ✕ button resolves its song by `s.id` rather than by position, and `dragend` re-finds the playing song by id so it keeps playing from its new slot.

**Write batching** — `main.js` calls `storageSet` very frequently (e.g. on every `input` blur). `firebase-store.js` debounces actual Firestore writes (~1.2s), diffs against the last-saved JSON per document so unchanged items aren't rewritten, and only marks a change as "saved" after the write actually succeeds (a failed write keeps the key `dirty` and retries automatically) — this was a deliberate fix for a bug where failures were recorded as successes and silently dropped edits.

**List order is a separate field and needs its own diff.** Array order is carried by `__order` on each doc, written in `flush()` and re-applied by the `.sort()` in `loadAll()`. But `savedJson` — the per-doc change detector — stores `stripMeta(it)`, which deletes `__order`. So **reordering a list changed no document's JSON and wrote nothing**: HOME card drags reverted on reload, and PAIR/OC lists drifted out of creation order (only items whose *content* also changed ever got a fresh `__order`, so the rest kept stale numbers — that drift is what `byNewest()` was papering over). Fixed with a parallel `savedOrder` map, populated in `loadAll()` from the post-sort index and compared alongside the JSON: `if (savedJson[sk] !== json || savedOrder[sk] !== i)`. It is assigned from `nextOrder` only after the batch commits and dropped with `dropSaved`, exactly like `savedJson`. **Any future per-doc metadata that lives outside the stored JSON needs the same treatment** — if it isn't in the compared string, changing it alone is invisible to the diff.

**Save-state visibility** — `SiteStore.onSaveState(cb)` fires `'saving' | 'saved' | 'error'`; `main.js` renders this as a fixed indicator (bottom-right) via `initSaveIndicator()`. Don't reintroduce silent failure here — if you touch the flush/retry logic in `firebase-store.js`, make sure errors still propagate to this indicator rather than only `console.error`.

**Signing in happens on the HOME postcard, not in a modal and not in the sidebar.** The old `.login-widget` (LOCKED/UNLOCKED badge + 로그인 button) and the `#modalLogin` overlay are both gone. What replaces them:
- **One text button does all three jobs**: `#postcardBtn`, 조선일보명조, `--accent`, no border or fill. Signed in → sign out. Signed out with the sheet closed → open it. Signed out with the sheet **open → it is the submit button**; there is no LOGIN or 취소 inside the box. Its label *is* the state readout, which is why the badge could be deleted: **Write a Postcard** / **Send a Postcard** (and `Sending…` while `signOut()` is in flight, since a backed-up flush can take seconds). `applyEditMode()` sets it.
- **It is `position:absolute; top:100%` under `.intro-card`, not in the card's flow.** The card is vertically centred in `#home-intro-page`, so a button in normal flow pushed the postcard up by half its height — the owner noticed immediately. Out of flow, the card centre is byte-identical to before the button existed (measured: page centre 611.5, card centre 611.5).
- **`#loginSheet` covers the postcard exactly** (`inset:0` on the card, `padding:0 24px` so the box's width equals the banner's) and opens in place rather than as an overlay — the ask was for it to feel like moving to a login page. Measured: box top/height identical to `.intro-card`, left/width identical to `.intro-banner`. `.intro-card` gets `.login-open`, which hides its other children with **`visibility:hidden`, never `display:none`**: the card must keep its height or the box is the wrong size and the page twitches. The **postcard button is excluded from that rule** (`:not(.postcard-btn)`) because it is the submit control, and for the same reason the outside-click-to-close handler must skip it — otherwise the `mousedown` closes the sheet before the `click` can log you in.
- **The border draws from two opposite corners.** `.ls-box` has no `border`; four absolutely-positioned `.ls-line` spans scale from 0 — top and left from the **top-left** corner, bottom and right from the **bottom-right** — and `.ls-inner` fades in (opacity only, no rise) on a `.42s` delay once they have nearly met. Same `display:none` rule as the playlist: these are animations, not transitions. The easing is `cubic-bezier(.4,0,.2,1)` rather than the site's usual `(.22,1,.36,1)`, which was 96% drawn at the halfway point and looked like the lines simply appeared.
- **Closing replays the same animations backwards, and the keyframes must have different names** (`ls-draw-x-r` / `ls-draw-y-r` / `ls-fade-r`, played with `animation-direction:reverse`). This is the whole trick: if the closing rules reuse the *opening* animation's name and only change direction, Chrome does not start a new animation — it **updates the running one in place and keeps its `currentTime`**. The opening animation has long since finished, so that time is past the end, and flipping direction there jumps straight to the start pose instead of rewinding. It shipped that way once and looked like no animation at all. Duplicated keyframes going 0→1 plus `reverse` (rather than hand-written 1→0 keyframes) keep the easing curve an exact mirror.
- **The postcard fades back in afterwards** (`.intro-card.login-back`, opacity only). Removing `.login-open` alone snaps the hidden content back into place. `#postcardBtn` is excluded from both rules — it stays visible the whole time, so fading it would make it blink.
- **`closeLoginSheet()` must not clear its own timer when it is already closing.** A successful login calls it **twice**: the auth listener fires *during* `signIn()`'s await, so `applyEditMode()` gets there first and starts the close, and then `submitLogin()` calls it again. The early-return for "already closing" originally sat *after* `clearTimeout`, so the second call cancelled the timer that removes `.open`/`.login-open` — the sheet animated to invisible and the postcard stayed hidden behind it, leaving a blank white page until you navigated away and back. Clear the timers only on the path that actually re-arms them.
- Closing: Escape, or a `mousedown` on `#home-intro-page` outside both `.ls-box` and `.postcard-btn`. While it is open the HOME wheel/swipe page flip is suppressed, or scrolling would carry you to the cards page mid-login. `markCurrentView()` also closes it with `closeLoginSheet(true)` (no rewind — it is off-screen by then) so leaving for another menu and coming back shows the postcard, not a stale login box.
- **The layout is a postcard back**: EMAIL top-left, PASSWORD bottom-right, an empty perforated stamp top-right, `img/postmark.png` (the owner's own artwork, colour untouched) rotated `-9deg` across it, and a faint vertical rule down the middle. `column-gap` is **twice** `.ls-box`'s horizontal padding so the two fields sit as far from the centre rule as from the outer edge. The postmark is a raster on a white background, so it carries `mix-blend-mode:multiply` to drop the white and leave the ink — **do not "fix" this by recolouring or redrawing it.** Fields are three ruled lines each (`.ls-input` + two `.ls-rule`, all 26px) rather than boxes; the phone block drops the decorative rules, the stamp, the postmark and the divider, because the box there is only as tall as the postcard (~198px).
- `.login-error` and `.login-modal` are **still used** by the folder and folder-unlock modals — don't delete those rules along with the login markup.

**Auth model** — Firebase Authentication (email/password), not the old hardcoded `CREDENTIALS` object (removed). `window.SiteStore.isAdmin` is true only when the signed-in user's UID matches `ADMIN_UID` from `firebase-config.js`; the client-side check is a convenience, the Firestore security rules in `firestore.rules` are the actual enforcement point. `js/main.js`'s login modal collects an email (not a username) — see `loginErrorMessage()` for the mapping from Firebase auth error codes to Korean UI messages if you need to add a new one (e.g. new failure codes from console changes like unauthorized domain).

**GitHub Pages deployment** — this repo must be named exactly `xngsuii.github.io` to serve from the domain root (user site, not project site); renaming it changes the site URL, and Firebase's authorized-domains list (console → Authentication → Settings) must contain whatever domain the site is actually served from or login will fail with `auth/unauthorized-domain`.

## Terminology

The user may refer to the two UI states by their badge labels:
- **LOCKED** = 보기 모드 (view mode) — visitor state, nothing editable
- **UNLOCKED** = 편집 모드 (edit mode) — admin signed in, `body.logged-in` is set and `[data-editonly]` controls appear

## Cache busting

`index.html` references its assets with a version query — `css/style.css?v=N`, `js/main.js?v=N`, `js/firebase-store.js?v=N` (and `firebase-store.js` imports `./firebase-config.js?v=N`). **Bump every one of those `N`s together whenever you change a CSS or JS file.** GitHub Pages serves the HTML with a short cache but assets with a long one, so without a bump a returning visitor gets new HTML with stale JS — and since `main.js` wires up elements at top level, a mismatch used to kill the whole script. The top-level init blocks now bail out politely when their elements are missing, but that only degrades gracefully; it does not make the page correct. The version bump is the actual fix.

## Workflow notes

- **Do not commit without testing first, and confirm with the user before committing.** Since there's no automated test suite, "testing" means actually loading the page (local server or the live site) and exercising the change in a browser — check the console for errors and confirm the save indicator behaves correctly for anything touching storage.
- **When a change touches color** (CSS colors, inline styles, color pickers, theme variables in `:root`), always print the affected HTML color codes (hex/rgba) in the response, not just describe the color.

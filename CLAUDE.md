# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A single-page personal "home" site (Korean: 갠홈) — a static HTML/CSS/JS app with no build step, deployed via GitHub Pages at `https://xngsuii.github.io/`. Data (profile, cards, pair posts, archive, images) lives in Firestore instead of localStorage, so edits persist across reloads, browsers, and devices; only the admin account (Firebase Authentication) can write.

There is no package.json, no bundler, and no test runner — the site is plain files served as-is.

## Commands

There is no build/lint/test tooling in this repo. To preview locally:

```
py -m http.server 8790
```

then open `http://localhost:8790/`. Serve over HTTP (not `file://`) — the app loads `js/firebase-store.js` as an ES module and needs a real origin for Firebase Auth persistence and CORS.

There are no automated tests. Verify changes by loading the page in a browser and checking the browser console for errors — do this before committing (see Workflow notes below).

## Architecture

**File layout** — everything is hand-split from what used to be one monolithic HTML file:
- `index.html` — markup only
- `css/style.css` — all styles
- `js/main.js` — UI logic and rendering (view switching, cards, pair posts, archive, image adjuster widget, rich-text editing)
- `js/firebase-store.js` — the persistence layer (see below)
- `js/firebase-config.js` — Firebase project config + `ADMIN_UID` (safe to be public; not a secret — see Security model)
- `audio/click.mp3` — the click sound (a static file served by Pages, not Firestore; see "Click sound")
- `firestore.rules` — Firestore security rules (read: public, write: admin UID only); must be pasted into the Firebase console manually, this repo file is not auto-deployed

**Storage adapter contract** — `main.js` never talks to Firestore directly. It only calls `storageGet(key, fallback)` / `storageSet(key, value)` (defined in `main.js`, thin wrappers around `window.SiteStore`). All Firestore-specific behavior (chunking, image extraction, debouncing) lives entirely in `firebase-store.js` behind that same `get`/`set` shape. When adding a new piece of persisted state, add its key to `SCALAR_KEYS` (single doc field) or `LIST_KEYS` (one Firestore doc per array item, keyed by `item.id`) in `firebase-store.js` — don't invent a new storage path in `main.js`.

**Why data is split across documents** — Firestore caps documents at 1 MiB. `cards`, `pairPosts`, and `archive` are arrays that could grow large, so each array item is stored as its own document under `site/main/<key>/<id>` instead of one big array field. Small scalar fields (`profile`, `siteName`, `homeIntro`, `homeBanner`, `archiveSeqCounter`) live together in the single `site/main` doc.

**Image/blob handling** — Images are still authored as data URLs in `main.js` (via `fileToDataUrl`, which now actually calls `SiteStore.compressImage` — resizes to a max dimension and re-encodes under a target size).

**`compressImage` must never flatten a transparent image**, and the check is "does it actually have holes", not "is it a PNG". JPEG has no alpha channel, so a background-removed sticker came back with a white rectangle behind it. The old logic was *try PNG, and if it exceeds `targetChars` fall through to JPEG-on-white* — and since PNG has no quality dial, anything but a small image took that branch. Now `hasTransparency(bmp)` samples the bitmap at 240px (any real hole averages down below alpha 250) and, when it finds one, encodes **WebP** with the same quality-stepping loop plus a dimension fallback — WebP keeps alpha *and* has a quality knob. `canEncodeWebp()` feature-detects once and falls back to plain PNG with dimension reduction. A PNG that turns out to be opaque still goes to JPEG, which is what makes screenshots-saved-as-PNG cheap. **Images uploaded before this fix are already flattened in Firestore** — the blob is a JPEG; re-uploading is the only repair. Before any save, `firebase-store.js` walks the value (including `data:` URLs embedded inside rich-text HTML fields) and pulls each one out into `site/main/blobs/<sha256>`, replacing it in place with a `blob://<hash>` reference; large blobs are split into `parts` sub-documents to stay under the size cap. On load, references are inflated back into real data URLs before `main.js` ever sees the data — the UI layer is unaware this happens. Same-hash images are automatically deduplicated. Unreferenced blobs are garbage-collected after the blob index arrives (only when logged in as admin, and only if there are no unsaved local changes — see `collectGarbage`). GC decides what to delete by scanning `savedJson` for `blob://` refs and removing everything in `knownBlobIds` that isn't there; the blob index only supplies the *candidate* list, so an incomplete index makes it delete **less**, never more. Do not invert that.

**Blobs load lazily — `blob://` refs stay in the data.** This is the single most important thing about the storage layer. Images are ~99.9% of this site's payload (measured: 984 blobs / 1000 chunks, against **0.09 MB** for every post, card and folder combined). `loadAll()` used to fetch all of them, one chunk at a time, *before* the first render — first paint took 23–28 s. It now fetches only `site/main` + the four list collections (~0.2 s), sets `loaded`, and returns; blobs are fetched **on demand**, 6 at a time (measured 2.8× faster than serial) via a priority queue.

**Read quota is the binding constraint, and every Firestore document is one read.** The Spark plan allows 50,000 reads/day; exceeding it suspends the project until midnight Pacific (16:00 KST). Two things used to blow it:
- `loadBlobIndex()` did `getDocs(blobs)` to learn each blob's chunk count — **one read per photo**, 984 of them on every single page load.
- After the first paint it queued *every* blob (`blobQueue = [...first, ...rest]`), so opening HOME downloaded the whole gallery — another ~1000 reads and several hundred MB.

Together ≈ **2,080 reads per visit**; twenty-four page loads exhausted the day. The three fixes, in order of size:
1. **Only fetch what was asked for.** `startBlobQueue()` seeds the queue from `blobWanted` alone. Everything drawn already registers demand through `whenImgArrives`/`applyThumbBg`, so nothing needs a manual prefetch to appear — if you add a render path that sets `img.src`/`background-image` from `imgUrl()` and *doesn't* register, that image now stays blank forever instead of arriving eventually. `.an-img` in the ARCHIVE grid was exactly that case and had to be fixed.
2. **The chunk table rides along on `site/main`.** `meta.blobIndex` is `{blobId: chunkCount}` (36 KB for 984 photos; the 1 MiB doc cap is ~25,000 photos away), so it costs **zero** extra reads — `loadAll()` has already fetched that document. `writeBlob()` returns its chunk count and `flush()` merges the new entries in one `setDoc(..., {merge:true})`; nested-map merge means other photos' entries are untouched. `collectGarbage()` removes entries with `deleteField()` **per id it actually deleted** — never rewrite the whole map, or a photo uploaded from another device disappears from the table.
3. **Photos are cached in IndexedDB** (`siteBlobs`, stores `blobs`/`stat`, 350 MB budget, oldest-first eviction). A blob id *is* the SHA-256 of its content, so a cached entry can never be stale — no expiry, no revalidation. Second and later visits fetch **no** photo documents at all.

**`meta.blobSizes` is the chunk table's twin, and it exists only so the sidebar gauge can be honest.** `blobIndex` stores *chunk counts*, which say nothing useful about volume — one chunk is anywhere from 1 to 700,000 characters, so estimating from it is off by a factor of hundreds of MB. Each blob's head document carries `len`, so `ensureBlobSizes()` builds `{blobId: charCount}` from one admin-only collection scan when the field is absent (~1,076 reads, once, then never again), and from then on `flush()` merges new entries beside `blobIndex` and `collectGarbage()` deletes from both in the same `setDoc`. **The two tables must keep identical lifecycles** — write to one without the other and the gauge drifts from reality with no way to notice. `storageStats()` sums that table plus the length of every entry in `savedJson` plus 90 bytes per photo for the two tables themselves; nothing is re-fetched. Data URLs are base64, so characters are bytes. The result is a slight *under*estimate (Firestore also charges for document names and index entries), which is the right direction for a "how full am I" readout.

**The blob index is an optimisation, never a source of truth.** `readBlob(id)` falls back to `getDoc(blobs/<id>)` for its chunk count when the id isn't in the table, so a missing, stale or half-written index costs an extra read per photo and nothing else. Keep it that way — the older code filtered unknown ids out of `wantBlobs()`, which meant any drift silently made photos un-loadable. `ensureBlobIndex()` builds the table from a full collection scan exactly once, admin-only, and only when `meta.blobIndex` is absent.

Result per visit: **~2,080 reads → ~126 first visit, ~96 on return** (the ~96 is one meta doc plus one per post/card — see "list order" below if you want that lower too).

Consequences you must respect:
- **`inflate()` is no longer applied at load.** `cache` — and therefore `state` in `main.js` — holds `blob://<id>` strings, not data URLs. Anything that draws an image must go through `SiteStore.resolve()` (`imgUrl()` in `main.js`), which returns `''` for a blob that hasn't arrived.
- **Never write `''` into the data in place of a missing image.** `deflate()` passes `blob://` through untouched (it only rewrites `data:`), so a save round-trips byte-identically whether or not the blob has loaded — but an empty string would be saved as an empty string and the image would be gone forever. This is why `resolve()` is a read-time lookup and not a mutation.
- **Editors must `await SiteStore.ensure(value)` before filling, and honour its answer.** `fillLogEditor()` and `openArcWriteModal()` do; they read the editor back out on save, so filling them with unresolved refs is exactly the data-loss case above. `ensure()` jumps the queue and resolves in well under a second for one post, but it **returns `false` on timeout** — both call sites then close the modal and say so rather than opening an editor over blank images. Do not "simplify" that back to an unchecked `await`.
- Everything else paints optimistically and repairs itself: `whenImgArrives(value, el, redraw)` parks a redraw closure, and `SiteStore.onBlobs` → `flushPendingPaints()` runs it when the blob lands (dropping entries whose element left the DOM). **Repaint the element, never re-render the view** — a full re-render moves the caret while the user is typing. `applyThumbBg()` self-registers, so any caller of it is already covered; anything that sets `img.src` or `background-image` directly needs its own `whenImgArrives`.
- **`SiteStore.prefetch(value)` now downloads, it no longer merely reorders.** While every blob was being fetched anyway, passing a whole post to it was free — it just moved things up the queue. Now it *is* the fetch, so scope every call to what is actually on screen. `openPairDetail`/`openOcDetail` use `prefetchDetailImgs()`, which strips `galleryFolders`/`gallery`: passing the raw post pulled 138 photos for one character (measured 167 in flight) where 12 were visible. The lightbox uses `prefetchLbWindow()` (2 back / 5 ahead, re-run on every paint) instead of the whole folder — 63 photos down to a handful. The grid page, the thumb strip and the pop-out all self-scope already.
- `blobIdsIn()` and `inflate()` both short-circuit on `data:` strings — they run on every paint, and scanning a 400 KB data URL for refs each time is visible.
- `SiteStore.blobStats()` drives `initPhotoIndicator()` (bottom-left, mirrors the save indicator). `total` is now **outstanding demand** (`loaded + queued + in-flight`), not the site's photo count — with on-demand loading there is no meaningful "all photos" figure. The indicator therefore hides and re-appears repeatedly as you browse, so its fade-out timer must be **cancelled** when new work arrives; leaving it latched pinned the indicator open forever after the second burst.
- A blob that fails is retried twice then dropped (`BLOB_TRIES`), because the old unconditional 4-second retry loop would hammer a missing document forever and burn quota with nobody watching. Any *fresh* demand through `wantBlobs()` clears the failure count, so a user action always gets a full set of retries.

Result: first paint **0.4 s** (was 23–28 s), and a visit costs ~126 reads / a few MB instead of ~2,080 reads / hundreds of MB. Moving image bytes to Firebase Storage or a CDN would be better still, but needs a paid plan and is deliberately **not** done.

**Thumbnail rendering** — stored images are ~800–1800px, but most places display them at 60–430px. Drawing a 830px source into a 124px box makes Chrome downscale ~7x in one pass, which visibly aliases ("계단 현상"). `downscaleThumb`/`applyThumbBg` in `main.js` build a **display-only** variant by halving on a canvas until close to the target, cached per (source, 64px bucket); the target is `display width × devicePixelRatio × 1.25`, and sources that aren't at least 1.25x larger than that are left alone. `state` always keeps the original, so full-size views and the zoom/pan adjuster are unaffected. If thumbnails still look rough, fix the downscale path — **do not raise `compressImage`'s `maxDim`**, which only inflates storage and makes the ratio worse. Callers pass a fixed `boxPx` for fixed-size boxes and omit it to have the element measured (with a short retry, since hidden views report width 0). Note `requestAnimationFrame` never fires in a background tab, so this code deliberately uses `setTimeout` to wait for layout.

**The site is one typeface: Pretendard Variable, and hierarchy is made with weight and size only.** `--mono` is `'Pretendard Variable', Pretendard, 'Segoe UI Symbol', system-ui, sans-serif`, and `--font-gm` / `--font-free` / `--font-chosun` / `--pixel` / `--name-font` are all **aliases of it** — the names survive only because rules all over the file call them, so use `--mono` in anything new. It replaced four faces assigned slot by slot (KoPub 돋움 / G마켓 산스 / 프리젠테이션 / 조선일보명조); that table used to live here and was deleted at the owner's request once she decided she would not go back. **Do not reintroduce per-slot faces, and never split scripts automatically** (an early version pulled Latin from one face and Hangul from another with `unicode-range` — it was reverted, and the reason still holds: she wants to see one decision, not a rule that guesses).

Two consequences of the swap are load-bearing and documented where they bite: **the fallback for symbols Pretendard doesn't carry must be pinned by hand** (see "Changing the body font can make symbols vanish" below), and **the weight axis is real**, so a thickening can be animated — 45–920 continuous, loaded from the jsDelivr dynamic-subset CSS in `index.html`. Weight is set with `font-variation-settings:'wght' N` (with `font-weight` alongside it where a non-variable fallback might land), not by picking a named cut. `--name-font`'s one call site (`.pd-name-input`) pins 800.

**`.modal h3`'s `letter-spacing:.04em` is for the English/uppercase headings only.** It was chosen for titles like `LOG` and `GALLERY`; on a Korean heading it reads as visibly loose next to every other Korean string on the site. Each Korean modal title therefore opts out by id — `#modalMusic h3` (노래 관리) and `#logWriteHeading` (게시글 작성 / 게시글 수정) both restate `letter-spacing:0`. **A new modal with a Korean `<h3>` needs the same line**; the owner has now pointed this out twice.

**Anything new goes on `--mono`.** This is an explicit standing instruction from the owner, given back when new windows and controls were arriving with three faces mixed together at the author's discretion. When you add a feature, a modal, or a control, put **every** string in it on `--mono` and say so in the hand-off; she will look at it and name the exceptions herself. Do **not** pick a face because it seems to suit the slot.

**Sidebar emphasis is text-only, which has three non-obvious costs.** Hover/current state is `color:var(--accent)` plus a thickening with **no background box**, so (a) the resting weight is light — `'wght' 300`, going to 800 on hover/active; starting heavy leaves nowhere to go and reads as a colour change only — and (b) `.nav-item`/`.nav-sub-item` carry a **fixed `height`+`line-height`** (27 / 26, `.nav`'s gap 0), because bold text is a hair taller and without it every hover nudged the items below by a pixel. Row spacing is therefore changed by moving those heights, not by padding — the phone block's vertical padding had to be dropped to `0` when they came down from 34/28, because 13px of padding on a 25px box makes the box 26px and the two menu levels stop lining up. The "you are here" bold on a sub-category is scoped by `body[data-view=…]` (set by `markCurrentView()`), not by `.active` alone: each menu keeps its own `.active` child, so styling `.active` directly left PAIR's last-picked category bold while you were looking at OC.

And (c) **the thickening is the real weight axis (`font-variation-settings:'wght'`), and the old fake-bold trick must not come back.** The owner asked for it to *animate*, which the previous face could not do: G마켓 산스 ships only 500 and 700 and is not variable, so CSS font-matching snapped anything above 500 straight to the 700 cut and the change landed in a single frame. The workaround then was to grow `-webkit-text-stroke-width` from `0 → .55px` instead. **Pretendard Variable is variable (45–920), so that workaround is now both unnecessary and worse** — a stroke is fake bold, and on Hangul it fills in the counters. The CSS says so at `.nav`'s comment; don't reintroduce it. All six selectors must move together (`.nav-item`, `.nav-item.active`, `.nav-item-row:hover .nav-item`, `.nav-sub-item`, `.nav-sub-item:hover`, and the three `body[data-view=…] … .active` rules); leaving one at a different weight makes that item jump while its neighbours fade.

**LOG is a masonry card grid on desktop and a plain table on phones.** Below 769px `renderLogList()` renders `.log-table-scroll` > `table.log-table` — the same markup and CSS as ARCHIVE's OOC/ETC — instead of cards; three columns of thumbnails at 393px made each card thumbnail-sized and the preview photo ate the screen, so the owner asked for the old row list back there. Only two spots branch on `asRows` (`isMobileWidth()`): which HTML is written, and whether the per-item binder is hung on `tr[data-abs]` or on `.log-card[data-abs]`. Click, select mode (the `.arc-td-check` column), folder drag and pagination are one shared `bindItem()` closure and are identical in both. `layoutLogCards()` runs only in the card branch, and `initResponsiveWatch()` re-renders the open detail screen's LOG on a breakpoint change because the two shapes are not interchangeable. **The two branches also page differently**: cards stay at a flat `LOG_PER_PAGE = 10` (they scroll inside `.log-cards-scroll` anyway), while the table row count is *measured* by `fitLogRows()` — the same trick as ARCHIVE's `fitArchiveRows()`, and for the same reason (phone heights vary, a fixed count either overflows or leaves the bottom empty). Everything below is about the card branch.

`renderLogList()` draws 10 cards (`LOG_PER_PAGE`) into `.log-cards`, and `layoutLogCards()` absolutely positions each one into whichever of three columns is currently shortest. CSS `column-count` was rejected on purpose: it reads top-to-bottom within a column, so the newest post would not sit top-left and the second-newest would land under it rather than beside it. Consequences worth knowing:
- **A card in a hidden pane measures 0 and cannot be laid out.** LOG lives behind a tab in both hosts, so it is *usually* hidden when first drawn. A short retry loop used to cover this and would simply give up if the user opened the tab later — leaving every card stretched to full width. There are now two paths: a `ResizeObserver` on `.log-list` (survives re-renders, and its own height is pinned by the parent so writing the grid height back doesn't re-trigger it), **and** an explicit `relayoutLogCards()` from the PAIR tab click and `setOcPage()`. Keep both — a background tab renders no frames, so the observer never fires there.
- **Never set `img.src` to the empty string.** A post's first image replaces the preview text, but the blob may not have arrived, and `imgUrl()` returns `''` for that. Assigning it fires `error` immediately, which collapsed the thumbnail before the photo could land. `draw()` now assigns only a non-empty URL and `whenImgArrives` fills it in later; `error` genuinely means a broken image.
- **The grid keeps a trailing gap below the last row.** `grid.style.height` is `Math.ceil(max(colH))` — the row gap is deliberately *not* subtracted. Subtracting it put the lowest card's bottom edge exactly on the scroll container's edge, and since card heights are fractional while `offsetHeight` is an integer, the last card looked clipped at full scroll.
- **Hover changes the border colour and drops a shadow; it never changes the fill.** An earlier version darkened the background to `--surface` and the owner asked for it back out — with ten cards of different heights the shifting fills read as noise. `border-color:var(--accent)` plus `box-shadow:0 5px 12px rgba(0,0,0,.16)` is the whole effect.
- **The card title and the post's own title must stay on the same face.** This used to be a real trap, back when the site used four faces: the card title had no case transform, but the old `#modalLogView h3` inherited `.modal h3`'s `text-transform:uppercase`, so an English title read lowercase on the card and SHOUTED once opened, and the fix was a one-off restatement of `font-family` / `text-transform` / `letter-spacing`. **Both of those rules are gone** — the LOG post is a screen now and its heading is `.arc-detail-bar h3`, which is already `var(--mono)` with `text-transform:none`. Only the size differs (17 vs 12.5).
- **The title→subtitle gap is matched to the number→title gap by eye, which is why `.lc-sub` has `margin-top:-2.6px`.** The card is a flex column with `gap:6px`, so every pair of lines is 6px apart as boxes — but the title (`line-height:1.35`) and subtitle (`1.45`) carry more half-leading than the number (`normal`), so the same 6px read much wider (ink-to-ink 15.3px against 9.7px). The negative margin takes back exactly that leading; measured after, both gaps are 9.7px for Hangul text (a Latin-only title reads about 1px wider). Change either line-height and re-measure ink, not boxes.
- Preview length is `-webkit-line-clamp:8`, not a character count — clipping by characters gives a different number of lines per card once the font or column width changes. A post shorter than eight lines simply makes a shorter card, which is the whole point of the layout.
- `.log-cards-scroll` had to be added to `consumedByInnerScroll`'s selector list, or scrolling the card list flips the OC page out from under you.
- **`.log-cards-scroll` reserves the scrollbar's width permanently (`scrollbar-gutter:stable`), and that is load-bearing.** `layoutLogCards()` reads `grid.clientWidth` and writes px widths and lefts, so anything that narrows the box *after* the measurement leaves the cards too wide. A vertical scrollbar does exactly that, and the `ResizeObserver` cannot catch it — it watches `.log-list`, whose size does not change when a scrollbar appears *inside* it. The owner saw this as "a horizontal scrollbar shows up whenever a vertical one does". Observing the scroll box instead would risk an oscillation (narrower → taller → still needs the bar); reserving the gutter means the width never moves. `overflow-x:hidden` is kept alongside it as a backstop for sub-pixel rounding.

**The detail gallery sizes its rows, not its thumbnails.** `.gallery-thumb` is `aspect-ratio:1/1` sized by the column width, which was fine in a 658px-wide modal (124px cells, three rows fit) but overflowed once the screen made the grid 823px wide (157px cells → 42px taller than the box). `.gallery-grid-wrap` has `overflow:hidden` and `justify-content:center`, so it spilled 21px past each end and covered the `＋ ✓` row and the page arrows. The two detail galleries therefore get `grid-template-rows:repeat(3,1fr)` and their thumbs `aspect-ratio:auto; width:100%; height:100%` — the cells divide whatever height is there, so nothing can overflow at any panel size, and the thumbs come out near-square anyway (measured 142×138). **The phone grid is deliberately left alone** (3 columns, 9 or 6 per page, `align-content:start`), so this override is scoped to `.pd-tab-pane-gallery` / `.oc-page-gallery`.

**Paged grids** — three views now share the same "one page fills the remaining height, page buttons pinned below" shape: Pair list, ARCHIVE PROMPT, and the detail gallery (LOG is no longer one of them — it is the card grid above, and is allowed to scroll). Their view roots (`#view-pair.active`, `#view-archive.active`) are `display:flex; flex-direction:column`, the body is `flex:1; min-height:0`, and the grid is `flex:1` with **explicit `grid-template-rows`**. The per-page count in JS must match rows × columns in CSS or the last row will be clipped: `PAIR_PER_PAGE`/PROMPT are `8` (4×2 desktop, 2×4 phone), OOC/ETC are 15 rows editing / **14 reading** on desktop, gallery is `galleryPerPage()`. OOC/ETC are the one case that varies with `isLoggedIn` — they're a `<table>`, not a grid, so there is no CSS row count to keep in sync, and reading mode gives a row back to the search bar that only exists there. `applyEditMode()` re-renders ARCHIVE, so the count follows a login/logout without anything extra.

**On phones the OOC/ETC row count is measured, not chosen** (`fitArchiveRows()`). A single number can't fit every handset — 10 rows left an iPhone 14 Pro a third empty and still nearly overflowed a shorter screen. After the table is drawn, `fitArchiveRows` reads one `tbody tr`'s height against `.archive-table-scroll`'s `clientHeight` minus the `<thead>`, and re-renders once if the answer differs from `arcRowsPerPage`. It converges in one step because that box is `flex:1` inside a `flex:1` body, so its height does not depend on how many rows are in it. Three things keep it safe: it is called from the **very end** of `renderArchive` (calling it mid-function would bind the pagination buttons a second time, on the DOM the recursive render just replaced), `arcRowsFitting` blocks a second level of recursion, and a zero height (view not on screen yet) makes it return without caching anything — which is why entering ARCHIVE always lands on PROMPT first and OOC/ETC are only ever measured while visible. `initResponsiveWatch()` clears `arcRowsPerPage` so a breakpoint change re-measures; a rotation that crosses no media query self-corrects on the next render. Measured: 16 rows at 393×852, 11 at 375×667, and 15 in reading mode at 393×852 where the search bar takes 46px — every one with `scrollHeight === clientHeight`.

**`.archive-body`'s `padding-bottom:4px` is a measured value, not a taste call.** Even at 14 rows the reading-mode table was 472px inside a 466px `.archive-table-scroll` and scrolled by exactly 6px; the 6px came back by trimming the body's bottom padding from 10px, which also pushes the page buttons down 6px (body height itself is unchanged). Because `.arc-nai-grid` and `.archive-table-scroll` are both `flex:1` in the same body, PROMPT grows by the same 6px and all three sub-categories keep their page buttons on one line. If you change row height, row count, `gap`, or the pagination slot's `min-height`, re-measure `scrollHeight - clientHeight` on `.archive-table-scroll` with a **full** page — a folder with fewer posts than a page will report 0 and tell you nothing. Short pages are padded with invisible `.post-slot` / `.gallery-slot` elements so the grid height never changes with item count.

**Gallery/LOG are shared engines** — the pair-detail gallery and log panes are also used by the OC detail screen, so those renderers do **not** look elements up by id. They read a *host* object — `PAIR_GALLERY_HOST` / `OC_GALLERY_HOST` / `PAIR_LOG_HOST` / `OC_LOG_HOST`, each `{root, getPost, save, horizontal}` — and resolve elements as `root.querySelector('.gallery-grid')` etc. via the `gq()` / `lq()` helpers. **If you add a control to one pane, give it a class and bind it inside `initGalleryRoot()` / `initLogRoot()`, not by id**, or the OC copy silently won't work. `galleryHost`/`logHost` are set when a detail screen opens (and re-set by any control's own handler, since only one detail screen is open at a time). Module-level gallery state (`galleryPage`, `gallerySelectMode`, …) is deliberately shared and reset on open. `host.horizontal` flips the page-change animation between `translateY` and `translateX`.

**OC** — a third content type between PAIR and ARCHIVE: `state.ocPosts` (a `LIST_KEYS` array) plus `state.ocCats` (see Sidebar sub-categories below), where **each category owns its own folder list** (`cat.folders`, same shape as PROMPT folders but blur is forced off and the folder modal hides that option via `ctx.hideBlur`). Folders used to be one flat list shared by every OC post regardless of category; `ocFolderCtx(catId)` / `renderOcFolderBar(catId)` / `ocFoldersOf(catId)` all take the category explicitly now, and `ocFolderIdOf(item)` resolves through `ocCatOf(item.type)` first — so switching categories in the sidebar shows a completely different folder bar. **HOME's entrance draws the grid lines first, then fills it.** The cells' `border`s can only appear or not — they cannot be drawn — so while `.home-grid` carries `.hg-intro` the cell borders go `transparent` and seven `.hg-line` elements grow in their place with `scaleX`/`scaleY`; when the class comes off, the finished lines hand back to the real borders at the same pixel positions. - **The lines must be `position:absolute`.** They take their geometry from `grid-area` (so a change to the column/row ratios carries automatically, with no measured numbers), but a grid item with a definite position is placed *before* auto-placed ones — in flow, the seven lines shove all fourteen cells out of their slots and the whole HOME layout breaks. **Unsaved-changes guard** — `guardUnsavedClose()` is **gone**. It hooked a modal's ✕ and its backdrop click in the capture phase, and both write modals (ARCHIVE, LOG) became in-panel screens, which have neither. Each screen now carries its own three-part guard, written the same way on both sides so they read as a pair: `arcEditSnapshot()` / `logEditSnapshot()` (a `JSON.stringify` of the current field values), `arcEditDirty()` / `logEditDirty()` against a baseline armed at the end of `enterArcEdit()` / `enterLogEdit()` (**after** any async content load, never before), and `leaveArcEdit()` / `leaveLogEdit()`, which asks via `siteConfirm(...)` and only then drops the `.arcd-editing` class. The point of the split is that a screen has several ways out — 취소, ←, Escape, the device Back button, **and the sidebar** — so the question has to be asked from one place: `allowLeaveEditing()`, which both `requestLeaveDetail()` (see the detail-screen navigation section) and the sidebar guard below call. 취소 is deliberately covered here even though it wasn't in the modal version: on a screen it no longer means "discard", it means "go back to reading this post".

**The sidebar was the way out that nobody guarded, and it left the edit mode running.** A screen is not a modal: clicking a sidebar menu or category does not "close" it, it just calls `activateView` for somewhere else — which cleared `body.dataset.detail` and closed the LOG screen but **never dropped `.arcd-editing` and never cleared `editingArcId`**. So editing ARCHIVE post A, switching category in the sidebar, then opening post B showed **A's editor sitting on top of B's reading content** (the owner's report: "수정하던 게시글이 뜬다"), and 게시 there would have written into A. Two changes, and both are needed:

- **The ask** — one capture-phase `click` listener on `.nav` (not on each button). It matches `.nav-item, .nav-sub-item, .nav-cat-add` (the four doors: the top-level menu, PAIR/OC categories, ARCHIVE sub-categories, and the ＋), skips `.ns-edit` (✎ opens the rename dialog and moves nothing), and on "leave" **re-fires the same button** — by then edit mode is off, so the second click sails through the guard and the original handler runs untouched. **Capture is the load-bearing part**: the handlers are bound on the buttons themselves, so only a capture listener on an ancestor gets there first and can `stopPropagation()` them. `stopPropagation()` runs *before* the await, so a slow answer cannot let the click through. Re-entry is not a hazard because `siteConfirm`'s overlay covers the sidebar — which matters, since `siteConfirm` assigns `onclick` properties and a second overlapping call would leave the first promise pending forever.
- **The guarantee** — `activateView` now calls `endArcEditing()` whenever it moves to anything but `archive-detail`. This is what actually fixes the stale screen: even a path that forgets to ask can no longer leave edit mode running. `endArcEditing()` is `exitArcEdit()` plus `editingArcId = null`, and it lives next to that variable's declaration so `activateView` (far earlier in the file) can call it safely. `openArcView()` and `openLogView()` also drop edit mode on entry, so "opening a post shows the post" holds inside those functions rather than depending on the caller.

Note the ordering both write paths already rely on: `addArchiveBtn` and the LOG `.log-add-btn` call `openDetailView()` / `openLogDetail()` **before** `enterArcEdit(null)` / `enterLogEdit(null)`. Reverse that and `activateView`'s cleanup would cancel the edit mode you just entered.

**Sign-out must not wait on the save queue** — `SiteStore.signOut()` used to `await flushNow()` unconditionally. `flushNow()` returns the tail of `flushChain`, and a Firestore write that never gets acknowledged (offline, or the write stream backed up) leaves that promise pending **forever** — so the 로그아웃 button silently did nothing, permanently, for the rest of the session. It now races the flush against a 3s timeout and signs out regardless. Any binder that awaits a Firestore promise before doing something user-visible needs the same treatment.

**Sign-out is also latched, because `signOut(auth)` can fail quietly.** Timing it out (or having it reject on blocked IndexedDB / no network) leaves the session **persisted in the browser**, so the next reload — or any token refresh, or another tab — fires `onAuthStateChanged` with the admin user still there and the site walks itself back into edit mode. That is the other way "로그아웃이 안 돼요" happens, and no amount of timeout tuning fixes it. `SiteStore.signOut()` therefore writes a `siteSignedOut` flag to `localStorage` **first**, before doing anything that can fail; while that flag is set, the auth listener refuses to go admin, reports signed-out, and retries `signOut(auth)` in the background until it takes. `signIn()` clears the flag **before** awaiting `signInWithEmailAndPassword`, not after — the auth callback lands during that await, and clearing afterwards would have the listener eject the login that just succeeded. `signOut()` also notifies unconditionally now instead of only `if (isAdmin)`, so a UI stuck in edit mode is pushed back regardless of what the module thinks the state is.

**The `n / total` chip is triggered by `.lb-row:hover`, plus a JS `peek`, and both halves are load-bearing.** It was `.lb-stage:hover` — exactly the photo's box — and the owner reported it "only shows when I flip images". `#lightbox` has a second state, `.zoomed`, toggled by the `.lb-zoom` button that shares `.lb-count`'s hover-to-reveal rule: it collapses the thumb bar and lifts the image cap from `80vw/74vh` to `calc(100vw - 116px)/100vh`. Four things it depends on:
- **The transition is on `max-width`/`max-height`, not `transform: scale()`.** Both caps are animatable lengths, so the photo really does take up more room as it grows — which matters because `.lb-count`, `.lb-zoom` and the two arrows are all positioned off the photo's actual box. A `scale()` would move the pixels and leave every one of those behind. `--lb-zoom-ms` / `--lb-zoom-ease` in `:root` keep the photo, the thumb bar and the column gap on one beat.
- **The thumb bar collapses by `max-height`, not `display:none`,** since display can't be transitioned — hence the `.lb-thumb-bar` wrapper around `.lb-thumbs`. And the "only one image" case hides that wrapper **by a `.hide` class rather than an inline `style.display`** (CSS cannot override an inline style, so the two hiding conditions would have fought).
- **The arrows stay flex siblings of the photo** at the usual 18px, in both states — anchoring them to the viewport edges instead left a huge dead gap beside a narrow photo. The price is that the 116px they occupy (`40×2 + 18×2`) has to come off the zoomed `max-width`, or a wide photo slides under them. The phone block already absolutes the arrows over the photo, and there `max-width` goes back to a full `100vw`. Verified: gap is exactly 18px either side, zoomed and not, for both a landscape and a portrait source.
- The zoom icon is inline SVG for the same reason the alignment icons are, and `openGalleryLightbox` clears `.zoomed` on every open so zoom never leaks from one photo to the next. That removal happens while the lightbox is still `display:none`, which is also what stops it from animating on open.

The photo is still capped at its natural size — `max-width` only ever shrinks — so zoom gains nothing on a source smaller than the viewport. Deliberate: upscaling past the stored resolution just looks soft.

**The thumb strip is a nine-wide window, not the whole folder.** `lbThumbWindow(idx)` is `clamp(idx − 4, 0, n − 9)`, which puts the current photo in the middle slot everywhere except the first and last four, where there is nothing to pad with and the strip sits flush against the end. `markGalleryLbThumb` recomputes it on every photo change and only re-renders when the window actually moved. The `‹ ›` buttons at the two ends (`.lb-thumb-nav`, which carries `.lb-nav` too so it inherits the symbol-rescue font, the centring correction and the styling) page **the strip alone** by nine at a time and deliberately leave the displayed photo where it is — so the strip stays where the reader put it until they change photo, at which point it recentres. `.lb-thumb-bar:not(.paged)` hides both buttons when nine or fewer images make paging meaningless. The widths are chosen so the whole bar is exactly 720px, which was the detail modal's width before it became a screen: `64×9 + 8×8 + 2×2 = 644` for the strip, plus `28×2` buttons and `8×2` gaps.

Arrow keys drive both lightboxes (`initLightboxKeys`, a single document-level `keydown`). It checks `#arcLightbox` before `#lightbox` because the attachment lightbox sits above the gallery one, and it bails on `isContentEditable`/`INPUT`/`TEXTAREA`/`SELECT` targets — a lightbox can be open while a post editor still holds focus behind it, and there the arrows have to keep moving the caret.

**Two more MCP limits worth knowing before you try to verify an interaction.** The `computer` tool's coordinates are in **screenshot space, not viewport CSS pixels** — at a 1920px viewport the screenshot is 1568 wide, so multiply by ~0.817 before clicking, or the click lands somewhere else entirely (this is the same mismatch the `hover` note below describes). And `computer key` delivers **no `keydown` to the page at all** — a document-level capture listener records nothing — so keyboard handling cannot be exercised that way. Dispatch a synthetic `KeyboardEvent('keydown', {cancelable:true})` and assert on `defaultPrevented` plus the DOM change instead; that exercises your own listener, and `preventDefault()` on `keydown` is what suppresses the browser's own editing anyway.

**Testing any of this from an automation tab needs care: the MCP tab reports `document.hidden === true`.** CSS transitions do not advance and `setTimeout` is throttled to ~1s there, so the zoom appears not to happen at all and one arrow press per ~2.5s is all that gets through `lbAnimating`. Neither is a real bug — nothing here waits on a transition event. To check the zoom rules, inject `*{transition:none!important}` and read the end state; to check the mid-flight layout, set the interpolated values by hand and confirm the photo never leaves the viewport (it can't: the photo grows by 26vh exactly as the 68px bar plus 14px gap collapse, landing on 100vh).

**Lightbox slide animation must not depend on animation events or on frames happening.** `slideGalleryLightbox(dir, commit)` chains out → swap → in, and both hand-offs are plain `setTimeout`s. `Animation.onfinish` was tried first and is wrong here: the finish event is delivered as part of the rendering step, so in a **background tab it never fires** — the image froze mid-fade and every later arrow press was blocked by the `lbAnimating` guard. For the same reason the incoming animation is explicitly `.cancel()`ed on a timer: a freshly created animation gets its start time during the first frame, so in a hidden tab it stays pending at keyframe 0 (opacity 0) forever. Timers are throttled to ~1s in background tabs but they do fire, so state always converges. Same rule applies to `scrollIntoView` — the thumb strip uses the default instant behavior, not `'smooth'`, which also needs frames.

**Pinning** — ARCHIVE and LOG (both PAIR's and OC's, via the shared engine) each cap pins at 3 and sort pinned items to the front at render time; nothing about the stored order changes, an entry just carries `pinned:true`. The visible `No` column is therefore **not** the row's position — it comes from a `Map` of registration order (`displayNo`), so pinning or searching never renumbers an existing post. The limit is per list: three per ARCHIVE category-set and three per post's `log`. The `📌` marker (`.arc-pin-tag`, shared by both tables) needs `display:inline-block; font-size:9px; line-height:1` — left at the cell's own size, an emoji's line box is taller than the text's and **grew the pinned row by 3px** (35 vs 32), so a pinned row visibly stepped out of the table. Any emoji dropped inline into a fixed-height row needs the same treatment.

**Two-across image blocks** (`.img-pair`) — unlike code fences and auto-format, this one **is** real saved markup, not a render-time transform: `<div class="img-pair" contenteditable="false"><div class="img-pair-cell"><img></div>×2</div>`. It is created by dragging one image in the editor onto another (`initEditorImageTools(editorId)`, wired for `arcContentEditor` and `logContent`), and afterwards edited only through the hover toolbar, which grows two buttons when the hovered image sits in a cell: `변경` (file picker → replace that one cell) and `⇄` (swap the cells). `↑ ↓ ✕` retarget too — up/down move the **whole block** among its siblings, and `✕` deletes just that cell and then *unwraps* the block back to a plain `<img>`, since a one-cell "pair" is meaningless.

Three constraints worth keeping:
- **Only plain images participate in the drag** — `plainImg()` returns `null` for anything already inside an `.img-pair`, on both the source and target side. Allowing a drop onto an occupied cell would silently discard the image that was there; the `변경` button is the one deliberate path for that.
- **The `drop` handler must `preventDefault()`.** contenteditable performs its own image move as the drop's default action, so without it the browser relocates the source image *in addition to* the block being built.
- `contenteditable="false"` on the block (same as `.code-embed`) is what stops the editor from splitting cells or parking a caret between them. It is a `DIV`, so `BLOCK_TAGS` already counts it as a fence line separator; `.fold-block > .img-pair` gets the same `margin-left:20px` as `.code-block` for when it lands as a direct sibling of `.fold-head`. `.img-pair > .img-pair-cell > img` needs **two classes** in the selector to beat the per-editor `… img{margin:8px 0}` rules, which are spread through the file and some come later.

Touch is not wired: `initDragEngine()` deliberately skips `[contenteditable="true"]` so iOS text selection keeps working, so the block is created on desktop only. It renders and can be reordered/deleted anywhere.

**The copy box (`.copy-box`) is real saved markup, and nothing inside it is ever transformed.** It is the one block whose whole point is that the text comes out exactly as typed — prompts, mostly. Structure is `.cb-title` (bold, always preceded by a drawn 5px square via `::before`) + `.cb-body` + a `.cb-copy` button, inserted by `insertCopyBox(editorId)` from a toolbar button in the ARCHIVE and LOG editors.

- **One change makes it inert, not three.** `flattenForFences` refuses to descend into `.copy-box` (it counts as a block and contributes a boundary, but no text and no marks). Because `applyCodeFences`, `applyMarkdownBlocks` and `applyAutoFormat` all read that flattened string, a ` ``` `, a `#` or a `**pair**` inside the box is invisible to all three at once. Verified: inside the box those stay literal, outside the box they still work.
- **A box holds *one or more* `.cb-body` divs, and copying must gather them all.** Chrome splits a block at the caret and clones its class, so an Enter or a multi-line paste in the body leaves `<div class="cb-body">` **per line** — visually identical (the lines run on exactly as before), which is why nobody noticed. The copy button read `querySelector('.cb-body')` and therefore **stopped at the first line**; 17 of the 32 boxes in the live data are split this way, one of them into 20 divs. `copyBoxText(box)` walks every `.cb-body` and joins them with `\n`. The stored HTML is left exactly as it is — the split is harmless once the reader gathers it, and rewriting saved posts to "repair" them would be touching data for no gain. Two details: it walks the nodes itself instead of using `innerText`, because a box inside a **collapsed fold** is not rendered and `innerText` then falls back to `textContent`, which loses every `<br>`; and the `<br>` that closes a body is dropped, since the join already supplies that line break and the browser does not draw it either (a `<div class="cb-body"><br></div>` is *one* blank line, not two). Verified against the 9-div box in ARCHIVE #73: 9 divs → 9 lines, 505 characters, byte-identical to what the box shows.
- **The copy button is a child of `.copy-box` but renders below it** (`top:100%; left:50%`). Pulling it out as a sibling would let the editor delete or absorb it independently of the box.
- **Backspace/Delete next to the box delete the whole box** (`initCopyBoxKeys`). Left to the browser, Backspace after the box steps *inside* and removes only the last child — the copy button — leaving a box that can no longer be deleted from outside. That shipped once. The same handler blocks Backspace at the very start of `.cb-title` and Delete at the very end of `.cb-body`, both of which break the box from within.
- **Enter is intercepted too** (`initFoldEnter`): in the body it inserts a plain `<br>` (otherwise Chrome splits the div and clones its class, exactly as it does to `.fold-body`); from the title it moves into the body — **except at the very start of the title, where it opens a line *before* the box**. Without that last case a box sitting first in a post is unwritable-above: there is no caret position ahead of it. The caret lands *before* the new `<br>`, which is the position browsers place reliably.
- **The face is Galmuri11, fixed at 11px.** It is a bitmap-derived pixel font drawn for 11px, so any other size (bar multiples like 22) goes blurry. The two `@font-face` rules point at jsDelivr and cost **zero bytes until a copy box is actually on screen** — a browser fetches a face only when something needs it, which matters here because the pair is 654 KB.
- Colours: box `#f6f5f2` (a step lighter than `--surface-2`, which is left alone because the sidebar and empty thumbnails share it), corner marks `--border` drawn as eight background gradients like the page's own trim marks, button outline `--rule-soft`.

**Post body transforms** — saved post HTML is decorated at *render* time, never at save time, so the stored content stays plain editor output. `decorateContent(el)` runs `applyCodeFences()` (turns ` ``` `-fenced runs into `.code-block` with a copy button), then `applyMarkdownBlocks()`, then `ensureCodeEmbedCopy()` (back-fills a copy button into `.code-embed` toolbars saved before that button existed). `applyAutoFormat()` skips anything inside `.code-block`.

**Font size is one shared function across four toolbars.** `stepFontSize(editorId, ±1)` walks the current selection, wraps it in a `<span style="font-size">` at ±1px from `selectionFontSize()`, strips any nested sizes so repeated presses keep a stable base, and re-selects what it just changed so you can hold on stepping. OC's free text and both memo boxes reach it through `bindFreeToolbar`'s `data-rt="sizeUp|sizeDown"`; ARCHIVE and LOG bind their own `#arcSizeUpBtn` / `#logSizeUpBtn` pairs by id, because those two toolbars are id-bound rather than delegated. **Every one of those buttons needs `mousedown` → `preventDefault()`** — the function works on the selection, and without it the click moves the caret first and nothing happens.

**Markdown is split across two functions by scope, and the order matters.** Line-level syntax (`> quote`, `# heading` ×6, `| table |`) lives in `applyMarkdownBlocks()`, which runs from `decorateContent` and therefore applies everywhere post bodies are drawn (ARCHIVE and LOG). Inline syntax (`***bold italic***`, `**bold**`, `*italic*`, plus the quote/paren auto-coloring) lives in `applyAutoFormat()`, which only LOG calls — so italic works exactly where bold already did. Three ordering constraints:
- `applyCodeFences` must run **first**, and `applyMarkdownBlocks` skips any line that resolves inside `.code-block`/`.code-embed` (`mdInsideCode`) — otherwise a `#` or `|` inside a code sample gets eaten.
- In `applyAutoFormat`'s alternation the star branches must run **three, two, one** — regex alternatives are tried in order, so italic-first would claim the leading `**` of every bold run and `***…***` would never be reachable.
- A table needs a `|---|---|` separator line **directly under** its header row (`MD_TABLE_SEP_RE` demands two or more columns). Without that requirement a lone `---` used as a divider, or any sentence containing `|`, would turn into a table.

**Inline markdown works on the flattened text, not on single text nodes, and that is the whole point.** The original `applyAutoFormat` walked text nodes and ran the regex inside each one. Applying a toolbar effect (highlight, bold, colour) to part of a `*…*` run splits it across elements — `*` `<span>기울임</span>` `*` is three text nodes — so the pair was never found: the asterisks stayed visible and the italic never applied. That was a reported bug ("이탤릭에 다른 효과를 겹치면 `*` 가 그대로 보여요"). It now uses the same machinery as code fences and block markdown — `flattenForFences` → find pairs in the flat string → `resolveFenceOffset` → `range.extractContents()` into a fresh `<b>`/`<i>`/`<span>` — so whatever markup sat inside the run survives, exactly as `mdBuildQuote` preserves a quote's contents. Four things this depends on:
- **The markers are cut off the extracted fragment, not excluded from the range.** `afCutEdge(frag, n, fromEnd)` removes *n* characters from the fragment's first (or last) non-empty text node, so a marker that itself sits inside formatting (`<b>**</b>굵게`) is still removed from the node it actually lives in.
- **Nesting is recursion, not a cleverer regex.** After a wrapper is built, `applyAutoFormat` runs again on its contents. Bold's content pattern admits lone `*` and italic's admits complete `**…**` runs, so `**볼드 *기울임* 끝**` and `*기울임 **볼드** 끝*` both resolve on the second pass; `***…***` has its own branch because non-greedy matching mis-pairs it otherwise. The recursion into a `"…"`/`(…)` wrapper passes `starsOnly`, because those keep their delimiters — the full pattern would match the same span again forever. Every other level strictly shrinks the text (the markers are gone), so it terminates on its own; `AF_MAX_DEPTH` is belt-and-braces.
- **A pair may not cross a table cell.** `<td>`/`<th>` are not in `BLOCK_TAGS`, so two cells run together in the flat string with no `\n` between them and a `*` in each would look like a pair. `afLineBox()` requires both ends to resolve to the same block-ish box and skips the match otherwise. Blocks are safe without this — they insert `\n`, which every branch excludes.
- Verified against all 102 stored post bodies: no exceptions, and the rendered text differs from the undecorated render **only** by `*` characters (15 posts actually change).

**`localLineBoundary` must not swallow a `<blockquote>` (`MD_KEEP_TAGS`).** Its fallback — "no line separator in this direction, so `el` is a one-line wrapper; replace `el` itself" — is what makes a code fence replace the whole `<div>` that held it, and nested folds depend on that. But a quote is not a line wrapper, and applying it there produced `<h1 class="md-h"><blockquote>제목</blockquote></h1>`: the quote ate the heading and the line still rendered as a plain quote, which the owner saw as "`#` doesn't work inside a 인용구". `MD_KEEP_TAGS` (currently just `BLOCKQUOTE`) makes the boundary the *inside* edge of the box instead, so the heading lands within the quote. Verified for a heading as the only line, as the first of several, and as the last. `.fold-body` is deliberately **not** on that list — the fence behaviour documented above relies on it being replaceable.

**A quote and a heading keep the DOM that was inside them; a table still does not.** `mdBuildQuote`/`mdBuildHeading` originally rebuilt the block from the flattened *string* (`createTextNode(line)` / `h.textContent = …`), which silently threw away every inline style on those lines — the reported symptom was "형광펜 applied inside a 인용구 doesn't show", and 글자색 and 볼드 were going the same way. They now take the `range.extractContents()` fragment instead and `stripLineMarks()` removes only the leading `>` / `#` marker, walking the fragment with the **same line rules `flattenForFences` uses** (`<br>`, block tags, `\n` inside a text node). That is what makes `<span style="background">> 인용</span>` work: the marker is deleted from the text node it actually sits in, so the span survives. `tidyMdBlock()` then drops the trailing `<br>` the extraction usually carries (skipping empty text nodes left by the split, or it stops at one and the `<br>` stays) and unwraps a single attribute-less `<div>` wrapper. **Tables are still text-only** — splitting a row into cells at `|` means cutting the DOM, not just trimming a prefix — so the table branch keeps `deleteContents()`. Do not "unify" the three back onto one path.

`applyMarkdownBlocks` reuses the code-fence machinery wholesale — `flattenForFences` → line list → `resolveFenceOffset` → `fenceLineBoundary` → replace one Range — for the same reason fences need it: contenteditable does not reliably put each visual line at the top level. Groups are collected first, then applied **back to front**, because `marks` holds pre-edit coordinates. Verified against all 53 stored posts: 0 exceptions, and on the two posts that actually convert, the rendered text is byte-identical once markdown markers are stripped — nothing but the markers is consumed.

**One rule sets the leading for every long-form text on the site.** `.profile-view-text{font-size:12.5px; line-height:1.6}` is worn by post bodies (reading *and* both editors, via `.arc-view-content` / `.log-editor` / `.arc-editor`), OC and PAIR descriptions, and OC free text — so that single declaration is the knob, and there is no need to hunt for others. Deliberate exceptions keep their own values: HOME intro 1.9, relationship box 1.7, side memo 1.6, LOG card preview 1.65. It was 1.4 until the owner asked for more air; the phone override that used to raise it to 1.55 was deleted rather than updated, since it now only *lowers* the inherited value.

**Post bodies have two deliberate leadings: 20px for a wrapped line, 24px for one the author broke with Enter.** The 24 is `line-height` + `margin-top:4px`. This started as `.fold-body`'s 8px, which existed only to separate a fold's title from its content — but because a single `.fold-block` routinely holds **many sibling `.fold-body` divs**, one per line, from the old Chrome-splits-on-Enter behavior (see the collapse-hiding note), that margin was in practice already acting as the Enter-line gap *inside* folds while lines outside folds got nothing. Three rules now carry it: `.fold-body` keeps `8px` (title gap only), `.fold-body ~ .fold-body` overrides to `4px` (line gap), and `.arc-view-content > div:not([class])` — plus the same for `.arc-editor` / `.log-editor` / `blockquote` — gives outside-fold lines the same `4px`. **These three numbers are tied to the line-height above**; the 1.4 → 1.6 change scaled all of them by 1.143 so that both baseline-to-baseline distances (21 → 24, 24.5 → 28) kept their old proportion. Change the leading again and re-derive them, or Enter-broken lines stop reading as separate paragraphs.

**`blockquote` had to be added to that selector list, and its absence was a real reported bug.** The lines inside a quote are children of the `<blockquote>`, not of `.arc-view-content`, so a `>` child combinator scoped to the body never reached them: line breaks inside a quote worked but produced no gap, which the owner described as "the Enter goes through but the blank space doesn't show". `blockquote > div:not([class])` covers both quote flavours at once — the markdown one (`.md-quote`) and the toolbar one are the same tag — and there is no other `<blockquote>` on the site, so it needs no further scoping.

`:not([class])` is what keeps this off the block widgets — the line `<div>`s contenteditable produces have no class, while `.fold-block` / `.code-block` / `.code-embed` / `.img-pair` all do and carry their own spacing. The `:first-child` reset only fires when a body happens to start with a `<div>`; the usual shape starts with a bare text node, so the first `<div>` is genuinely the second line and correctly keeps its margin. A `<div><hr></div>` line measures more than 24 — that is the `<hr>`'s own margin, not a bug.

Two things this cost a round trip to learn, worth not repeating. First, pasted blank lines (`<div><br></div>`) are all over these posts and *look* like the cause — they are not, and stripping them at render time is the wrong fix: a blank line is supposed to render as a blank line. Measure `getBoundingClientRect()` on consecutive single-line blocks against the wrapped-line delta inside one block before concluding anything. Second, "make the spacing consistent" turned out to mean "standardize on the larger value," not the smaller one.

**Paste normalization is formatting-only, by explicit instruction.** `normalizePastedText()` converts CRLF→LF and `&nbsp;`→space and does nothing else. Earlier versions also collapsed blank lines and trimmed trailing whitespace; that was rejected as **changing the author's content** rather than matching format. Keep any future additions to this function on the same side of that line — invisible characters that break layout, yes; anything that removes or merges what was written, no.

**Fold blocks** (`.fold-block`, Notion-toggle style) are real saved markup; a delegated click toggles `.open` — the whole `.fold-head` is clickable when reading, but **only the `.fold-arrow`** while editing, so clicking the title still places the caret. `.fold-title`/`.fold-body` hold no placeholder text — they're genuinely empty and rely on `body.logged-in .fold-title:empty:before` / `.fold-body:empty:before` (same trick as `.oc-free:empty:before`) for the "타이틀"/"내용을 입력하세요" hint, so there's nothing to select-and-delete before typing. All three editors that offer a fold button (ARCHIVE, PAIR_LOG, OC free text) insert them through the shared `insertFoldBlock(editorId)`, and save through `editorHtml(editorId)`, which strips `.open`, so a post always opens collapsed no matter how the author left the editor.

**Collapsing hides every direct child of `.fold-block` except `.fold-head`** (`.fold-block:not(.open) > *:not(.fold-head){display:none}`), not specifically `.fold-body`. This is deliberate defense-in-depth: some already-saved posts have a fold with **multiple sibling `.fold-body` divs** inside one `.fold-block` (see the `initFoldEnter` note below for how that happened), and `applyCodeFences` itself can legitimately leave a `.code-block` as a direct sibling of `.fold-head` rather than nested one level down inside `.fold-body` (when the fenced lines were the *only* content of their line-container — see the `fenceLineBoundary` note). Targeting `.fold-body` specifically would miss both of these and leave content visible after collapsing.

`insertFoldBlock` builds the block with `document.createElement` and places it via `Range.insertNode()` at the current selection **instead of** `execCommand('insertHTML')` — critically, this means it inserts wherever the caret actually is, including inside another fold's `.fold-body`, which is what makes folds-inside-folds work with zero extra code. The same reasoning applies to `insertBlockquote(editorId)` (shared by ARCHIVE and OC free text): `execCommand('formatBlock', false, 'blockquote')` converts the *nearest block ancestor*, which inside a fold is `.fold-body` itself — it doesn't turn the quoted line into a blockquote, it wraps the whole fold body in one (`<blockquote><div class="fold-body">…`), corrupting the fold. `insertBlockquote` sidesteps this the same way `insertFoldBlock` does: build the `<blockquote>` and `Range.insertNode()` it (wrapping the current selection if non-collapsed, otherwise inserting empty with a `<br>` to type into).

**Anything inserted through a modal or native file picker must save and restore the caret Range explicitly**, or it silently escapes an enclosing fold. `arcInsertCodeBtn` (opens `#modalArcCode`) and `arcInsertImageBtn` (opens a native `<input type=file>`) both call `editor.focus()` right before their `execCommand('insertHTML', …)` — but focusing an already-focused editor does **not** restore whatever selection existed before the modal/file-dialog stole focus, so without help the browser drops the caret back at its own default position (observed: escaping any enclosing fold entirely). Both now capture `window.getSelection().getRangeAt(0).cloneRange()` the moment the button is first clicked (before focus moves anywhere) and re-`sel.addRange()` it right before the `insertHTML` call.

**Fold Enter** is handled by `initFoldEnter(editorId)` (wired for all three editors alongside their fold button), which covers **two** carets, not one:

- **`.fold-title`**: pressing Enter always inserts a single `<br>` and never touches `execCommand`. If the fold is **collapsed**, the `<br>` goes immediately after the `.fold-block` in *its own* parent — which is either the top-level editor or, for a nested fold, the outer fold's `.fold-body` — so the cursor "exits" exactly one level up. If the fold is **open**, the `<br>` goes at the very start of `.fold-body` instead, so Enter drops the cursor straight into the content without leaving the fold. Both branches are one `insertBefore` call; nesting depth never needs special-casing because the block's own `parentNode` is always the correct target.
- **`.fold-body`**: this branch exists because leaving Enter here to the browser default is actively destructive. Chrome splits a block on Enter by cloning its own class onto a new sibling — so typing multiple lines inside `.fold-body` produced **several sibling `<div class="fold-body">` elements** instead of one `.fold-body` with internal `<br>`s. (This is why the collapse-hiding rule above targets "every child but the head," and why some already-saved posts have this exact shape.) The fix intercepts Enter here too and inserts a plain `<br>` in place, so multi-line fold content always stays inside the one `.fold-body` it started in.

Both branches route the resulting cursor placement through **`placeCursorAfterBr(sel, br)`**, not a bare `range.setStartAfter(br)`. This exists because of a real Chrome quirk: if the freshly-inserted `<br>` ends up as the *last* node in its container, positioning the collapsed selection immediately after it is not reliable — `execCommand('insertText')` (and real typing) can insert the next character *before* the `<br>` instead of after it, even though the Range itself was provably at the correct DOM boundary. `placeCursorAfterBr` works around this by guaranteeing the `<br>` is never trailing: if there's nothing after it (or only an empty text node), it inserts a filler `<br>` right after and points the selection **before that filler** instead — "before a following node" is the position browsers handle predictably; "after the last node in a container" is not. Watch for this same failure mode in any *new* Enter-key handling added to a contenteditable region — it doesn't reproduce under `dispatchEvent`-only synthetic testing without actually typing more text afterward, so verify with a real follow-up character, not just `evt.defaultPrevented`.

**Blockquote keys** live in `initBlockquoteKeys(editorId)`, which **every editor with a 인용구 button must call** — ARCHIVE directly, and the three free-text editors (OC free text, the two memos) through `bindFreeToolbar`. It was hard-wired to `#arcContentEditor` before, so quotes in the other editors had neither behaviour.

- **Enter** (not Shift+Enter, which keeps the browser's in-place `<br>`) `extractContents()`s anything after the caret into a new sibling `<div>` and moves the caret there, so writing continues as a normal paragraph instead of the browser's default of minting a second, nested blockquote.
- **Backspace at the very start** unwraps the blockquote in place. Without this a quote sitting at the **top of the post is unremovable** — the browser's default backspace merges a block into the preceding one, and when there is no preceding one it does nothing at all, with no other gesture that dissolves a blockquote. "Very start" is tested by cloning the range from the quote's start to the caret and checking it holds no text and no `img`/`hr`, so a leading image counts as content; anywhere else, and for non-collapsed selections, the browser's default is left alone.

`initFoldEnter` **returns early when the caret is inside a blockquote**, because a quote nested in a fold body puts both listeners on the same Enter and `preventDefault()` does not stop the other one from running. The innermost construct wins.

**Code-fence parsing (`applyCodeFences`) works on flattened text, not top-level DOM children.** An earlier version grouped only the element's *direct* children into "lines" (`<br>` or a top-level block tag as the separator), on the assumption that contenteditable always puts each visual line at the top level. It doesn't — the line right after inserting an `<img>` or `<hr>` often lands as a bare text node merged with the previous inline content (no `<br>` at all), which silently deleted that content and could desync which `` ``` `` paired with which, dropping or corrupting later code blocks in a post with several. `flattenForFences(root)` instead does a full recursive walk, building one plain-text string (with `\n` inserted for every `<br>` and — de-duplicated, so adjacent block tags don't produce a blank line — every block-tag boundary at any nesting depth) plus a parallel `marks` array of `{pos, container, offset}`, always recorded even when the `\n` itself is deduped away, so a position where several nesting levels' boundaries coincide still resolves to a specific (and specifically the most-recently-recorded) DOM point. `applyCodeFences()` finds all `` ``` `` occurrences globally and pairs them in document order `(1,2)(3,4)…` (an unpaired trailing fence is left untouched). Pairs are walked **back to front** so an earlier deletion never shifts a later mark's coordinates.

**Font size is the one thing carried across the fence.** `.code-block-body` is a `<pre>` filled by `textContent`, so every scrap of markup inside the fenced region is discarded on purpose — code has to render as written. That silently threw away the size set with the ˄/˅ buttons, which is the only formatting anyone actually wants on a code block. `fenceFontSize(root, range, point)` therefore reads a size out of the region *before* `deleteContents()` and `makeCodeBlock(code, fontSize)` writes it back as an inline style on the `<pre>` (beating the class's `font-size:11px`). It looks in two places because `stepFontSize` can leave the `<span style="font-size:…">` either **inside** the fenced region (the usual case — only the code lines were selected) or **wrapping the whole thing including both fences**, in which case the span is an ancestor of the range and never appears in `range.cloneContents()`; the second lookup walks ancestors up to `root`. The size lives on in the stored source as that same span, so it survives edit round-trips.

**Finding *which* DOM range to delete for a fence pair needs two passes, not one.** `resolveFenceOffset()` turns `openPos`/`closePos` (positions in the flattened string) back into an exact `(textNode, offset)` — that part is unambiguous, since fence characters always live in one specific text run. But the *deletable range* isn't "from one resolved point to the other": `fenceLineBoundary(root, point, after)` walks up from that text node to the nearest enclosing block-tag element (e.g. `.fold-body`), because coordinate math alone can't disambiguate nested closing boundaries that land on the same character position (opening boundaries nest inward so last-recorded/innermost naturally wins a tie; closing boundaries cascade outward, so the same rule picks the **outermost** one — exactly backwards for staying inside a fold). It returns `null` when there's no wrapping block at all (bare text merged directly into the editor root), and only then does the coordinate-based `resolveFenceOffset` fallback apply.

Finding the enclosing block is still not the whole answer, though — **that block can itself hold more than one line.** If a fold's content was typed as `<br>`-separated lines directly inside one `.fold-body` (rather than one nested `<div>` per line), naively deleting "all of `.fold-body`" to remove just the fenced lines would take the surrounding lines with it — real content loss, not just a fold-nesting cosmetic issue. `localLineBoundary(el, node, dir)` handles both shapes with one rule: walk `node`'s siblings within `el` looking for a **line separator** in direction `dir`; if found, the boundary is *inside* `el`, right at that separator (correctly scoping to just this line among several). If none turns up before running out of siblings, that means `el` itself holds nothing but this one line (the one-`<div>`-per-line shape), so the boundary is `el`'s **own** position within *its* parent — which is what makes `el` (the whole line-`<div>`) the unit that gets replaced, matching the earlier-established nested-fold behavior. This is also why the collapse-hiding CSS rule (above) can't assume the resulting `.code-block` always ends up wrapped in a `.fold-body` — the `<br>`-lines case leaves it as a direct sibling of `.fold-head` instead, by design, which is in turn why `.fold-block > .code-block/.code-embed` needs its own `margin-left:20px` to line up with `.fold-body`'s `padding-left`.

**A "line separator" is not just `<br>`** (`isLineSeparator()`): it also counts `<img>`, `<hr>`, any `BLOCK_TAGS` element, and existing `.code-block`/`.code-embed` boxes. These contribute **zero characters** to the flattened text, so in string coordinates they collapse onto the same position as whatever surrounds them — but every one of them renders as its own `display:block` line and, more importantly, is content that must not be deleted. This was a live data-loss bug: real saved posts contain `<div class="fold-body"><img>```</div>` (image inserted into a fold, then backticks typed immediately after, with no `<br>` in between). Scanning backward for `<br>` alone found nothing, fell through to the "replace the whole `el`" branch, and **deleted the image along with the fence line** — silently, at render time, on every view. Counting `<img>` as a separator makes the boundary land right after the image instead. When touching this scan, remember the invariant is "don't cross anything that occupies its own line," not "find a `<br>`."

If two pairs' line-ranges would overlap (only possible if a closing fence and the next block's opening fence somehow land on the exact same line, which normal typing doesn't produce), the earlier one is left as plain text rather than risking a corrupt range — same "if unsure, don't touch it" fallback as an unpaired fence.

**ARCHIVE write modal (`#modalArcWrite`) fills available height with flexbox** (`display:flex;flex-direction:column`, plus `.arc-editor{flex:1 1 auto;min-height:160px;max-height:none}`) instead of giving the editor a fixed `max-height`. A fixed px cap (previously 320px, copied from `.log-editor`) meant a post with a large image made only the editor scroll internally (correct, per the "ARCHIVE 글쓰기 모달 스크롤" requirement) but left the *edit* modal much shorter overall than the *view* modal — since only `.arc-editor` was capped, not the modal around it. With flex, `.arc-editor` absorbs whatever room the fixed-size chrome (title, category, toolbar, attachments, buttons) doesn't need, up to the inherited `88vh`, so a large-image post's edit modal now reaches the same height as its view modal, and a short/blank post's modal still sizes naturally to its content (flex-grow has nothing to distribute when total content is already under `88vh`) rather than stretching into a mostly-empty box.

**That flex rule must stay scoped to `#modalArcWrite`** (`#modalArcWrite .modal.wide.arc-modal{…}`) — **`#modalArcView` reuses the very same `.modal wide arc-modal` class list**, so an unscoped `.modal.wide.arc-modal{display:flex}` silently reformats the read-only view modal too: `.arc-view-content` becomes a flex item, gets shrunk instead of laying out at full height, and the modal's own `overflow-y:auto` stops being what scrolls. The two modals are meant to scroll differently — **view scrolls as one window** (plain `.modal` block layout, the default), **edit scrolls inside the body box only** (flex, so the surrounding chrome stays pinned while typing). Verify both when touching `.arc-modal`: view should report `display:block` with `modal.scrollHeight > modal.clientHeight`, edit should report `display:flex` with the modal *not* scrolling and `#arcContentEditor` scrolling instead.

**Changing the body font can make symbols vanish, and fallback will not always save you.** The worst case is a face that carries the character as an *empty* glyph — present, zero advance width, nothing drawn — because the character is technically covered and the browser never falls through. KoPub 돋움 did exactly that with `⇄ ‹ › ⋮`, and the lightbox arrows and kebab buttons silently disappeared. Pretendard is the gentler case: it simply **lacks** a fair number of glyphs (`⇄ ⋮ ✕ ✎ ⠿ ︽ ︾ ✥ ☰ ✓ ＜ ＞ …`), so fallback does happen — but to whatever the device offers, which means the same button is drawn from a different face on different machines. So the targeted `font-family:system-ui,'Segoe UI Symbol',sans-serif` rules stay, with a changed job: they no longer rescue an invisible glyph, they **pin which face gets the fallback** so one screen doesn't mix two symbol faces at two apparent weights. Two places carry them — the group at the top of the file (`.lb-nav`, `.arc-lb-nav`, `.arc-kebab-btn`, the image toolbar's flip button) and `.dt-back` on its own. This is also why the `‹ ›` optical correction has to be measured against the fallback face rather than `--mono` (see "single-glyph icon button" above). **After any font swap, sweep for it**: walk every text node plus `[placeholder]`/`[title]`/`[value]`, keep the non-Hangul/ASCII characters, and measure each one's width in the new face against a face that certainly lacks it — equal widths mean the new face didn't draw it. 37 characters were in play the first time and exactly four failed.

**A font swap also knocks every single-glyph icon button off centre, and `align-items:center` is what betrays you.** Flex centring centres the *line box*, not the ink, and the line box is built from the font's ascent/descent — KoPub 돋움 is 0.85/0.25 em where 조선굴림체 was 0.86/0.14. The extra descender room parks the glyph high. Two facts make this tractable:
- **`line-height` is not the knob.** Under `align-items:center` the baseline lands at `contentCentre + (ascent − descent)/2`, which contains no `line-height` term — changing it does nothing. The knob is `padding-top`/`padding-bottom`, and because the boxes are fixed-height `border-box`, **a padding of N moves the glyph N/2**.
- **Chrome quantises the used ascent/descent to whole pixels at small sizes**, so the pure-metrics prediction can be a full pixel out. Measure the rendered result, don't compute it.

Measure like this: append a zero-height `inline-block` next to the glyph (**inside a `<span>` wrapping the text** — a bare append to a flex button becomes its own flex item and reads nonsense) and its bottom edge is the exact baseline; get the ink extents from canvas `measureText().actualBoundingBox*` at ~1000px and scale down; compare the ink midpoint with the box midpoint. **The values in the file were re-measured for Pretendard on 2026-09-10**, and the lesson of that pass is worth more than the numbers: **most of these corrections existed only because of KoPub 돋움 and should have been deleted, not adjusted.** Pretendard's ascent/descent split is even, so a glyph it draws itself lands centred on its own. **A photo is a bare `src` string, or `{src, title}` once it is given a title.** Titles are opt-in, so every photo without one stays exactly the string it always was and there is no migration. Read a photo's address through **`photoSrc(v)`** and its title through **`photoTitle(v)`**; **`withTitle(v, text)`** puts one on and takes one off (an empty title collapses the object back to the bare string, so no `{src, title:''}` husks accumulate). The same shape works inside a stack, so a photo in a bundle can carry its own title. Four things this touches beyond the accessors:
- **`normalizeGalleryEntries()` had to learn the shape first** — it drops anything that is neither a string nor a stack, so a titled photo would have been deleted on the next load and that deletion saved. This is the same landmine stacks hit; see the warning on that function.
- **`entryCover()` returns `photoSrc(...)`, never the entry itself.** It used to hand back a bare `v` for a non-stack, which is now sometimes an object. `attachDraggedThumbToGrid` goes through it too (it was reading `folder.images[idx]` raw, which was already wrong for a stack).
- **Two write-guards tested `typeof v === 'string'` and would have silently refused to save.** The page-reorder guard in `initGalleryRoot` and the stack-edit `dragend` guard both ask "is this a real photo" now (`!!photoSrc(v)`), not "is this a string". A guard that quietly declines to write is the worst failure mode here, because nothing appears broken until a reload.
- The stack-edit guard's comparison key is `a.map(photoSrc).sort().join('\u0000')` — sorting the raw entries would collapse every titled photo to `[object Object]`. The separator is written as an escape on purpose: it used to be a **literal NUL byte pasted into the source**, which rendered as a space, made `js/main.js` register as a binary file to `grep`, and made that one line unfindable by string search.
- The storage layer needed nothing: `deflate`/`inflate`/`blobIdsIn` all recurse into plain objects, so `{src:'data:…', title:'…'}` gets its `src` extracted to a blob ref and its `title` passed through.

**Gallery stacks — a folder entry is a photo *or* a bundle.** `folder.images` used to be an array of `src` strings; an entry can now also be `{images:[src, …]}`. A stack occupies **one grid slot**, so pagination, cross-page drag, folder-tab drops and delete all keep working untouched. Plain photos are still bare strings, so there is no migration.

- **`normalizeGalleryEntries()` is the load-time landmine.** The line it replaced was `f.images.filter(src => typeof src === 'string' && src)` — a cleanup for old empty slots that would have **silently deleted every stack (and the photos in it) on the next page load, then saved that**. Any future non-string entry type has to be taught to this function first. It also collapses a 1-photo stack back to a bare string and drops empty ones.
- **The drag-reorder write guard had the same assumption**: `reordered.every(src => typeof src === 'string')` refused to save any page containing a stack. It now checks "not an empty slot" instead.
- Blob GC is safe as-is — `collectGarbage`'s `scan` already recurses into objects and arrays, so photos nested in a stack count as referenced.
- Helpers: `isStack` / `stackImagesOf` / `entryCover` / `entryCount`.

**The lightbox counts two ways at once, and that is the whole design.** Arrows move by **photo** (`galleryLbFlat`, built by `flattenEntries()`; `galleryLbIndex` indexes it, and the `n / total` chip counts every photo in the folder including stacked ones). The thumbnail strip moves by **entry** (`galleryLbEntries`; `lbThumbWindow()` and `lbThumbStart` are entry indices) — a stack is one 64px slot showing *the photo currently being viewed*, with a `+N` corner tag. **Its pop-out must be `position:fixed` with JS-computed coordinates** (`openLbPop`): `.lb-thumbs` carries `overflow-x:auto` for narrow screens, and an absolutely-positioned pop-out above the strip is simply clipped away — it renders but is invisible. It opens on **click** and closes on a click anywhere else (a document-level listener that skips anything inside `.lb-thumb.pop-open`); hover-to-open was unusable because crossing the gap to the pop-out left the thumb and closed it. The active stack's thumb therefore does *not* get the jump-to-entry click handler — it is already the entry you are looking at. Mixing the two indices is the easiest way to break this; `lbCurEntryIdx()` is the only bridge. `openGalleryLightbox(entries, entryIdx, stackIdx, folder)` takes the folder's **live** array (not a copy) because stack editing mutates it in place; the one caller without a folder (a chat-bubble photo) simply can't stack-edit.

- **Behind cards** (`.lb-back-1..3`, max 3) are only what is *still ahead* in the current stack, so the pile thins to nothing on the last photo and the arrow then leaves the stack. Each keeps **its own aspect ratio** — `left/top:50%` + `max-width/height:100%` inside `.lb-stage` (which is exactly the current photo's box), so every transform must carry a leading `translate(-50%,-50%)`. Hidden while `.lightbox.zoomed`.
- **`LB_BACK_OFFSET` in JS must match `.lb-back-1..3` in CSS.** The values are duplicated on purpose: reading `getComputedStyle().transform` off three freshly-appended cards forces three layouts and visibly stutters the first frame. `lbBackTf(d)` treats `d = 0` as "where the main photo sits", which is what makes the rise/sink animations fall out of the same table.
- **Moving inside a stack is a card deal, and the two directions are exact mirrors.** `dealGalleryLightbox()` (▸) flings the current photo out to the **left** (`LB_DEAL_AWAY`) while `.lb-back-1` animates from its resting transform to identity. `dealBackGalleryLightbox()` (◂) runs it backwards: it commits *first*, then brings the new main photo in from that same thrown-away position while the photo you just left — now `.lb-back-1` — sinks from identity to its resting transform. Both commit on a `setTimeout`, never on an animation event: animation events never fire in a background tab and the photo would freeze half-gone. (Testing note: background tabs also throttle `setTimeout` to ~1s, so automated clicks need >1s between them or the `lbAnimating` guard swallows them.)
- **The pile always moves; `lbBackAnim` says how.** A caller sets it to `'fan'` (cards spread out from behind the photo, nearest first — the delay is keyed to `d` because DOM order is farthest-first), `'up'` (every card slides one level closer — set by `dealGalleryLightbox`, otherwise card 2 would teleport into card 1's slot) or `'down'` (one level further — set by `dealBackGalleryLightbox`, which is also how the photo you just left sinks into the pile, since it starts at `d = 0`). `paintLbStackBack` consumes it once and clears it; with nothing set it fans only when the pile appears from nothing. `openGalleryLightbox` resets `lbBackShown` so opening straight onto a stack fans out.
- **A card that was squeezed while it sat behind has to grow back.** Back cards are capped at the *current* photo's box, so a landscape photo waiting behind a portrait one renders at less than half size (measured 436px behind, 932px in front). `growLightboxFrom(fromW)` runs a scale FLIP on `#lightboxImg` after the swap, gated on the new photo's `load` because an `<img>` has no layout size until it decodes, and skipped when the difference is under 3% so same-shaped photos don't twitch.
- **`.lb-nav` needs `position:relative; z-index:3`.** The rotated back cards overflow `.lb-stage` and covered the arrows — both visually and for clicks, since they carry `pointer-events:auto`.
- **The thumb strip's "do I need to redraw?" test compares against what is *drawn*, never against `lbThumbStart`.** `markGalleryLbThumb()` skips the rebuild when nothing moved — that is what keeps arrow-stepping from remaking nine cells per photo. But `openGalleryLightbox()` and `refreshGalleryLb()` both assign `lbThumbStart = lbThumbWindow(...)` *before* calling in, so testing `want !== lbThumbStart` was comparing a value against itself: the signal was erased at the only moment it mattered. Re-opening the lightbox in the same folder therefore left the strip parked wherever it was — open entry 14 of 27, close, open entry 0, and the strip still showed 10–18 with the current photo nowhere in it. The other three conditions couldn't save it either: they all assume you are inside the *same* entry list, so a different character's first photo passed every one and left the **previous document's thumbnails on screen**. `renderGalleryLbThumbs()` now records `lbThumbShownStart`/`lbThumbShownFor`/`lbThumbShownN` — the window start, the entry array's identity, and its length — and `heavy` compares the wanted state against those. A folder *is* its own array, so identity catches folder and document changes while length catches stacking/unstacking within one. Swept all 729 entries across every OC and PAIR folder (31 of them containing stacks): the active cell is always present and always at the window position `max(0, min(e-4, n-9))`.
- **ARCHIVE's attachment lightbox slides like the gallery one, and shares its constants.** `slideArcLightbox()` mirrors `slideGalleryLightbox()` and reuses `LB_SLIDE_PX`/`LB_OUT_MS`/`LB_IN_MS`/`LB_EASE` on purpose — duplicating the numbers lets the two lightboxes drift apart when only one gets tuned. It commits on a timer rather than on `finish` for the background-tab reason above, and `renderArcLightbox()` (rebuilds the thumb rail) is now split from `paintArcLightbox()` (swaps the image and moves the `active` class) so stepping doesn't rebuild the rail underneath the animation. **There were two `function stepArcLightbox` declarations in this file** — the later one won, so the arrows, swipe and arrow keys all ran the un-animated version while the animated one sat unreachable. The duplicate is gone; don't reintroduce the name.
- **The fan waits for its images.** Opening a stack for the first time can hit photos whose blob hasn't arrived, and animating immediately made them pop in one at a time in load order — a visible stutter. The cards are held at `opacity:0` until every one reports `load`/`error` (or 500 ms passes), then the whole fan starts. This also hides the flash of the end state that `fill:'backwards'` would otherwise show.
- **`markGalleryLbThumb()` has a cheap path**: it only rebuilds the strip when the window moved or a stack is involved on either side; plain-to-plain moves just re-toggle `.active`.

**Stack reordering must key off the photo, never the slot number.** `dragend` used to rebuild the array from each cell's `dataset.s` (`order.map(i => entry.images[i])`), which duplicated photos: if `renderStackEdit()` ran while a drag was in flight — which it does, because `dragend` is `async` and re-renders after `await gallerySave()`, so starting a second drag before the first save lands re-renders under it — the dragged node was detached, `dragover`'s `insertBefore` **put the stale node back**, and the grid ended up with n+1 cells whose `dataset.s` values collided. Each cell now carries `_src` and the new order is read from that. Two guards back it up: `dragover` bails when `seDragEl.parentNode !== grid`, and `dragend` refuses to save unless the result is the same length and the same multiset as the current array (otherwise it just re-renders). Verified: normal reorder writes 4/4 with no duplicates; a re-render mid-drag leaves the grid at 4 cells and the array untouched; a stale cell force-appended to make 5 is rejected.

**Stack editing is edit-mode only and lives in the lightbox** (`#lbStackEdit`, left of the zoom button, `right:46px`), shown only when the current entry is a stack. `#stackEdit` overlays the lightbox: square cells, `draggable="true"` to reorder (so `initDragEngine` drives it on both mouse and touch), hover overlay with a big `✕` that **takes a photo out of the stack without deleting it** (it lands as a loose entry immediately after the stack — `removeFromStack` never drops a photo from the folder, and asks nothing, because nothing is lost), and 풀기 to splice the stack's photos back in place. Reordering rewrites `entry.images`, which also changes the cover (the first photo) — that is intended. Dropping to one photo auto-unstacks and closes the panel. Unstacking leaves `galleryLbIndex` valid because flattening in place doesn't move anything in the flat list.

**묶기** (`.gallery-select-stack`, in the select-mode fab row) merges the selected slots into one stack **at the position of the first selected slot**. Selected stacks contribute their photos first, in slot order, then the loose photos — so "add a photo to an existing stack" comes out as "appended to the back". Stacks never nest. Cross-folder stacking is impossible by construction: switching folder tabs already clears `gallerySelectedIdx`. Counts are by photo, not slot (`selectedPhotoCount()`), so a loose photo plus a 3-stack deletes as "4장". **`updateGallerySelectCount()` had never been called on thumbnail selection** — the "n개 선택됨" label was dead and the 묶기 button's enabled state depends on it, so the selection click now calls it. The label lives *inside* `.gallery-fab-row`, right of the trash; as its own block above the grid it pushed the whole grid down whenever select mode turned on.

**`#modalConfirm` is z-index 900, and that is load-bearing.** It used to be 200 — the same as `.lightbox`, which comes later in `index.html` and therefore won. Any `siteConfirm()` raised from inside the lightbox (stack edit's 풀기 and per-photo delete) opened *behind* it and looked like a dead button. It must stay above every overlay, including `.arc-lightbox` (700).

**Window palette is three variables that move together.** `--bg` (body ground), `--surface` (sidebar, topbars, punch margins) and `--surface-2` (one step darker: empty thumbs, hover fills) are one family; brightening only one breaks the step between them. Current values are **`#ffffff` / `#fbfaf6` / `#f6f4ee`**. They started as `#f4f1ea / #ece7d9 / #e2dbc8` and were lifted toward white by 30%, then 50% (`#faf8f5 / #f6f3ec / #f1ede4`), and finally the owner asked for the brightest of them to *be* white — so the last step was an **additive** shift of `+5,+7,+10` on all three rather than another percentage, which keeps the gaps between them byte-identical while pinning the top at `#ffffff`. Percentage lifting is no longer available now that the top is at white; move the three by equal amounts. Five places need `--bg` as a *translucent* colour and therefore can't use `var()`: `.topbar` and `.cards-topbar` (`rgba(255,255,255,.92)` behind a `backdrop-filter`), `.modal-close` and `.arc-kebab-btn` (`.9`), and `.pd-header-fade`'s gradient (`,0` stop). **Change `--bg` and those five must change in the same edit** — there is a comment on `:root` listing them. `--accent-soft` (`#f4dcce`) is deliberately *not* part of this family: it is `--accent` mixed into white, so it moves only when `--accent` does. The grain overlay is unaffected: its `brightness()` normalizes the texture to mid-grey, which is a no-op regardless of what's underneath.

**Sidebar profile block** — the gap above the name and the gap below the bio are both **38.75px**, and both numbers are measured, not chosen: sidebar padding 20 + `.profile-block` `padding-top:17.75` + the name input's own 1px on top; the input's 2px + `padding-bottom:36.75` on the bottom. **Move one and you must move the other.**

That empty space has to live in `.profile-block`'s padding, not in the bio box — this is the whole point. When it was `min-height:44px` on `.profile-bio` instead, a *two*-line bio still fitted inside the box and nothing moved; growth only started at three lines. `.profile-bio` is now exactly as tall as its text (`min-height` is one line, for the empty case) and `overflow:hidden`, with `autoGrowBio()` (from `renderAll()` and on `input`) setting the inline height to `scrollHeight`. **It must blank the height to `0px` before measuring, never `auto`** — `auto` on a textarea means the `rows` attribute (2 by default), so a one-line bio measured 39px instead of 21.25px and the box appeared not to shrink. Growth pushes the divider and the whole nav down, which is intended. Chrome returns an integer `scrollHeight`, so multi-line heights land within ±0.5px of the exact line multiple.

**Paper grain overlay** — `.paper-grain` is a fixed, `pointer-events:none` full-viewport layer that gives the whole page (including the red page margin) a printed-paper texture. Three things about it are load-bearing:

- **It is an `<img>`, not a `background-image`.** Texture photos routinely carry an EXIF orientation tag; `<img>` honours it in every engine, `background-image` does not, so a background version can render rotated 90°. `img/paper-grain.jpg` is also the repo's only binary asset — unlike everything else on this site it is a static file, so it is browser-cacheable and costs nothing after the first visit. It sits at the very end of `<body>` so it never blocks first paint.
- **`mix-blend-mode: overlay`, not `multiply`.** Multiply darkens every channel equally and turned the `#EF3921` page red muddy. Overlay only pushes light areas lighter and dark areas darker, so hues survive.
- **`filter: brightness()` must be re-derived whenever the texture image changes.** Overlay's no-op point is mid-grey; a texture whose *mean* luminance isn't 0.5 shifts the entire page's brightness. The filter normalizes that: `brightness = 0.5 / mean`. The current image measures 0.798, hence `brightness(.627)`. Measure a replacement (draw it to a canvas and average the luminance) and update the number — otherwise the whole site gets brighter or darker and it will look like a color-palette bug.

`--grain` in `:root` is the only strength knob (1 = full, lower = fainter); `soft-light` is the gentler alternative to `overlay` if it ever reads as too much. `z-index:50` deliberately places it above all in-page content (which tops out at 20) but **below** the mobile drawer (55–60) and every modal/lightbox (100+), so modals render clean — verified with `elementFromPoint` and by comparing z-indexes. Measured cost is zero (16.7 ms median frame time with and without). Hidden in `@media print`.

**Switching menus goes through `activateView(view)` — nothing else may toggle `.view.active`.** All three entry points (the nav button, `openNavSection`, the ARCHIVE sub-menu) call it, and it adds `.view-enter` so the new screen rises 20px and fades in over `.42s`. It is also the **last line of defence for edit mode** — moving anywhere but `archive-detail` ends ARCHIVE's edit mode, and moving anywhere but the two detail screens closes the LOG screen; see the unsaved-changes guard for why. Three more constraints baked into it: it animates **only when the view actually changes** (picking another PAIR category or ARCHIVE sub-category re-runs the same view, and re-animating that every time is exhausting); it does **not** fire on first paint, because `#view-home` is already `.active` in the HTML and `window-in` is already lifting the whole window; and `.main:has(.view.view-enter)` hides overflow for the duration, because a view is `height:100%` and pushing it down 20px otherwise flashes the orange scrollbar. The class is stripped on a timer (`VIEW_ENTER_MS`) so `animation-fill-mode:both` doesn't leave `transform`/`opacity` pinned.

**A LOVE INTEREST card can carry a link** (`card.link`, a plain string; absent on older cards, and `''` means none — it is cleared to `''` rather than deleted so a merge-style write can't leave the old value behind). In edit mode `🔗` sits immediately left of `📷` and opens `#modalCardLink`; in view mode clicking the card's **photo** opens the link in a new tab (`window.open(…, '_blank', 'noopener')`), and a card with no link does nothing. - **The two buttons share one flex row, `.dc-tools`.** `createAdjustable` hides `📷` with an inline `display:none` whenever the card has no photo, so a separately positioned `🔗` would be stranded away from the corner; in a row, whichever survives closes up. `.dc-tools .adj-change{position:static}` undoes the camera's own absolute placement inside that row only.

- `commitCardLink` refuses to write if the card was deleted while the dialog was open (`state.cards.includes(c)`).

**HOME cards are greyscale until hovered** — `filter:grayscale(1)` with a `.5s` transition on `.dc-adjustable` only, never on `.dream-card`. Filtering the card would drain the gradient, the text and the ✕/⠿ buttons along with the photo. **Header bars** — `.topbar` (PAIR/ARCHIVE) and `.cards-topbar` (LOVE INTEREST) are pinned to a fixed `height:60px`, not padding-driven. That number is the edit-mode height (14+14 padding + a 31px button + 1px border); without it the bar collapsed to 44px in view mode and the LOVE INTEREST bar sat at 50px, so the title line jumped when switching views or logging in. **`.li-icon`'s explicit `width` must equal that height minus the 1px border** (59px) — Safari can't derive an `aspect-ratio` width from a stretched height, so the square is hard-coded. On phones the padding drops to 9px so the 40px touch-target buttons still fit inside the same 60px.

**Responsive layout** — the site was desktop-only until responsive support was added; all of it lives in `@media` blocks at the **end of `css/style.css`**, plus a handful of existing `:hover` rules wrapped in `@media (hover:hover)` inline. Two breakpoints: `769–1100px` (tablet — releases the 16:9 letterbox, keeps the sidebar) and `≤768px` (phone). **Nothing applies above 1100px, so the PC design is untouched** — after any phone change, re-measure a few desktop anchors (detail bar `753×66`, `.pd-info-grid` `212 / 297 / 212` with areas `"char center persona"`, detail gallery `5 × 3`, `documentElement.scrollWidth === innerWidth`).

- **A detail gallery's thumbnails must keep `aspect-ratio:1/1` on phones.** Desktop turns it off (`.pd-tab-pane-gallery .gallery-thumb{aspect-ratio:auto}`) because there the grid divides a known height, so `1fr` rows are already sized. On a phone `.gallery-grid-wrap` is `flex:0 0 auto`, so the only thing that can size a `1fr` row is its content — and `.gt-img` is `position:absolute` and contributes none. **A page completely full of photos therefore collapsed to 2px rows.** Pages with empty `.gallery-slot`s (which do carry `1/1`) looked fine, which is why it appeared to depend on the folder. Anything that sizes a row from content on a phone deserves the same suspicion.
- **A phone-only rule that restates `display` on a `[data-editonly]` control must be scoped to `body.logged-in`.** The touch-size rule for the HOME cards' ✕ and ⠿ was written as `.dream-card .dc-del{…display:flex}` — two classes, which outranks the global `[data-editonly]{display:none}` — so the delete button was visible in reading mode on phones and nowhere else. (`.dc-drag` escaped it only because `body:not(.logged-in) .dc-drag` happens to be one specificity point higher.) Anything that resizes an edit-mode control for touch has the same trap.
- **HOME's `︾ ︽` page buttons are gone.** They were the phone stand-in for the wheel, and the owner had them removed once the swipe worked — the markup, the CSS and `initHomeTouchNav`'s two handlers all went with them. The swipe (and, on desktop, the wheel) is now the only way between the intro postcard and LOVE INTEREST.

**Dragging: the browser's drag-and-drop is not used anywhere.** `initDragEngine()` in `main.js` is one delegated `pointerdown`/`pointermove`/`pointerup` listener that serves **both** mouse and touch. It clones the source into a `.drag-ghost` that follows the pointer and **dispatches `MouseEvent`s named `dragstart`/`dragover`/`dragleave`/`drop`/`dragend`** at the right targets, so every existing handler runs unchanged — including the gallery's dwell-on-arrow page flip. If you add a new drag site, just set `draggable="true"` and it works, on both inputs; don't add pointer code.

Two reasons it ended up this way, and both matter if you are tempted to go back:
- HTML5 DnD does not fire on touch **at all**, which is why the engine existed for touch first.
- The picture the browser sticks to the cursor is **semi-transparent and cannot be styled** — not by CSS on the source (that only fades the copy left behind on the page), and not by `setDragImage`, which lets you replace the *content* while the browser re-applies its own alpha. This is Chromium-wide: Chrome and Edge behave identically. The owner asked for the dragged thing to look normal, and this is the only way to get it. (Stickers had already been written this way, for exactly this reason.)

The one place native DnD is still allowed is **inside a text editor**: `[contenteditable="true"]` is skipped, so text selection and iOS's magnifier keep working, and an image dragged inside a post body still uses the browser's drag. That path keeps a `setDragImage` call that swaps in an exact clone — it cannot fix the transparency, but it does drop the padding/outline the auto-generated snapshot carries. A capture-phase `dragstart` listener cancels the native drag for everything else (`e instanceof DragEvent` distinguishes a real drag from the synthetic events the engine fires).

Two details in the ghost that are easy to get wrong:
- **`.drag-ghost.dream-card` drops both its shadow and its background.** A LOVE INTEREST card has no border — photo and text sit straight on the page — so a shadow invents a box that was never there, and the card's own `background:var(--bg)` drags a white panel along behind the text.
- **Two ghosts are deliberately translucent**: `.drag-ghost.log-card` and `.drag-ghost.arc-nai-thumb` (`opacity:.7`). Those two are dropped *onto folder tabs* rather than reordered, and an opaque card covers the tab you are aiming at. Everything else stays fully opaque — that was the whole point of the rewrite. OOC/ETC rows need no rule: a `<tr>` has no background, so it already shows through.
- **The source is hidden (`visibility:hidden`) for the duration**, not left in place. Two copies of the same thing — one under the cursor, one in the list — read as a bug. `visibility` rather than `display` so the slot stays: `dragover` moves the (hidden) source through the list, so that gap *is* the drop preview.
- **A `<tr>` cannot be cloned on its own.** Lifted out of its table it loses the concept of a cell and the row's text collapses onto one line (this actually shipped for a moment). `makeGhost()` wraps a row clone in a `<table>` carrying the original's class, `table-layout:fixed`, and each cell's measured width. Everything else clones as-is — this codebase styles by class, not by ancestor, so a clone parented to `<body>` keeps its look.

Mouse and touch differ in exactly one thing — **when the drag starts**. Touch waits 400 ms and treats earlier movement as a scroll; the mouse starts after 4px of movement, because making a mouse wait feels broken and there is no scroll gesture to disambiguate from. `body.dragging-now` is set for the duration (it kills text selection, and the page/side pagers check it so a drag never flips a page). Wheel-only interactions (Home page flip, gallery paging) got touch equivalents too: a swipe handler for HOME, and for the gallery a swipe plus tappable `︽`/`︾` arrows (`pointer-events` is opened up on phones only — their tap padding is horizontal-only so it can't cover the first thumbnail row).

**Sticker shadows are a saved on/off setting.** The checkbox sits in the drawer's header row (`#sdShadowChk`, `data-editonly` — it changes what every visitor sees, so it is not a per-device preference and lives in `SCALAR_KEYS` as `stickerShadow`). The style is `drop-shadow`, never `box-shadow`: stickers are cut-out PNGs, so a box shadow would draw a rectangle that isn't there. `applyStickerShadow()` syncs both the layer class and the checkbox and is called from `renderAll()`; `renderStickers()` also sets the class, since it rebuilds the layer.

**Stickers float over the whole page, and their permission split is unusual.** `state.stickers` (a `SCALAR_KEY`, `[{id, src, lines, w, x, y, flip, out}]`) draws into `#stickerLayer`, a `position:fixed; inset:0; pointer-events:none` layer at **z-index 30** — above everything inside `.app-window` (max 20) and above the red page background, **below `.paper-grain` (50)** so the texture passes over a sticker too, and below the mobile drawer (55–60) and every modal (100). The owner asked for "above the window and background, below modals"; sitting under the grain is the extra choice, made so a sticker reads as being on the same sheet of paper. Raising it to 51 is a one-line change if that ever needs revisiting.

The split the owner asked for, and the reason it costs code:
- **Taking a sticker out of the drawer, dragging it, and resizing it work in view mode.** Adding, deleting and editing the phrases are `[data-editonly]`.
- **But a visitor cannot write to Firestore**, so `commitStickerChange()` and the resize handler save only when `isLoggedIn`. A position changed in view mode lives until reload and then snaps back. That is deliberate, not a bug to "fix" by saving unconditionally — the write would just fail.
- **On phones there are no stickers at all now.** `@media (max-width:768px)` hides `.sticker-drawer` *and* `.sticker-layer`, and `positionStickerDrawer()` closes an open drawer and returns early instead of placing it. The clip had no punch margin to sit in on a phone and ended up floating awkwardly over the topbar; the owner's call was to drop the feature there rather than find it a better corner. **Keep the `stickerLocal` split below anyway** — with the drawer gone there is no way to pull one out, so the phone path now simply yields an empty layer, and it is what still guarantees a phone can never write to `s.out` / `s.x` / `s.y` while the viewport is being resized across the breakpoint.
- **On phones the saved `out` flag is ignored entirely.** `stickerOut()` reads a module-level `stickerLocal` (`Set` + `Map`, never persisted) when `isMobileWidth()`, so a phone always starts with an empty screen and shows only what was pulled out in that session. `setStickerPos()` likewise writes to `stickerLocal.pos` instead of `s.x/s.y` there. Without that split, pulling a sticker out on a phone would move it on the PC too. `initResponsiveWatch()` re-renders on the breakpoint change because the two paths read different sources.
- **`flip` is a CSS-only mirror, and it belongs on the `<img>`, never on `.sticker`.** 좌우반전 in the add/edit modal toggles `stickerDraftFlip`, saves as `s.flip`, and shows up as a `.flipped` class on the sticker, on its drawer thumbnail, and on the modal preview — all of which resolve to `img{transform:scaleX(-1)}`. Putting the mirror on `.sticker` itself would collide with `st-drop`/`st-squish`, which animate that element's own `transform` and would wipe it out mid-motion. The stored image is untouched, so flipping is free and reversible.

**The drawer is a handle at the bottom of the sidebar**, sitting in the normal flow just above the music widget (`.sticker-drawer{margin-top:auto}` is what pins that whole group — handle, widget, storage meter — to the bottom, so removing it also unpins the two below). It used to be a paperclip biting the window's right punch margin, positioned by measuring `.app-window`; when the punch margins went, so did that. **`positionStickerDrawer()` still exists but no longer positions anything** — all it does now is close an open drawer when the viewport crosses into phone width, so a drawer left open doesn't spring back out on the way back to desktop. The panel itself rises *above* the handle (`bottom:100%`), which is why the drawer needs no room reserved below it.

This placement also **sidesteps the topbar entirely**, which an earlier in-window version could not: the button cluster reaches 163px in from the right on PAIR/OC and **249px on ARCHIVE**, and a clip anywhere near the corner sat exactly on 선택 (measured 1353–1387 against 1336–1387).

**The clip's "behind the paper" look is one `clip-path`, not layering.** `.sc-outer` is a stroked rounded `<rect>` (the complete outer loop, drawn over everything) and `.sc-inner` is the inner ∩ **clipped to the region above the paper line** (viewBox `y < 40` of 100), so its two arms vanish at the window's edge exactly like a real clip. The clip element is rotated `-11deg`, so the clipping rect carries a compensating `rotate(11 20 40)` — otherwise the cut-off line tilts with the wire and stops matching the horizontal paper edge. The card underneath is `rotate(-3deg)` and its `top` is tuned so its corner reaches the same bite line. Opening runs `sd-slip` (`translateY(-26px) rotate(-10deg)` → `rotate(-3deg)`), closing replays it with a **separately-named** `sd-slip-r` + `animation-direction:reverse` (same trap as the login sheet — reusing the name makes Chrome keep the finished animation's `currentTime` and jump instead of rewind). There is no ✕: the corner is where the clip is, so the clip toggles and Escape closes.

Thumbnails are **CSS multicol, not a JS masonry**: `.sd-list{column-count:2}` with `break-inside:avoid` and `img{width:100%;height:auto}` gives the brick-stacked, aspect-preserving look for free. The scrolling `max-height` must sit on a **wrapper** (`.sd-scroll`), never on the multicol element — a height-constrained multicol fragments sideways into new columns instead of scrolling.

**Phrases are added one at a time, on purpose.** The first version split a textarea on `\n`, which made a multi-line phrase impossible to enter. `stickerDraftLines` is now a real array: 추가 pushes the textarea's contents (each line trimmed, blank leading/trailing lines dropped, inner newlines kept), each entry gets its own row with a ✕, and the save handler calls `addStickerLine()` once more so a phrase typed but not yet added isn't silently lost.

Three implementation details worth keeping:
- **Dragging is `pointerdown`/`pointermove`/`pointerup` with `setPointerCapture`, not HTML5 DnD**, precisely because the owner asked that the sticker *not* go translucent while being dragged — the browser's own drag ghost is semi-transparent and cannot be styled. This site was the first to be written that way and later became the argument for doing the same everywhere (see the drag section). It has its own pointer code rather than going through `initDragEngine()`, because a sticker is not reordered into a list — it is moved to an arbitrary x/y — and it needs no touch code of its own (`touch-action:none` on `.sticker` plus pointer events covers both).
- **Under 5px of travel counts as a press, not a drag**, and a press is what raises the speech bubble (`speakSticker`). With two or more phrases the previous one is skipped, so a repeat click always changes the text.
- **Resizing sets `width` only.** `.sticker img` is `width:100%; height:auto`, so the aspect ratio is preserved for free; writing a height as well is what would break it. Clamped 40–640px.

Two motions the owner picked by name, and **both are on the sticker itself**: coming out of the drawer is `st-drop` (falls from −92px and bounces twice — translate only, no squash; she asked for the landing squash to come back out) and a press is `st-squish` (`1.16/.84` wide → `.92/1.1` tall → settled). **The speech bubble has no animation** — it was tried there first and moved to the sticker on her instruction. The drop is opt-in per sticker via `stickerDropIds`, a set that `renderStickers()` reads and then **clears**: the layer is re-rendered for unrelated reasons (login state, breakpoint), and a persistent flag would make every sticker on screen fall again. `squishSticker()` removes the class, reads `offsetWidth` to force a reflow, then re-adds it — toggling in one synchronous block is a no-op in Chrome, so a second press would otherwise do nothing.

**Both classes must be taken off again when their animation ends, and that is not cosmetic.** `.dropping` and `.squishing` are two same-specificity rules setting `animation` on the same element, so only one applies at a time — which means removing `.squishing` while `.dropping` is still attached flips `animation-name` back to `st-drop` and **replays the fall**. That shipped: pressing a freshly-added sticker made it squish and then drop again, and a reload "fixed" it only because `stickerDropIds` was empty by then. Both are cleared by `setTimeout` (`STICKER_DROP_MS` / `STICKER_SQUISH_MS`, which must match the CSS durations), and `squishSticker()` drops `.dropping` first. **`animationend` is not usable here** — a background tab renders no frames, so the event may never arrive and the class would stay forever.

**The sidebar's bottom strip is a Firestore usage gauge**, `#storageMeter`, edit-mode only (`[data-editonly]`, so it needs its own `display:block` rule — the shared one is `inline-flex`). It sticks to the bottom via `margin-top:auto` because `.sidebar` is a flex column. `renderStorageMeter()` reads `SiteStore.storageStats()` and is called at boot, from `applyEditMode()`, and from `SiteStore.onStorageChange()` — which fires after load, after every successful flush, and after garbage collection. It turns red past 80%. The numbers and their caveats are in the `meta.blobSizes` note above; the only thing to remember here is that **the gauge never fetches anything**, so putting it on screen costs nothing per render.

**Click sound.** Pressing the left mouse button anywhere plays `audio/click.mp3` — on `pointerdown`, not `click`, because `click` arrives on release and the sound then lags the finger. Mouse only (`pointerType === 'mouse'`); taps on a phone stay silent. It is Web Audio rather than `<audio>`: an element re-prepares the file each time and cuts off the previous play when pressed quickly, whereas a decoded `AudioBuffer` can be started any number of times at once. Three things to keep:
- **The `AudioContext` is created on the first press, not at load.** A context created before any user gesture starts suspended and Chrome logs a warning on every page load. The 5KB file is fetched at load, decoded on that first press, so only the very first sound is a few ms late. `decodeAudioData` consumes its `ArrayBuffer`, so decoding runs exactly once (`clickDecoding`).
- **`CLICK_SOUND_SKIP` (18ms) is the file's leading silence** — MP3 encoders pad the start — measured by decoding and scanning for the first sample above 2% of peak. Playback starts from that offset; the file itself is untouched. **Re-measure if the sound is replaced.** The clip is 228ms with a peak of 0.99, which was too loud as-is — the owner asked for it quieter, so `CLICK_VOLUME` is `0.4` (about −8 dB). That constant is the only knob.
- **The file has its own `?v=` in `CLICK_SOUND_URL`**, independent of the site asset version — bump it only when the audio changes.

**The browser tab title follows the HOME site name.** `syncDocTitle()` sets `document.title` from `state.siteName` in `renderAll()`, on `input` while typing (saving still happens on `change`), and on `change`. An empty name falls back to whatever `<title>` was at load (`홈`), because a blank title makes browsers show the URL instead. Before data arrives the static `<title>` shows briefly. `apple-mobile-web-app-title` is deliberately left alone — iOS reads it once, when the icon is added.

**Sidebar music widget** — the old name/bio block is gone from the sidebar; `state.profile` is still loaded and saved, so restoring the markup would bring the text back. In its place a widget drives a YouTube IFrame player: `musicList` (a `SCALAR_KEY`, `[{id, videoId | src, title, artist, cover?}]`) holds the playlist, while **volume lives in `localStorage`, not Firestore** — it is a per-device preference and syncing it would change the volume on her other machines. Two things are easy to get wrong here:
- **The player element must stay inside the viewport.** `display:none` or `left:-9999px` makes Chrome treat it as not worth rendering and playback sticks in `BUFFERING` forever. `#ytHost` sits at the bottom-left corner at its real 200×150 with `opacity:0`.
- **There is no autoplay.** Browsers block sound without a user gesture, so the first song is `cueVideoById`'d (loaded, paused) and waits for ▶. Don't "fix" this with `loadVideoById` on boot — it just fails silently and looks broken.
`musicVolume()` guards `raw == null` explicitly because `Number(null)` is `0`, not `NaN` — reading the unset key straight through silenced the widget on first visit.

**The LP is a turntable: a black record with the album art as its label, and a tonearm that swings onto it while playing.** It replaced a line-drawn LP whose orange progress ring showed elapsed time; the owner asked for an ordinary record from a reference picture, so the ring and everything that fed it (`.mb-lp-prog`, `LP_PROG_LEN`, `resetLpProgress()`) are gone — elapsed time is still the `0:00 / 0:00` text. `#mbLp` is `72×64` with a `72×64` viewBox, so one SVG unit is one CSS pixel; the extra 8px over the old 64 is where the arm rests. Things it depends on:
- **Only `.mb-disc` spins**, not the SVG. The arm and `.mb-sheen` (a static diagonal highlight, clipped to the record) must stay still — real vinyl reflections don't turn with the record. Rotating a group *inside* an SVG with CSS needs **both** `transform-box:view-box` and a `transform-origin` in viewBox units (`29px 32px` for the disc, `64px 8px` for the arm's pivot); without them the group spins about (0,0) and flies out of the widget.
- **The arm's `rotate(25deg)` is measured, not picked.** At rest its head sits at (64,47), 35px from the record's centre — off the 28px record. At 25° it lands at (47.5,43.3), 21.7px out: inside the rim, clear of the 11.5px label. Change the record radius, the label, or the arm length and re-measure.
- **A plain record needs something asymmetric to look like it is turning.** Grooves are concentric, so without art the default label carries an off-centre `--accent` dot (`.mb-label-dot`). With art, the picture does that job.
- **Colours are literal, not theme tokens** — a record is black on any theme: disc `#151515`, grooves `#ffffff` at 7%, label `#e9e4da`, arm `#ffffff` outlined `#b9b3a6`, base `#efece6`.
- `prefers-reduced-motion` stops the spin and removes the arm's transition.

**Album art is `song.cover`, and `normalizeMusicList()` has to carry it.** That function rebuilds each song from the fields it knows, so a new field that isn't copied there is **deleted on every load and the deletion saved** — the same landmine as `normalizeGalleryEntries()`. Art can be picked in the add form (`#mmCoverBtn`, beside the audio file picker; it applies to YouTube songs too) and, for songs already in the list, from the small dashed square in each `.mm-row` — without the per-row cell, adding art to an existing file song would mean re-uploading the audio. Both go through `pickCoverImage()`, which compresses to **320px / ~80KB** (`COVER_MAX_DIM`, `COVER_TARGET_CHARS`) rather than the site default 1800px: the label is drawn 23px wide, and full-size art would cost as much storage as a gallery photo per song. It is a data URL when picked and becomes a `blob://` ref on save like any image, so `paintLpArt()` resolves it with `imgUrl()` and registers `whenImgArrives`. There is no "remove art" control yet. `.mm-kind` is a fixed 32px so the art cells line up between FILE and YT rows.

**The song name marquees instead of ellipsizing.** `setMarqueeText(box, text)` puts the string in an inner `.mb-mq` span and `applyMarquee(box)` compares `inner.scrollWidth` against `box.clientWidth`; if it overflows it writes `--mq-dist` and an `animation-duration` and adds `.scrolling`, which slides the span left by exactly the overflow, pauses, and slides back (`@keyframes mb-marquee`, ~16px/s). Two details: the measurement is repeated on a **700 ms `setTimeout`** because a webfont arriving late changes the text width and `requestAnimationFrame` never fires in a background tab, and `.mb-title`/`.mb-artist` must keep `overflow:hidden` with **no `text-overflow`** — an ellipsis and a marquee cancel each other out.

**The playlist (`#mbPlaylist`) is an in-flow accordion inside `.music-block`, not a floating panel.** It was tried as a `position:fixed` pop-out first (anchored beside, then under, the widget) and rejected: the owner wants it to **push the menu down** rather than cover it, with no border or shadow so it sits on the sidebar's own ground. That means there is no placement code at all — the DOM order does the work, which is also why it must live *inside* `.music-block` rather than as a sibling (the block's `padding-bottom:26px` is the gap to the menu, and a sibling would add the sidebar's own 16px flex gap on top).

Two numbers are linked: `.mbp-list{max-height:104px}` shows exactly five rows, where a row is `3 + 14 + 3 = 20px` and four `1px` hairlines sit between them (`.mbp-item + .mbp-item{border-top}` — between only, never after the last). **Change the font size or the row padding and that 104 has to be recomputed**, or you get a clipped sixth row instead of a clean five.

Opening runs `@keyframes mbp-drop` (`max-height 0 → 116px`, opacity, `translateY(-8px) → 0`) so it reads as coming down from above. It has to be an **animation, not a transition** — the element goes from `display:none`, and a transition cannot run on the frame an element starts being rendered. The 12px gap above the list is `padding-top` rather than `margin-top` for the same animation: margin sits outside `max-height`, so the menu would jump that 12px before the list started opening. (Testing note: toggling the class off and on in one synchronous block produces **no** animation at all — Chrome sees no net class change. Let a frame pass in between or you will think it is broken.)

Only the LP and Escape toggle it. An outside-click-to-close listener was removed when it stopped floating: clicking a menu item would collapse the list and yank the whole nav upward mid-click. Rows show a zero-padded number (`.mbp-no`) before the title. The list is read-only by design — reordering and deleting stay in the 노래 관리 modal — and clicking a title jumps to that song, loading before rendering for the same reason `stepMusic` does (a render-time `cue` would overwrite the play request).

**Reordering in 노래 관리 is a live FLIP, and its handlers must not close over the index.** `dragover` moves the row with `insertBefore` and replays `flipByKey`, `dragend` reads the order back out of the DOM — re-rendering mid-drag would destroy the dragged node and `dragend` would never fire, exactly like the sidebar categories and the gallery. Because nothing re-renders until the drop, the ✕ button resolves its song by `s.id` rather than by position, and `dragend` re-finds the playing song by id so it keeps playing from its new slot.

**Write batching** — `main.js` calls `storageSet` very frequently (e.g. on every `input` blur). `firebase-store.js` debounces actual Firestore writes (~1.2s), diffs against the last-saved JSON per document so unchanged items aren't rewritten, and only marks a change as "saved" after the write actually succeeds (a failed write keeps the key `dirty` and retries automatically) — this was a deliberate fix for a bug where failures were recorded as successes and silently dropped edits.

**List order is a separate field and needs its own diff.** Array order is carried by `__order` on each doc, written in `flush()` and re-applied by the `.sort()` in `loadAll()`. But `savedJson` — the per-doc change detector — stores `stripMeta(it)`, which deletes `__order`. So **reordering a list changed no document's JSON and wrote nothing**: HOME card drags reverted on reload, and PAIR/OC lists drifted out of creation order (only items whose *content* also changed ever got a fresh `__order`, so the rest kept stale numbers — that drift is what `byNewest()` was papering over). Fixed with a parallel `savedOrder` map, populated in `loadAll()` from the post-sort index and compared alongside the JSON: `if (savedJson[sk] !== json || savedOrder[sk] !== i)`. It is assigned from `nextOrder` only after the batch commits and dropped with `dropSaved`, exactly like `savedJson`. **Any future per-doc metadata that lives outside the stored JSON needs the same treatment** — if it isn't in the compared string, changing it alone is invisible to the diff.

**Save-state visibility** — `SiteStore.onSaveState(cb)` fires `'saving' | 'saved' | 'error'`; `main.js` renders this as a fixed indicator (bottom-right) via `initSaveIndicator()`. Don't reintroduce silent failure here — if you touch the flush/retry logic in `firebase-store.js`, make sure errors still propagate to this indicator rather than only `console.error`.

**Signing in happens on the HOME postcard, not in a modal and not in the sidebar.** The old `.login-widget` (LOCKED/UNLOCKED badge + 로그인 button) and the `#modalLogin` overlay are both gone. What replaces them:
- **One text button does all three jobs**: `#postcardBtn`. Signed in → sign out. Signed out with the sheet closed → open it. Signed out with the sheet **open → it is the submit button**; there is no LOGIN or 취소 inside the box. Its label *is* the state readout, which is why the badge could be deleted: `Sign in` / `Sign out` (and `...` while `signOut()` is in flight, since a backed-up flush can take seconds). `applyEditMode()` sets it, through `loginLabel()` — see the sign-in button note in the HOME entrance section, which is where its look and its two underlines are described.
- **It is a grid cell of its own** (`.hg-login`), not a button floating under the postcard. It began as `position:absolute; top:100%` beneath `.intro-card`, because the card is vertically centred in `#home-intro-page` and a button in normal flow pushed the card up by half its height. That is no longer how it sits — the HOME grid gave it a cell — but the constraint that produced it still holds: **nothing may be added to `.intro-card`'s flow**, or the card stops being centred.
- **`#loginSheet` covers the postcard exactly** (`inset:0` on the card, `padding:0 24px` so the box's width equals the banner's) and opens in place rather than as an overlay — the ask was for it to feel like moving to a login page. Measured: box top/height identical to `.intro-card`, left/width identical to `.intro-banner`. `.intro-card` gets `.login-open`, which hides its other children with **`visibility:hidden`, never `display:none`**: the card must keep its height or the box is the wrong size and the page twitches. The **postcard button is excluded from that rule** (`:not(.postcard-btn)`) because it is the submit control, and for the same reason the outside-click-to-close handler must skip it — otherwise the `mousedown` closes the sheet before the `click` can log you in.
- **The border draws from two opposite corners.** `.ls-box` has no `border`; four absolutely-positioned `.ls-line` spans scale from 0 — top and left from the **top-left** corner, bottom and right from the **bottom-right** — and `.ls-inner` fades in (opacity only, no rise) on a `.42s` delay once they have nearly met. Same `display:none` rule as the playlist: these are animations, not transitions. The easing is `cubic-bezier(.4,0,.2,1)` rather than the site's usual `(.22,1,.36,1)`, which was 96% drawn at the halfway point and looked like the lines simply appeared.
- **Closing replays the same animations backwards, and the keyframes must have different names** (`ls-draw-x-r` / `ls-draw-y-r` / `ls-fade-r`, played with `animation-direction:reverse`). This is the whole trick: if the closing rules reuse the *opening* animation's name and only change direction, Chrome does not start a new animation — it **updates the running one in place and keeps its `currentTime`**. The opening animation has long since finished, so that time is past the end, and flipping direction there jumps straight to the start pose instead of rewinding. It shipped that way once and looked like no animation at all. Duplicated keyframes going 0→1 plus `reverse` (rather than hand-written 1→0 keyframes) keep the easing curve an exact mirror.
- **The postcard fades back in afterwards** (`.intro-card.login-back`, opacity only). Removing `.login-open` alone snaps the hidden content back into place. `#postcardBtn` is excluded from both rules — it stays visible the whole time, so fading it would make it blink.
- **`closeLoginSheet()` must not clear its own timer when it is already closing.** A successful login calls it **twice**: the auth listener fires *during* `signIn()`'s await, so `applyEditMode()` gets there first and starts the close, and then `submitLogin()` calls it again. The early-return for "already closing" originally sat *after* `clearTimeout`, so the second call cancelled the timer that removes `.open`/`.login-open` — the sheet animated to invisible and the postcard stayed hidden behind it, leaving a blank white page until you navigated away and back. Clear the timers only on the path that actually re-arms them.
- Closing: Escape, or a `mousedown` on `#home-intro-page` outside both `.ls-box` and `.postcard-btn`. While it is open the HOME wheel/swipe page flip is suppressed, or scrolling would carry you to the cards page mid-login. `markCurrentView()` also closes it with `closeLoginSheet(true)` (no rewind — it is off-screen by then) so leaving for another menu and coming back shows the postcard, not a stale login box.
- **The layout is a postcard back**: EMAIL top-left, PASSWORD bottom-right, an empty perforated stamp top-right, `img/postmark.png` (the owner's own artwork, colour untouched) rotated `-9deg` across it, and a faint vertical rule down the middle. `column-gap` is **twice** `.ls-box`'s horizontal padding so the two fields sit as far from the centre rule as from the outer edge. The postmark is a raster on a white background, so it carries `mix-blend-mode:multiply` to drop the white and leave the ink — **do not "fix" this by recolouring or redrawing it.** Fields are three ruled lines each (`.ls-input` + two `.ls-rule`, all 26px) rather than boxes; the phone block drops the decorative rules, the stamp, the postmark and the divider, because the box there is only as tall as the postcard (~198px).
- `.login-error` and `.login-modal` are **still used** by the folder and folder-unlock modals — don't delete those rules along with the login markup.

**Auth model** — Firebase Authentication (email/password), not the old hardcoded `CREDENTIALS` object (removed). `window.SiteStore.isAdmin` is true only when the signed-in user's UID matches `ADMIN_UID` from `firebase-config.js`; the client-side check is a convenience, the Firestore security rules in `firestore.rules` are the actual enforcement point. `js/main.js`'s login modal collects an email (not a username) — see `loginErrorMessage()` for the mapping from Firebase auth error codes to Korean UI messages if you need to add a new one (e.g. new failure codes from console changes like unauthorized domain).

**GitHub Pages deployment** — this repo must be named exactly `xngsuii.github.io` to serve from the domain root (user site, not project site); renaming it changes the site URL, and Firebase's authorized-domains list (console → Authentication → Settings) must contain whatever domain the site is actually served from or login will fail with `auth/unauthorized-domain`.

## Icons

There are **two** marks, deliberately different, both drawn from `img/postmark.png` (the airmail cancellation stamp on the login sheet):

| | app icon | favicon |
|---|---|---|
| source | `img/app-icon.svg` | `img/favicon.svg` |
| ships as | `app-icon-180.png` | the SVG + `favicon-16/32/48.png` |
| ground | solid `#EF3921`, **no transparency** | **transparent** |
| ink | white | `#EF3921` |
| composition | stamp left, waves running off the right edge, stroke 7 | stamp centred, **no waves**, stroke 15, bigger plane |

The favicon is not the app icon recoloured. It renders at **16px**, where stroke 7 becomes 0.6px and disappears; the small-size version drops the waves, centres the stamp and doubles the stroke. Keep them in sync in spirit, not geometry — changing one does not imply changing the other.

The favicon has no background because tab bars are light in some browsers and dark in others; orange ink reads on both, while a filled tile looks like a sticker on one of them.

### Home-screen app icon (iOS)

`index.html`'s head carries four tags that turn "홈 화면에 추가" into a real app entry. Without them iOS screenshots the page and uses that shrunken image as the icon.

- `<link rel="apple-touch-icon" href="img/app-icon-180.png?v=N">` — **iOS will not accept an SVG here.** The vector source is `img/app-icon.svg`; the PNG is a 180×180 bake of it. Change the SVG and the PNG stops matching, so re-bake. The `?v=` is not the site-wide asset version and does **not** move with it — bump it only when the artwork itself changes, because iOS holds an already-installed icon for a very long time and someone who added the site to their home screen keeps seeing the old one otherwise.
- The icon must be **square with no rounded corners and no transparency.** iOS applies its own squircle mask, so rounding it here rounds it twice; transparent pixels are filled with black. `app-icon.svg` therefore starts with a full-bleed `<rect>`.
- `apple-mobile-web-app-capable=yes` launches it without Safari's address bar and toolbar — which also removes Safari's back button, so every route has to be reachable from the in-page nav. It is (the drawer covers everything). Two download paths exist (`code-embed.png` via html2canvas, and Archive attachment links); modern iOS routes those to the Files app, but they are the parts most likely to behave oddly in standalone mode.
- `apple-mobile-web-app-status-bar-style=default` keeps the clock/battery strip in its own space with the page starting below it. `black-translucent` would slide the page up under the notch and hide the top punch-hole strip.
- `apple-mobile-web-app-title` is the label under the icon; without it iOS uses `<title>` and truncates.

**Re-baking the PNG.** There is no build step and no rasteriser installed. The route used was: a scratchpad page with the SVG inlined, drawn into a 180×180 `<canvas>`, then `canvas.toBlob` POSTed to a throwaway Python server that writes the bytes to disk. Reading the base64 back through the browser tool does not work — base64 payloads are blocked in tool output. Afterwards verify the file really is 180×180 and that **minimum alpha across all pixels is 255**; a stray transparent pixel turns black on the home screen.

### Favicon

`index.html` links the SVG first and the PNGs after: browsers that understand SVG favicons use it at every size, the rest pick a PNG. 16 and 32 are baked separately because a browser halving the 32 looks visibly worse than one drawn at 16 from the start; 48 is for Chrome's shortcut tiles and Windows shortcuts. The `?v=` on these is the artwork's own, not the site asset version.

**Re-baking the favicon PNGs.** The canvas route above needs a working browser connection, which is not always there. These were produced instead by a throwaway Python script using **only the standard library** (`zlib` + `struct`), and that is the more reliable path because the artwork is just two shapes:

- For each output pixel, supersample 16×16 sub-points. For each sub-point, undo the transforms and test membership: undo `rotate(-8, 90, 90)`, then the ring is `62 ± 15/2` from the centre; for the plane, additionally undo `rotate(-14)` and `scale(1.95)` and run a ray-casting point-in-polygon test against the path's vertices (the nose's short bezier can be treated as a straight line — it is invisible at these sizes).
- Coverage fraction becomes the alpha; RGB is `#EF3921` everywhere.
- Write the PNG by hand: signature, `IHDR` (bit depth 8, colour type 6), one `IDAT` of zlib-compressed scanlines each prefixed with filter byte 0, `IEND`, each chunk followed by its CRC32.

Verify without eyes: re-parse the file and check the CRCs, then print an ASCII ramp of the 16×16 alpha channel — the ring and the plane should be legible in the terminal. Corner alpha must be 0 and the centre 255.

## Cache busting

`index.html` references its assets with a version query — `css/style.css?v=N`, `js/main.js?v=N`, `js/firebase-store.js?v=N` (and `firebase-store.js` imports `./firebase-config.js?v=N`). **Bump every one of those `N`s together whenever you change a CSS or JS file.** GitHub Pages serves the HTML with a short cache but assets with a long one, so without a bump a returning visitor gets new HTML with stale JS — and since `main.js` wires up elements at top level, a mismatch used to kill the whole script. The top-level init blocks now bail out politely when their elements are missing, but that only degrades gracefully; it does not make the page correct. The version bump is the actual fix.

## Workflow notes

- **Do not commit without testing first, and confirm with the user before committing.** Since there's no automated test suite, "testing" means actually loading the page (local server or the live site) and exercising the change in a browser — check the console for errors and confirm the save indicator behaves correctly for anything touching storage.
- **When a change touches color** (CSS colors, inline styles, color pickers, theme variables in `:root`), always print the affected HTML color codes (hex/rgba) in the response, not just describe the color.
